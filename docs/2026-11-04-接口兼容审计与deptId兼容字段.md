# 接口兼容性审计 + `deptId` 只读兼容字段

> 起因：`sys_user.dept_id` 改成多对多 `sys_user_depart` 之后，需要确认「之前写的接口」是不是都得跟着改。
> 结论：**65 个接口里只有 9 个涉及用户对象，且都是「只加字段」的兼容变化**；唯一有破坏性的一处
> （响应里 `deptId` 消失）本轮用只读兼容字段补齐，旧前端/旧 Postman 用例不用改。

### 唯一一处破坏性变化及处理

| 变化 | 影响 | 处理 |
| --- | --- | --- |
| 用户对象的 `deptId` 字段消失（改成 `depts` 数组） | 旧前端/脚本读 `user.deptId` 会拿到 `undefined` | 补 `deptId` 只读字段（= 主部门 id），旧代码继续可用 |

## 三、每个东西是干什么的

### 1. `deptId` 只读兼容字段

- 名字与旧字段一致，但**不是数据库列**，只在 Service 组装响应时赋值：`user.deptId = user.dept?.id ?? null`。
- `@ApiPropertyOptional({ deprecated: true })` 让 Swagger 里显示为「已废弃」，提醒新代码用 `depts`/`deptIds`。
- 写入侧被 `stripUnwritableFields` 删除，避免有人传 `deptId` 进 `PUT /users/:id` 时被 TypeORM 当成未知列。

### 2. `refreshToken` 改用 `findOneDetail`

原来 `refresh` 只查主表，返回的 `userInfo` 里既没有 `depts` 也没有 `deptId`，和登录返回结构不一致，
前端刷新令牌后用户信息会「退化」。改后三个入口（登录 / 刷新 / profile）结构完全一致。

### 3. 兼容性的边界

- 兼容的是**旧代码能继续跑**；不兼容的是「一个用户只能有一个部门」这个假设——旧代码若把 `deptId` 当唯一部门写回，只会覆盖主部门，不会清掉其它部门（`update` 只有显式传 `deptIds`/`deptId` 才重绑）。
- 若旧代码需要「编辑用户时回填部门」，读 `deptId`（主部门）即可；要支持多部门则改读 `depts`。

### 4.2 `src/modules/user/user.service.ts`（三个私有方法）

```ts
  /**
   * 去掉不允许客户端直接写入的字段
   * - depts / dept / deptId：关系字段与组装字段，非数据库列
   * - depart_ids / org_code：由 assignDepts 按主部门统一维护，避免两处写法互相覆盖
   */
  private stripUnwritableFields(data: Partial<UserEntity>): void {
    delete data.depts
    delete data.dept
    delete data.deptId
    delete data.departIds
    delete data.orgCode
  }

  /** 按 depart_ids 顺序整理部门，并把 depts[0] 同步到兼容字段 dept / deptId */
  private applyDepts(user: UserEntity): void {
    user.depts = this.orderDepts(user.depts ?? [], user.departIds)
    user.dept = user.depts[0] ?? null
    user.deptId = user.dept?.id ?? null
  }

  /** 批量补部门（列表页一次查关联表，避免 N+1） */
  private async attachDepts(users: UserEntity[]): Promise<void> {
    if (!users.length) {
      return
    }
    const rows = await this.repository.find({
      where: { id: In(users.map(user => user.id)) },
      relations: { depts: true }
    })
    const deptMap = new Map(rows.map(row => [row.id, this.orderDepts(row.depts ?? [], row.departIds)]))
    for (const user of users) {
      user.depts = deptMap.get(user.id) ?? []
      user.dept = user.depts[0] ?? null
      user.deptId = user.dept?.id ?? null
    }
  }
```

### 4.3 `src/modules/auth/services/auth.service.ts`（`refreshToken` 尾部）

```ts
  /** 用 refreshToken 换新令牌对 */
  async refreshToken(refreshToken: string): Promise<LoginResult> {
    let payload: JwtPayload
    try {
      payload = this.jwtService.verify<JwtPayload>(refreshToken, {
        secret: this.configService.get<string>('JWT_REFRESH_SECRET')
      })
    } catch {
      throw new UnauthorizedException('refreshToken 无效或已过期')
    }

    // 与登录返回保持同构：带角色与部门（depts / dept / deptId）
    const user = await this.userService.findOneDetail(String(payload.id))
    return this.issueTokens(user)
  }
```

## 五、遇到的坑

1. **只读字段一旦漏进 `update` 就会报未知列**
   TypeORM 的 `repository.update(id, dto)` 按实体元数据映射属性，`deptId` 不是列会直接抛错（或生成非法 SQL）。
   所以每加一个「非列展示字段」，必须同步加进 `stripUnwritableFields`。

2. **`deptId` 在 DTO 里是入参、在实体里是出参，同名不冲突但别混**
   `CreateUserDto.deptId`（deprecated，旧入参）和 `UserEntity.deptId`（只读出参）是两个不同的东西：
   一个定义请求体，一个定义响应体。看到同名不要以为「又把列加回来了」。

3. **`refresh` 返回结构容易漏**
   登录走 `findByUsername`（带 roles + depts），refresh 原来走 `findOne`（主表），
   改多部门后两边差得更多，前端刷新后拿不到部门。统一走 `findOneDetail` 才对齐。

4. **`string | null` 的 `deptId` 会不会又被推断成 Object？**
   不会，因为它没有 `@Column` 装饰器，TypeORM 根本不把它当列，也就不参与数据类型校验。

## 六、怎么验证 / 怎么用

```bash
# 1) 登录：deptId 回来了
curl -s -X POST http://127.0.0.1:3459/api/auth/login \
  -H "Content-Type: application/json" -d '{"username":"admin","password":"123456"}'
# data.userInfo → deptId: "dept_1", dept: {...}, depts: [...], orgCode: "A01"

# 2) 列表 / 详情 / profile / refresh 四个口都能读到 deptId

# 3) 旧入参仍可用
curl -s -X POST http://127.0.0.1:3459/api/users -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"username":"legacy_dept","realname":"旧参兼容","password":"123456","deptId":"dept_4"}'
# → deptId: "dept_4", depts: [研发部], orgCode: "A01A02"
```

| `GET /auth/profile` | `deptId=dept_1`、`depts=1` |

## 七、给前端的迁移建议

1. 展示部门：`user.depts.map(d => d.departName).join('、')`；只展示一个就继续用 `user.dept?.departName`。
2. 编辑用户：读 `user.depts.map(d => d.id)` 回填多选；顺序第一个作为主部门提示。
3. 提交：`{ deptIds: [...] }`；只有单部门场景也可以继续传 `deptId`，接口兼容。
4. 数据权限：后端已把主部门机构编码放到 `user.orgCode`，前端不需要自己拼。
