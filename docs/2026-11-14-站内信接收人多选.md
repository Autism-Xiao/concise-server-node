# 2026-11-14 站内信接收人改为多选选人控件

## 背景

用户提问：消息中心「发送站内信」的接收人，不是站内的吗，能不能多选？

排查结论：
- **接收人本来就是站内用户**：后端 `SendMessageDto.userIds` 收字符串数组（1~1000 个），按 `sys_user.username` / 用户 ID 双向解析，过滤不存在/已删账号——后端无需任何改动；
- **缺的只是前端体验**：原来是一个手填文本框（textarea，账号用换行/逗号分隔），要打字、容易拼错账号，拼错后只能靠后端「静默过滤」兜底，发件人无感知少发了人；
- 项目已有现成多选选人组件 `UserMultiSelect`（`features/users/components/user-multi-select.tsx`），公告表单在用：chips 标签 + 服务端搜索（账号/姓名/电话，防抖 250ms）+ 按租户收窄候选 + 已删用户红色 `#id` 兜底显示。

## 改动清单

| 文件 | 类型 | 说明 |
| --- | --- | --- |
| `concise-admin/src/features/system/message/index.tsx` | 修改 | 发送弹窗接收人从手填 Textarea 换成 `UserMultiSelect`；状态从字符串改为 `receiverIds: string[]`（提交时直接是用户 ID 数组，后端按 ID 精确匹配，不存在打错账号问题）；弹窗说明文案同步更新 |

仅前端 1 个文件，后端零改动。

## 行为变化

- 选人：点输入框弹出候选面板（服务端搜索、可连续勾选），chips 显示「账号（姓名）」，点 × 或退格移除，面板底部显示已选人数 + 清空；
- 提交：`userIds` 传用户 ID 数组（原来是用户名/ID 混填字符串），后端解析路径更直接；
- 权限边界：候选列表走 `GET /v1/users`（需 `system:user:list`），无该权限时面板提示「无法加载用户列表」——与公告选人控件行为一致。

## 踩的坑

1. **Textarea import 删早了**：弹窗里「正文」栏还在用 `Textarea`，删 import 导致 tsc 报 `Cannot find name 'Textarea'`——删 import 前先全局搜一遍组件内剩余引用；
2. **vite 只监听 `[::1]`**：无头脚本连 `127.0.0.1:5175` 报 ERR_CONNECTION_REFUSED，改 `localhost:5175` 才通；vite 端口被占会自动 +1（本次 5173/5174 被占落在 5175）；
3. **JS `input.focus()` 不可靠**：无头环境下面板没弹出，改用 CDP `Input.dispatchMouseEvent` 真实鼠标点击才触发 React onFocus；
4. **连续 `click()` 两个候选项只选中一个**：第一次 click 触发 React 重渲染，第二次 click 拿到的 DOM 节点引用已失效——测试脚本要「点一个 → 等 400ms 重渲染 → 重新 query 再点下一个」。

## 验证

- `tsc`、ESLint、`pnpm build` 全部通过；
- 无头浏览器实测（手签 admin JWT 注入）：弹窗打开、选人面板弹出且列出全部 4 个站内用户、勾选 2 人后 chips 正确显示、面板底部「已选 2 人/清空」正常。

## 如何扩展

- 其他「选人」场景（任务指派单选、公告指定用户多选）复用同一个 `UserMultiSelect`，`single` prop 控制单选/多选；
- 若发送方没有 `system:user:list` 权限又要选人，可考虑给后端加登录即可用的用户候选端点（类似 `lookup` 的搜索版），目前与公告一致先不加。
