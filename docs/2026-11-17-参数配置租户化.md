# 参数配置租户化（默认版）

- 日期：2026-11-17
- 类型：功能（多租户商业化 SaaS 化挂账项之一）
- 关联：`2026-11-17-租户隔离收尾.md` 中挂账的「租户级参数回退链」；`sys-config.entity.ts` 旧注释里预留的设计（「精确租户 → 回落 0 两级查找」）

## 需求

对照《多租户底座细化说明书》第 6 条「参数配置（双重隔离）」：

- 平台级参数：全局安全策略、邮件网关等，租户只读。
- 租户级参数：租户自定义，读取时**优先租户级，无覆盖则回退平台级**。

本次交付**默认版机制 + 一组默认租户参数**，前端页面暂不需要改（列表/保存接口契约向后兼容，新增字段均为附带信息）。

## 设计

### 数据模型（sys_config）

| 变更 | 说明 |
|---|---|
| 新增 `tenant_id`（int, default 0） | 0 = 平台级参数（所有租户的默认值）；>0 = 该租户的覆盖行 |
| 新增 `allow_tenant`（tinyint, default 0） | 平台闸门：1 = 租户可写覆盖行；0 = 仅平台可改（存量 security/mail/ops 全部为 0） |
| 唯一键 `uk_config_key` → `uk_tenant_config_key (tenant_id, config_key)` | 同一参数每个租户最多一行覆盖。存量全是平台行（tenant_id=0），全局唯一 ⇒ 联合唯一必然满足，无损切换 |

### 读取回退链

```
租户覆盖行 (tenant_id = 本租户) → 平台行 (tenant_id = 0) → 代码默认值 DEFAULTS → 调用方 fallback
```

- 进程缓存键从 `configKey` 改为 `${tenantId}::${configKey}`，一次加载全量行（参数行数少）。
- 任何写入后整表缓存失效（平台行变更会影响所有租户的回退结果）。

### 写入分流

| 视角 | 行为 |
|---|---|
| 平台（tenantId=null/0） | 直接更新平台行；无 allowTenant 限制 |
| 租户（tenantId>0） | 仅 `allow_tenant=1` 的参数可写；首次写入按平台行元数据（valueType/group/name/remark）生成覆盖行（isBuiltin=0）；已有覆盖行则改值 |

租户**不能新建参数键**（resolveWrite 以平台行为元数据来源，键不存在直接 400）；并发撞联合唯一转 400 可读报错。

### 新增接口

- `DELETE /v1/configs/override?configKey=` —— 租户取消覆盖（删自己的覆盖行，恢复跟随平台）；平台视角调用返回 400。权限 `system:config:update`。

### 默认租户参数（迁移预置，分组 tenant）

| 键 | 说明 |
|---|---|
| `tenant.ui.themeColor` | 租户品牌主题色，留空跟随平台默认 |
| `tenant.login.welcomeText` | 租户登录页欢迎语，留空跟随平台默认 |

两者 `allow_tenant=1, is_builtin=1`，是租户级差异化的样板；后续要开放更多参数给租户，把对应行的 `allow_tenant` 置 1 即可，无需改代码。

## 每项作用

- **resolveWrite**：写路径唯一入口——校验键存在、租户视角校验 allowTenant、定位覆盖行；updateOne/updateBatch 共用，批量「整批校验通过才写」的语义保持。
- **writeValue(manager)**：平台视角 update 平台行；租户视角 upsert 覆盖行（事务内传 manager）。
- **invalidate()**：写入后清整表缓存。原先只删单键，在两级回退下会漏（平台行变了，租户回退结果也变），参数行少，整表重建成本可忽略。
- **currentTenantId()**：`filterTenantId() ?? 0`——平台超管未指定租户（null）与无归属账号（0）统一按平台 0 处理。

## 踩的坑

1. **TS 类体内不能写 `private interface`**——第一次把 WriteTarget 声明在 class 里编译会挂，提到模块顶层。
2. **invalidate 语义变化**：单键失效 → 整表失效。两级回退下平台行变更影响所有租户，逐键失效容易漏。
3. **列表契约向后兼容**：新增 `allowTenant/platformValue/tenantConfigured` 字段，前端老代码不读也不炸；configValue 在租户视角变为「生效值」（覆盖优先）——这正是租户管理员期望的所见即所得。
4. **登录链路的上下文**：login 请求无 JWT，中间件上下文 tenantId=null → 读平台行 → 密码策略等安全参数天然平台级，租户即使有覆盖也不影响认证（这些键 allow_tenant=0，本就不可覆盖）。

## 如何扩展

- **开放更多租户参数**：平台把该参数行 `allow_tenant` 置 1（SQL 或后续平台管理页加开关），租户端即可覆盖，零代码改动。
- **新增参数**：DEFAULTS 加默认值 → 迁移插平台行（tenant_id=0）→ 需要租户差异化再置 allow_tenant=1。
- **前端增强（可选挂账）**：参数页对租户视角渲染「已覆盖/跟随平台」标签 + 「取消覆盖」按钮（调 DELETE override）；对 allow_tenant=0 的行禁用输入框。
- **平台查看各租户覆盖情况**：本次未做（list 平台视角仍只列平台行），需要时加 `GET /v1/configs/overrides?configKey=` 列各租户覆盖值。
