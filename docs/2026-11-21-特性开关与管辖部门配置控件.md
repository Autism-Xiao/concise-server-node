## 设计决策

1. **开关即数据**：不建新表、不引入配置中心，复用 sys_config 的 `feature.*` 键。平台在参数配置里新增一行（allow_tenant=1）即得到可按租户灰度的开关——「加开关零迁移、零代码发布」。DEFAULTS 里登记默认值只是缺行时的代码侧兜底。
2. **守卫位置**：FeatureGuard 放 PermsGuard 之后 ApiScopeGuard 之前。先鉴权再谈开关：无权限的用户拿不到 403-vs-404 的开关状态差异，避免通过错误码探测功能开通情况。
3. **两个消费者的语义刻意不同**：
   - `feature.rbac.superviseDept` 默认**开**——kill switch 模式，关掉即整体下线监管配置入口，存量行为不变；
   - `feature.log.maskSensitive` 默认**关**——opt-in 模式，开启才改变日志落库口径（宁可多打不漏：金额类整值 `***`，手机号保留前 3 后 4 便于排障）。
4. **params 惰性构建**：脱敏开关读取是异步的，把 params 计算从请求入口移进 concatMap/catchError（sys_config 有进程内缓存，开销可忽略）；失败日志与成功日志同口径。
5. **`GET /users/:id/supervise-depts` 独立成接口**而不是塞进详情：所有详情响应都多一次查询不值，只有配置对话框需要回显。

## 踩的坑

1. **`/g` 正则的 `test()` 有状态**（lastIndex）：手机号判定必须用非全局正则 `/^1[3-9]\d{9}$/`，替换才用 `/g`。
2. **布尔型 sys_config 的 API 写入值是 `true/false` 字符串**，传 `0/1` 会被 ValidationPipe 拒（"只能是 true 或 false"）——冒烟脚本第一版全栽在这。
3. **sys_log 的列名是 `operate_type`** 不是 `oper_type`。
4. **冒烟残留**：脚本中途异常退出时已写入的监管配置会污染下一次运行，脚本开头先重置再断言空集合（幂等原则）。
5. 旧文件里原有的 `sanitize(value)` 与新签名并存导致 TS2393 重复实现——编辑长文件时先读全文再改。

## 如何扩展

- **加一个新开关**：参数配置加一行 `feature.xxx`（allow_tenant=1）→ 代码侧 `@FeatureFlag('xxx')`（端点）或 `featureService.enabled('xxx')`（逻辑内）→ 前端 `GET /v1/features` 取 map 渲染。零迁移。
- **前端按 flag 渲染**：拉取 `/v1/features` 后按 `map['xxx']` 控制入口显隐；后端开关是权威，前端只是少展示。
- **管辖部门控件**：`SuperviseDeptsDialog` 是树形多选 + 全量覆盖；后端保存时展开子孙，所以只勾顶层节点即可。
