## 二、关键设计

### 1. 职级为什么是 `level_id` 单列而不是多对多

截图语义是一人一个职级（员工/部门经理这类职级天然唯一）。单列 + 索引比再造一张
`sys_user_level` 关联表省一张表、省一次事务，列表组装也只多一次 `In` 查询。
哪天要支持一人多职级再迁成关联表，成本也只是把列搬进关联表。

### 2. `resolveLevelId()`：空串归 null + 存在性校验

前端「未选择」提交的是 `''`，直接入库会留下空串而非 NULL（`IS NULL` 查询会漏）；
非空但不存在则必须 400 —— 否则写进去一条孤儿引用，列表永远显示 `-` 还没法排查。

### 3. `attachLevel()` 的空集合短路

先收集非空 `levelId` 去重，一个都没有就直接 return（多数用户的职级为空，不发空 `In()` 查询）。
与 `attachDepts/attachRoles/attachPosts/attachWatermark` 同款模式，列表一次列表 = 每类关联各一条批量 SQL。

### 4. 灌数脚本的幂等判据

| 数据 | 判据 | 存在时行为 |
| --- | --- | --- |
| 职级 | `level_name` | 刷新 `level_rank`（总经理助理插 4，副总经理→5，总经理→6） |
| 部门 | `depart_name + parent_id` | 跳过；另查 `org_code` 是否被**别的**部门占用（被自己占用是上次跑一半，不算冲突） |
| 岗位 | `post_code` | 刷新名称/排序/挂靠部门 |

## 三、遇到的坑

1. **QueryRunner 没有 `hasIndex`**（本版 TypeORM 只在 DataSource 上有）——迁移里判索引走
   `information_schema.STATISTICS`，和租户迁移判列是同一招。
2. **灌数脚本首跑漏了南山区研发中心**：预设的 `A01A02` 已被一个历史部门占用（其父部门不是 dept_1，
   所以从 dept_1 子部门列表里看不见）。改成 A01A05 并把「org_code 占用」判断改成排除同名部门，
   否则重跑时罗湖区研发中心会被自己的旧行挡住。
3. **冒烟测试在 sys_depart 留了 108 条垃圾**：`smoke_父部门_xxx / smoke_子部门_xxx` 成对出现
   （多租户冒烟跑了很多轮没清理部门）。脚本顺手按 `depart_name LIKE 'smoke\_%'` 清掉（108 条）。
4. **停用职级的回显**：下拉过滤 `status==='1'` 会把"已选了停用职级"的老用户显示成"未设置"，
   误保存就把历史值洗掉了。前端只过滤下拉**可选项**，编辑回显直接用 `user.levelId`（不在选项里时
   Radix Select 显示 value 本身，可接受）。

## 四、怎么扩展 / 使用

- **给用户设置职级**：用户管理 → 编辑 → 职级下拉（数据来自系统管理里的职级字典）；
  接口 `PUT /v1/users/:id` 带 `levelId`（`null` 清空）。
- **灌数**：`npm run build; if ($?) { node scripts/seed-user-demo-org.cjs }`，可重复执行。
- **列表再加列**：后端在 `listByQuery` 的 attach 链上加一条，前端 `index.tsx` 的 columns 里
  加一个 `accessorFn` 列即可。
- 冒烟账号（`smoke_verify_*`）仍在库里（del_flag=0），属于历史遗留，需要的话单独跑一轮清理。
