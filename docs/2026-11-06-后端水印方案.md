# 后端水印方案（设计稿，未落代码）

> ⚠️ **已废弃**：实际需求是「页面安全水印的用户级管控」，不是图片水印。请以
> `docs/2026-11-06-用户级页面水印方案.md` 为准，本文仅作历史记录保留。

> 状态：待评审。本文只做方案设计，不含实现。
> 目标：水印由**服务端**决定与生成，前端无法关闭、无法传参、无法绕过取到无水印原图。

---

## 一、需求边界

要做的是「图片水印」，且必须满足三条硬约束：

1. **服务端生成**：水印内容、位置、透明度、开关全部来自后端配置，上传接口不接受任何水印参数。
2. **不可绕过**：前端只能拿到已加水印的地址；无 watermark 参数时也一定带水印。
3. **可运维**：能一键关闭、能改文案后重跑、能定位到「谁上传的、什么时候」。

非目标（本期不做，避免范围失控）：PDF/Word 水印、Excel 导出暗水印、视频水印、盲水印溯源。若实际诉求是这几类，方案需另起一条线（见 §10）。

## 二、现状盘点

| 环节 | 现状 | 对水印的影响 |
| --- | --- | --- |
| 上传入口 | `POST /api/upload`（`tools/upload`，无 v1 版本） | 需要补 `/api/v1/upload`，与全站 v1 对齐 |
| 内存缓冲 | `FileInterceptor` 默认 memoryStorage，10MB 上限，单文件 | 可直接把 `file.buffer` 交给图像库，无需二次读盘 |
| 类型校验 | multer MIME 白名单 + `detectImageSignature` 文件头复核 | 已挡住「.html 改名为 .png」，是水印前置的可信输入 |
| 落盘 | `public/upload/{日期}/{类型}/{文件名}`，`saveLocalFile` 写盘 | **关键问题**：public 是公开静态目录，谁都能直接访问原图，水印形同虚设 |
| 静态托管 | `app.useStaticAssets(public)`，带 nosniff / CSP / attachment | 水印图沿用此路径，前端零改动 |
| 数据记录 | `tool_storage`：name / path / type / size / userId | 缺原图路径、宽高、水印状态，需加列 |
| 图像库 | 仅 `jimp@0.22.12`（纯 JS） | **不支持 WebP**，而上传白名单含 WebP；纯 JS 处理大图是秒级 CPU 占用，不适合在线链路 |
| 缓存/队列 | 已有 ioredis（`REDIS_ENABLED` 可关） | 可用于水印任务队列与派生图缓存，但非必须 |
| 限流 | 自研 `@RateLimit` 已在上传接口（30 次/分钟/IP） | 水印加工后 CPU 成本上升，需按账号维度再加一道 |

## 三、三条技术路线

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| **A. 上传时同步烧录** | 接收即处理，原图私存、派生图带水印公开 | 链路最短；出图后就是普通静态资源，CDN/浏览器缓存全部生效；前端零改动 | 同步占用 CPU，上传耗时增加约 100~300ms；改水印参数需重跑 | **本期主选** |
| B. 访问时动态生成 | 走 `/api/v1/upload/:id/view`，每次请求实时叠加 | 可按登录用户打不同水印（溯源）；改参数立即生效 | 每次请求吃 CPU，必须做缓存与签名 URL；`<img>` 带不了 Authorization 头，前端改造成本高 | 二期，仅用于敏感图/溯源 |
| C. 异步队列烧录 | 上传先落原图返回 id，后台任务生成 | 上传快，可重试、可批量补跑 | 存在「刚上传看不到图」的窗口，前端要轮询；复杂度最高 | 图片量大（>1 万/天）再考虑 |

**推荐组合**：一期 A（同步烧录）+ 保留原图 → 二期按需接 B（动态/溯源）。A 和 B 共享同一套水印渲染内核，不重复开发。

## 四、推荐架构（一期）

```
前端 multipart(file)
   │  不收任何水印参数，DTO 里也不声明（whitelist 会剔除）
   ▼
POST /api/v1/upload
   │
   ├─ 1. multer：MIME 白名单 + 10MB + 单文件          （已有）
   ├─ 2. magic bytes 复核真实类型                      （已有）
   ├─ 3. sharp 元数据预检：宽高 ≤ 10000、总像素 ≤ 2400 万、拒绝动图/异常帧
   ├─ 4. 原图落盘 → var/storage/private/{日期}/{类型}/   （非公开目录）
   ├─ 5. 读水印策略（服务端唯一来源：配置文件 + DB 覆盖）
   ├─ 6. sharp 渲染：rotate(EXIF) → resize(长边≤2560) → 平铺水印 → 去元数据 → 按原格式编码
   ├─ 7. 派生图落盘 → public/upload/{日期}/{类型}/        （路径约定不变）
   └─ 8. 写 tool_storage（原图路径 / 宽高 / 水印快照 / sha256）
   ▼
返回 { id, path, width, height, watermarked: true }   ← 前端只拿得到这个 path
```

**「前端不能控制」的三道保证**：

1. 接口契约里没有水印参数（`ValidationPipe({ whitelist: true })` 会丢弃前端多传的 `watermark=false`）。
2. 策略只从服务端读（`config/watermark.config.ts` + 可选 DB 表），与请求体无关。
3. 原图不在 `public`，`tool_storage.path` 只指向派生图；想拿无水印图必须读服务器文件系统。

## 五、关键设计

### 5.1 水印策略

一期用配置文件 + 环境变量（够用、可 review、可回滚）：

```ts
// src/config/watermark.config.ts
export interface WatermarkConfig {
  enabled: boolean // 总开关，false 时原图直接落 public（保留旧行为）
  text: string // 全局文案，如「内部资料 · 禁止外传」
  includeAccount: boolean // 是否追加「用户名 + 日期」用于溯源
  opacity: number // 0.04 ~ 0.35
  rotate: number // 建议 -30
  logo: string | null // public 之外的白名单路径，不允许用户上传
  maxEdge: number // 派生图长边上限
  fontFamily: string // 中文字体名，见 §9 坑位
}
```

二期加 `sys_watermark_policy` 表支持按角色/目录/业务线覆盖，`scope` 优先级：user > role > global。

### 5.2 水印算法要点

- **平铺而非单点**：单角水印一裁就没。用一块 tile（文字 + 间距）以 `composite: [{ input: tile, tile: true }]` 平铺，裁掉任何区域都还有。
- **尺寸自适应**：字号 ≈ `min(width, height) / 28`（下限 14px），间距随字号走，避免大图水印小到看不清、小图水印糊满。
- **明暗自适应**：`sharp(buf).stats()` 取通道均值，暗图用浅色水印、亮图用深色，或统一「白字 + 半透明黑描边」，保证任何底图都可读。
- **先缩放再打水印**：2560 长边足够展示，处理量降到原图的 1/3~1/5，水印边缘也不会因二次压缩糊掉。
- **去元数据**：`withMetadata(false)`，顺手清掉 EXIF 里的 GPS/设备信息（原有链路没做，算是额外收益）。
- **tile 缓存**：文字 + 字号 + 颜色 → sha1 → `var/cache/watermark/{hash}.png`，同样参数只渲染一次。

### 5.3 存储布局

```
var/storage/private/2026-11-06/图片/a-20261106xxxx.png   ← 原图（不进静态目录）
public/upload/2026-11-06/图片/a-20261106xxxx.png          ← 带水印派生图（对外）
```

原图的保留策略：默认长期保留（重跑水印、审计需要）；磁盘吃紧时按「派生图存在超过 N 天且业务表未引用」清理，做成独立任务而非上传时同步删。

### 5.4 表结构变更（新增迁移）

```sql
ALTER TABLE tool_storage
  ADD COLUMN source_path VARCHAR(255) NULL COMMENT '原图私有路径',
  ADD COLUMN width INT NULL COMMENT '宽',
  ADD COLUMN height INT NULL COMMENT '高',
  ADD COLUMN watermark_status TINYINT NOT NULL DEFAULT 0 COMMENT '0未处理 1已烧录 2失败 3跳过(动图)',
  ADD COLUMN watermark_spec JSON NULL COMMENT '水印参数快照(服务端生成)',
  ADD COLUMN sha256 CHAR(64) NULL COMMENT '原图摘要, 可用于秒传/查重',
  ADD INDEX idx_storage_sha256 (sha256);
```

历史数据：`source_path` 为空 → 视为「无原图」，不再重跑，直接沿用现有公开文件（见 §8 兼容）。

### 5.5 接口

| 方法 | 路径 | 说明 | 权限 |
| --- | --- | --- | --- |
| POST | `/api/v1/upload` | 上传并返回带水印的 path；`/api/upload` 保留兼容 | `tools:upload` |
| GET | `/api/v1/upload/config` | 仅回显 `{ watermarked: true }`，不暴露参数细节 | 登录 |
| POST | `/api/v1/storage/:id/rerender` | 改文案后重跑单张（幂等） | `tools:upload:rerender` |
| POST | `/api/v1/storage/rerender` | 按日期/类型批量重跑，返回任务 id | 同上 |

批量重跑走后台任务（`setImmediate` 分批 + 限速），不要在一次请求里跑几百张图。

### 5.6 依赖选型：sharp 而非继续用 jimp

| 维度 | jimp 0.22 | sharp 0.34 |
| --- | --- | --- |
| WebP | 不支持（上传白名单里就有） | 支持 |
| 4K 图耗时 | 纯 JS，秒级 | 原生 libvips，几十到两百毫秒量级（经验值，落地需实测） |
| 平铺水印 | 需手工逐块 composite，代码量大 | `tile: true` 一行 |
| 并发 | 单线程占满事件循环 | 内部线程池，可 `sharp.concurrency(2)` 限流 |
| 部署 | 纯 JS，零负担 | 平台相关二进制，换平台需重装（与 `@node-rs/argon2` 同类问题） |

结论：sharp。项目已经接受过 argon2 的平台相关性，部署侧成本可复用（见 §9）。

## 六、性能与容量

- 单张成本：解码 + 缩放 + 平铺，2560 长边下量级 100~300ms（含 tile 生成）。上传接口现状是同步返回，可接受；若压测超 500ms，退化为方案 C。
- 并发保护：`sharp.concurrency(2)` + 全局信号量（同时处理 ≤ 4 张），超出排队而非直接吃满 CPU；配合已有 `@RateLimit`，按 userId 限 10 次/分钟。
- 缓存收益：tile 缓存后，同参数图片只多一次 composite 与编码，实测量级会明显低于首次。
- 磁盘：原图 + 派生图 ≈ 1.6 倍单份体积。按日均 200 张 × 3MB 估，约 1GB/天，需配清理策略。

## 七、安全清单

1. **解压炸弹**：`sharp(buf, { limitInputPixels: 24e6 })`，超限抛错转 400，不要让它进解码器。
2. **SVG 注入**：用户名字若来自 DB（如 `includeAccount`），拼进 SVG tile 前必须 XML 转义 `& < > " '`；否则 `<image href="file:///...">` 这类 payload 有读取本地文件的风险。
3. **字体白名单**：`fontFamily` 只从配置读，不接收外部输入。
4. **原图暴露面**：`var/storage/private` 不能出现在 `useStaticAssets` 里；顺手在 `.gitignore` 排除。
5. **派生图缓存头**：`Cache-Control: public, max-age=31536000, immutable`（文件名带时间戳，天然不冲突）。
6. **失败降级**：处理异常时**不要**回落到「原图直接公开」，应返回 500 并记录，否则一次异常就等于水印被绕过。
7. **EXIF 剥离**：避免上传者把敏感 GPS 信息随图流出（原链路未做）。

## 九、坑位清单（提前避雷）

1. **中文字体豆腐块**：sharp 的 SVG 文本依赖系统字体。Windows 开发机有「微软雅黑」，Linux 容器默认没有 → 生产镜像必须装 `fonts-noto-cjk`（或用 `FONT_PATH` 指定 ttf），否则水印全是 `□□□`。建议加**启动自检**：渲染「水印自检」并比对非空像素，失败则 warn 提示。
2. **WebP / GIF**：jimp 读不了 WebP，这是必须换 sharp 的直接原因。GIF 动图一期建议**跳过着色**并记 `watermark_status=3`（强行处理会变静态帧，属功能回退，需产品确认）。
3. **pnpm 安装**：sharp 有安装脚本，会撞 `ERR_PNPM_IGNORED_BUILDS`（本项目已遇到过 `@scarf/scarf`）。需在 `pnpm-workspace.yaml` / `package.json` 的 `pnpm.onlyBuiltDependencies` 放行 `sharp`，否则 `require('sharp')` 在运行时报找不到二进制。
4. **平台相关性**：node_modules 不可跨平台拷贝（Windows 开发 → Linux 生产必须重新 `pnpm install`），与 argon2 同一类问题，部署文档要写。
5. **`sharp` 是可选依赖**：建议懒加载 + 缺失时直接启动失败（fail fast），而不是静默降级成无水印——静默降级是最危险的行为。
6. **BMP**：编码支持有限，统一转 PNG 输出更稳（前端不关心扩展名）。
7. **`@Type(() => Number)` 无关但易踩**：本方案新增的 DTO 字段若含数字，记得加，否则 query 参数是字符串。
8. **静态目录命中优先级**：`useStaticAssets` 在 Nest 路由之前注册，派生图路径不要和接口路径重叠（保持 `/upload/...` 前缀即可）。

## 十、若诉求其实是「导出文件加水印」

如果是给导出的 Excel / CSV / PDF 打水印，方案完全不同，先说清楚再动手：

- Excel（已有 exceljs）：页眉页脚文案 / 单元格背景图做平铺（需 `addImage` + 定位），只能做「可见弱水印」，防不住复制。
- PDF：需引入 `pdf-lib`，在每页叠加半透明文字/图层。
- 这类水印本质是「事后可移除」，只能做**威慑与溯源**，不能做**访问控制**。图片水印若原图不私存，同样是这个性质——所以 §5.3 的原图私有化是整个方案的地基。
