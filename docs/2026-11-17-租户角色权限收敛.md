# 租户角色权限收敛（菜单 / 角色 / 导出）

> 2026-11-17 · 安全 · 承接《租户访客用户权限收紧》，影响：所有租户的 `viewer` / `editor`

## 清出来的三类问题

把三个租户的 viewer 授权摊开对比后，发现租户 1（默认租户，角色是早期手工建的）比模板生成的租户 19/20 **多 4 条高危授权**，`sys_role_permission.operate_date` 为 null 说明是直接 SQL 插的、绕过了业务层。

| 类别 | 权限 | 判断依据 |
|---|---|---|
| 菜单管理 | `system:menu:list/add/update/delete` | 菜单表全平台共享（`sys_permission` 不分租户），改一处影响所有租户的侧边栏 |
| 角色配置 | `system:role:list` + `system:role:export` | 角色权限是「谁能干什么」的配置表，租户内也只该管理员看 |
| 组织架构导出 | `system:dept:export` / `level:export` / `post:export` | 一条接口就能把整个部门树、岗位、职级拉成文件 |
| 死码 | `system:log:export` | 没有配套的 `log:list`，接口拿到了也用不上，却让「安全审计」空分组一直挂在侧边栏 |

## 实测后的重要澄清

`system:menu:add` 这类权限**即使被脏数据授予，实际也调不动**：`/v1/menus` 返回

```
403 code=1004 「system:menu:add」是平台级权限，仅平台管理员可操作
```

PermsGuard 对 `scope='platform'` 的权限码有第二层判定（要求 `is_platform_admin`），所以这不是「正在被利用的漏洞」。本次清理属于**最小权限 + 纵深防御**：让租户角色的授权表与实际能力一致，避免以后有人去掉 scope 校验时这些脏授权变成真后门。

## 改动

| 文件 | 类型 | 说明 |
|---|---|---|
| `src/modules/system/tenant/tenant-role-template.ts` | 修改 | `TENANT_RESTRICTED_MODULES` 增加 `system/menu`、`system/role` 两个模块（新租户自动不授予） |
| `src/migrations/1794880000000-TightenTenantViewerPerms.ts` | 新增 | 删 `tenant_id>0` 且 `viewer/editor` 的 `system:menu:*`、`system:role:*`、四个导出权限；`down` 按旧白名单幂等补回 |

删除条件是 **perms 前缀 + url 前缀双条件**：页面节点万一没写 perms，靠 `/system/menu`、`/system/role` 的 url 兜住，否则只删按钮会留下一个点进去 403 的菜单入口。

## 验证（3461，清过 `perm:role:*`）

租户 1 的 viewer 从 31 条降到 21 条，剩余：

```
目录 5：仪表盘 / 系统管理 / 数据管理 / 安全审计 / 协同办公
页面 12：数据字典 通知公告 日历 行政区划 文件 消息 部门 供应商 岗位 任务 职级 订单 客户
按钮 3：字典导出 文件下载 公告查询
```

接口层：

```
GET  /menus     403（平台级权限兜底）    GET /roles    403
POST /menus     403                      GET /users    403
GET  /depts     200   /posts 200   /levels 200   /regions 200   /files 200
GET  /dicts     200   /notices 200  /messages 200  /tasks 200
```

菜单树：5 个分组 / 13 个页面 / 14 个权限码。

## 仍未解决（P2 挂账）

「安全审计」是**空目录**（`menu_audit` 授予了，但下面一个页面权限都没有），前端 `treeToGroups` 把无子项的目录当普通菜单项渲染，所以侧边栏会出现一个点进去 `/audit` 404 的入口。

根因在模板：`acceptsByLevel` 对无权限码的目录节点一律放行，不检查它是否有可见子节点。要彻底修需要三处一起动：

1. `provisionIn`：算完 targetIds 后，剔除「没有任何已选子节点」的目录节点
2. 迁移：清理所有租户 viewer/editor 的空目录授权
3. 前端 `treeToGroups`：`loose` 只收 `menuType === 1` 的节点（防御历史数据）

## 踩的坑

1. **`operate_date` 为 null 是脏数据指纹**：`grant()` 写入时一定带 `NOW()`，为空说明是手工 SQL 插的。以后排查「这条授权是谁给的」，先看这个字段。
2. **url 要按前缀匹配而不是精确**：`/system/menu` 与 `/system/menus` 两种写法在库里都出现过，用 `LIKE '/system/menu%'` 才不漏。
3. **别把「有脏授权」直接等同于「可利用」**：先实测接口，PermsGuard 的平台级 scope 判定会兜住一部分。结论写进文档，避免下次复现时误判严重性。
4. **缓存必须手清**：角色权限集合缓存在 Redis（`perm:role:<roleId>`，TTL 300s），迁移改完 DB 后用旧缓存仍能拿到已删的权限，要 `DEL perm:role:*` 或重启。

## 如何扩展

- 继续收紧：往 `TENANT_RESTRICTED_MODULES` 加 `{ urlPrefix: '/system/file', permsPrefix: 'system:file' }` 就能让访客连文件管理都没有（注意 `file:download` 是租户内合法需求，要单独权衡）。
- 想按「页面」而不按「模块」排除：`restrictedMenuIds` 已经支持任意多个 module 条目，粒度可以细到单个 url（如 `/system/dept/export`）。
- 让编辑者能改菜单但访客不能：把 module 条目改成带 `levels: ['read']` 的形态，在 `restrictedMenuIds` 里按 level 过滤即可 —— 当前实现是「read 和 write 一视同仁」。
