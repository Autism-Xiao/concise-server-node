## 二、每个东西是干什么的

**唯一键口径（本次统一）**：

- **DB 层**：`(tenant_id, code)` 联合唯一 → 保证「同一租户内不重码」；**允许租户之间重码**。
- **应用层查重**：`applyTenantScope`（本租户 ∪ `tenant_id=0` 共享行）→ 租户视角还**不允许与平台内置编码冲突**（避免运行时按编码取字典产生歧义）；平台视角（tenantId=null）全局查重。
- 两层合起来的语义：租户之间可重码，租户不能冒充/覆盖平台内置编码。迁移只动 DB 层（原全局唯一比联合唯一更严，存量数据必然满足新约束，`ADD UNIQUE` 不会失败）。

**service 层顺带修掉的同类问题**（改唯一键时发现，与 P0 审计同源的漏网）：

- `dict.service` 的 `findActive`/`updateDict`/`deleteDict`、`dict-item.service` 的详情/更新/删除原来都是**不带租户条件的直写**——租户管理员知道 id 就能改/删平台字典。现在读路径走 `applyTenantScope`、写路径全部加 `tenantWriteCondition`（共享行只有平台视角能改，命中不了按 404 处理）。
- 三处导入（字典/岗位/职级）原来 `repository.find()` 全表捞 + 按编码全局匹配更新，租户导入会**跨租户改到别人的数据**。现在：匹配范围收进租户可见范围；命中共享行时按「与平台内置编码冲突」报行级错误而不是更新它；导入新建的字典项（`manager.save` 不走 BaseService）显式补 `tenantId` 打标。

## 三、遇到的坑

1. **「不许撞共享行编码」DB 层表达不了**：联合唯一键 `(tenant_id, code)` 天然允许 `tenant_id=0` 与租户行同码，这条语义只能靠应用层查重（租户范围含共享行）实现——DB 探针测试「租户撞共享编码成功」不是 bug，是分层设计。
2. **`manager.save` / `repository.update` 绕过 BaseService**：租户打标（`stampTenant`）和写条件（`tenantWriteCondition`）都挂在 BaseService，凡是手写直连 repository 的路径都要自己补——本次字典项导入落库、dict-item 更新/删除全是这类。
3. **导入是隐性跨租户写入口**：`find()` 不带范围 + 按 code 全局匹配 + 直写，租户导入平台内置编码的数据就能改掉平台数据。导入的「已存在即更新」语义必须连同租户边界一起收窄。
4. **dept 的 org_code 生成链路是租户感知的既有正确实现**（sibling 查询已走 `applyTenantScope`），但占用检查用的全局 `count`——两者口径不一致，统一收进 `isOrgCodeTaken()`。
5. 数据权限过滤走的是部门 **ID**（`sys_user_depart.dep_id IN`）而非 org_code 前缀，所以放开 org_code 跨租户重码不会引起数据权限串数据（改之前专门核查过 `applyDataScope`）。

## 四、怎么扩展/使用

- **以后新增带 tenant_id 且有业务编码的表**：建表迁移直接写联合唯一键 `(tenant_id, xxx_code)`；实体**不要**写 `unique: true`；service 的查重用 qb + `applyTenantScope`（不要裸 `findOne({ where: { code } })`）；导入按「租户可见范围匹配 + 共享行报冲突 + `this.create` 走 BaseService」三件套。参照本次 dict/post/level。
- **平台内置数据（tenant_id=0）的编码是全局保留字**：租户创建/导入撞内置编码会得到 400（单条）或行级失败（导入），文案里写明「与平台内置 XX 冲突」。
- **迁移幂等**：`TenantUniqueKeys17948200000000` 的 up/down 都用 `information_schema.STATISTICS` 探测索引再动，可安全重跑；down 要求届时表内无跨租户重码（上线后产生过重码需先人工处理）。
- **冒烟要点**：跨租户重码、同租户重码拒绝、租户撞共享编码拒绝、租户读只见自己+共享，四条都要测（本次用 3461 免验证码实例 + `X-Tenant-Id` 头实测通过，探针数据已清理）。
