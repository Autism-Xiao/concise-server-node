# 前后端冒烟测试与代码隐患分析

> 日期：2026-11-06　｜　范围：`concise-server-node`（117 个 v1 接口 + 40 个旧版接口）、`concise-admin`（全量源码）
> 结论速览：**功能链路基本健康（136 项检查 130 通过），但存在 1 个中高危安全问题、3 个数据一致性缺陷、4 个安全基线缺失**

## 一、这轮怎么测的

不是「点几下页面」，而是三层验证：

| 层次 | 做法 | 产出 |
| --- | --- | --- |
| 接口层 | 新写 `scripts/smoke-test.cjs`，对着 3460 端口的独立实例跑 136 项断言 | `PASS 130 / FAIL 6` |
| 数据层 | 每条写操作前后查库核对，结束后按 `smoke_` 前缀清理 | 无残留（已核对 8 张表） |
| 代码层 | 静态审读鉴权链、异常兜底、事务、上传、密码、分页、缓存 | 20 条隐患，分级如下 |

测试环境要点：

- **不硬编码任何真实密码**：管理员令牌用 `.env` 的 `JWT_SECRET` 直接签发（HS256，与后端同算法）；需要验证登录链路时，脚本自己建临时账号 + `crypto.randomBytes` 生成密码，用完即删。
- 测试实例以 `PORT=3460 CAPTCHA_ENABLED=false` 启动，这样才能真实跑通「登录 → 拿令牌 → 调接口」；3000 端口的开发实例（验证码开启）未受影响。
- 所有写操作只碰 `smoke_` 前缀数据，脚本末尾统一删除，失败也会在「清理」小节暴露出来。

## 三、6 项失败：逐条定位

### ① 上传接口不做类型校验 → 存储型 XSS（**中高危**，实测复现）

`upload.controller.ts` 里定义了白名单常量，但**从未使用**：

```ts
export const UPLOAD_MIMETYPES = ['image/png', 'image/gif', 'image/jpeg', 'image/webp', 'image/svg+xml']

@Post()
@UseInterceptors(FileInterceptor('file', { limits: { fileSize: UPLOAD_FILE_SIZE } }))  // 只有体积限制
```

实测：

```
POST /api/upload  （Content-Type: text/html，内容 <script>alert(document.domain)</script>）
→ 200 {"path":"/upload/2026-11-06/其他/xss-test-20261106123241055.html"}

GET /upload/2026-11-06/其他/xss-test-20261106123241055.html
→ HTTP 200  text/html  65 bytes   ← 浏览器会执行里面的 JS
```

因为 `main.ts` 里 `app.useStaticAssets(path.join(process.cwd(), 'public'))` 把上传目录公开挂载，攻击者只要有一个 `tools:upload` 权限的账号，就能上传 HTML/SVG 拿到**同源脚本执行**，配合前端把 token 存在 `localStorage`，可直接窃取管理员会话。

修复建议（任一或组合）：

1. 加 `fileFilter` 真正校验 `UPLOAD_MIMETYPES`，并用文件头（magic bytes）复核，不只信 `Content-Type`；
2. 上传目录 `setHeaders` 强制 `Content-Disposition: attachment` + `X-Content-Type-Options: nosniff`；
3. 更彻底：文件走独立域名/对象存储，与主站不同源；
4. 若必须支持 SVG，用 `<img>` 展示、禁止直接打开。

### ② 重复用户名创建 → HTTP 500（**中危**）

```
POST /v1/users {"username":"smoke_user_xxx","realname":"重复账号","password":"another-password"}
→ 500 {"code":1006,"message":"服务器内部错误"}
服务端日志：QueryFailedError: Duplicate entry 'smoke_user_xxx' for key 'sys_user.uniq_sys_user_username'
```

根因：`user.service.create()` 直接 `save`，没有前置查重、也没捕获 `ER_DUP_ENTRY`。对比之下 `import` 路径做得很好（会提示「该账号已删除，但唯一索引仍占用，请先恢复原账号或换一个」），`role`/`dict` 也都有前置校验 —— 只有「新建用户」这条路径漏了。

同类隐患：其他表若有唯一索引而未前置校验，都会以 500 形式暴露。

### ③ 软删除用户残留关联表 → 角色永远删不掉（**中危**，实测复现）

```ts
// user.service.ts
async delete(id: string): Promise<void> {
  ...
  await this.repository.update(id, { delFlag: 1 })   // 只改标记，不动 sys_user_role / sys_user_depart
}

// role.service.ts
const users = await this.roleRepository.createQueryBuilder().relation(RoleEntity, 'users').of(id).loadMany()
if (users.length) throw new BadRequestException(`该角色下还有 ${users.length} 个用户，请先解绑后再删除`)
```

实测链路：创建用户并绑定新角色 → 删除该用户（软删成功）→ 删除角色，返回：

```
400 该角色下还有 1 个用户，请先解绑后再删除
```

而那个「用户」已经被删除、在界面上根本找不到，也就无法解绑 —— **角色进入死锁，只能改库**。同时 `sys_user_role` / `sys_user_depart` 会随删除次数无限累积，将来恢复账号时旧权限会「自动复活」。

修复建议（推荐方案）：

1. 软删用户时同步删除 `sys_user_role` / `sys_user_depart`（推荐，语义清晰）；
2. 或角色删除保护改为只统计 `del_flag = 0` 的用户；
3. 或在恢复账号时重建关联（与 1 不冲突，1 更简单）。

### ④⑤⑥ 三个安全基线缺失（**中低危**，均为「缺能力」而非「有 bug」）

| 项 | 实测 | 影响 |
| --- | --- | --- |
| `X-Powered-By: Express` 暴露 | 响应头存在 | 泄露技术栈，便于针对性扫描 |
| 无 `X-Content-Type-Options` | 缺失 | 配合 ① 的 HTML 上传更危险 |
| 无 `X-Frame-Options` / CSP | 缺失 | 可被 iframe 嵌套做点击劫持 |

三个都是装 `helmet` 一行的事（注意上传静态目录要单独放开，别让 CSP 把图片/Jimp 生成的头像拦了）。

### ⑦ 分页返回结构不统一（**中危**，影响前端可扩展性）

| 返回 `{records,total,current,size,pages}` | 返回纯数组（无 total） |
| --- | --- |
| `/v1/users`、`/v1/notices`、`/v1/jobs`、`/v1/logs/*`、`/v1/online` | `/v1/roles`、`/v1/depts`、`/v1/levels`、`/v1/posts`、`/v1/dicts`、`/v1/menus` |

后者即使传了 `?page=1&pageSize=2` 也不返回总数，前端只能「全量拉回来再本地分页」。现在数据量小看不出问题，字典/部门/菜单一旦上千条，前端首屏就会明显卡顿，且没法做服务端分页。

建议：统一成 `{records, total, current, size, pages}`（`helper/paginate` 已有这套结构，让 6 个模块改用即可），或至少在 DTO/文档里写明两套约定并给前端一个 `normalizeList()`。

## 四、代码层面另发现的隐患（静态审读，未在冒烟中体现）

### A. 全项目 0 处事务（**中危**）

```
grep -rln "transaction(" src  →  0 个文件
```

多步写的场景至少三处：

| 场景 | 步骤 | 中断后果 |
| --- | --- | --- |
| 新建用户 | 插 `sys_user` → 插 `sys_user_role` → 插 `sys_user_depart` | 用户建好了但没有角色/部门；重试又撞唯一索引 |
| 更新用户 | 更新主表 → 重绑角色 → 重绑部门 | 角色已换、部门没换 |
| 角色授权 | 删旧 `sys_role_permission` → 插新 | 删完没插上 → 该角色瞬间失去全部权限 |

修复：`dataSource.transaction(async manager => {...})` 包一层即可，改动量不大，收益很直接。

### B. 无任何请求限流 / 登录失败锁定（**中危**）

依赖里没有 `@nestjs/throttler`，`main.ts` 也没有限流中间件。现在唯一的防爆破手段是滑块验证码，而验证码是**开关式**的（`CAPTCHA_ENABLED=false` 即为关闭）。一旦关闭或验证码服务异常（Redis 挂掉时验证码接口 503），登录接口就是无限次撞库。

建议：`@nestjs/throttler` 全局 100 次/分钟，登录单独收紧到 5 次/分钟 + 同账号连续失败 5 次锁 15 分钟（可复用 Redis，在线会话已经用上了）。

### C. 密码算法是 PBEWithMD5AndDES（**中危，兼容性使然**）

`password.util.ts` 复刻 JeecgBoot 的 PBKDF1-MD5(1000 次) + DES-CBC，输出 16 位 hex。DES 密钥 56 位、MD5 已可高速并行，GPU 下弱密码几分钟即出。

这是为了兼容既有 `sys_user` 数据，短期不能直接换。建议路线：新密码用 argon2id/bcrypt 存，登录校验时「旧格式通过 → 顺手用新算法重写该行」做透明迁移，两套并存期间用一个字段或前缀区分。

### D. `trust proxy = true` 无条件开启 → 审计 IP 可伪造（**中低危**，实测复现）

```ts
app.set('trust proxy', true)
```

实测：请求头加 `X-Forwarded-For: 1.2.3.4` 后，登录日志记录的 `ip` 就是 `1.2.3.4`。当前是直连部署（没有 Nginx），任何客户端都能伪造来源 IP，登录日志/操作日志的 IP 归属地和风控判断全部不可信。

修复：只在确认部署在反代后面时开启，并指定受信代理网段，例如 `app.set('trust proxy', 'loopback, 10.0.0.0/8')`；或由环境变量 `TRUST_PROXY` 控制。

### E. Swagger 无鉴权且始终开启（**中低危**）

`/api/docs` 无需登录即 200，`/api/docs-json` 可导出完整 OpenAPI。开发方便，但生产等于把 117 个接口的入参结构、权限点、业务码全部公开。

修复：`if (process.env.NODE_ENV !== 'production')` 才 `SwaggerModule.setup`，或加 Basic Auth。

### F. refreshToken 不轮换（**中低危**）

`refreshToken()` 校验通过就直接签发新令牌，**旧 refreshToken 不会失效也不会被拉黑**（只处理了 logout 场景）。结果是：refreshToken 一旦泄露，7 天内可以无限续期且无法被察觉（无「同一 refreshToken 被重复使用」告警）。

修复：刷新时把旧 refreshToken 加入黑名单（`online:revoked:*` 机制已有），并检测「已用过的 refreshToken 再次出现」→ 判定为盗用，踢掉该用户全部会话。

### G. 每请求 3–5 次 IO，权限实时查库（**性能隐患**）

单个受保护请求的固定开销：

1. Redis `GET` 黑名单
2. MySQL 查用户 + 角色（`findOneWithRoles`）
3. MySQL 查权限（`PermsGuard` 的 `sys_permission join sys_role_permission`）
4. Redis `SETEX` 刷新会话

本地 10–20ms 无感，但 QPS 上去后 DB 会被这类「与业务无关的鉴权查询」占满。建议：权限集合按 `userId` 缓存 30–60 秒（角色/菜单授权变更时主动失效），在线会话 `lastActive` 改成 60 秒才写一次（现在是每请求都写）。

### H. 其他一致性 / 维护性问题

| 问题 | 说明 |
| --- | --- |
| 旧版 40 条路由与 v1 并存 | 双份实现（`user.controller.ts` 与 `user.v1.controller.ts`），目前权限一致（实测旧路由同样 403），但靠人自觉维护，容易漂移；建议加 `Deprecation` 响应头并排期下线 |
| 登录成功返回 201 | Nest POST 默认 201，语义上登录应为 200；前端不care，但网关/压测工具会当成「创建成功」 |
| 验证码错误返回 HTTP 200 + code 412/413 | 与登录失败 401 不一致，WAF/监控无法按状态码统计攻击量；建议验证码类业务异常也用 400 |
| 同一 handler 只能建一条定时任务 | `jobClassName` 唯一，但 `/v1/jobs/handlers` 不返回「是否已被占用」，前端下拉让用户选到已占用项必然报错；也无法给同一任务配两套 cron 参数 |
| 批量删除静默忽略不存在的 id | 实测 `ids:[a,b,不存在]` → `{"deleted":2,"failed":[]}`，前端无法解释「明明选了 3 个」 |
| 在线会话列表 SCAN 全表 + 内存分页 | O(n)，会话上万时 `/v1/online` 会明显变慢 |
| 部门树 / 菜单树 / 角色下拉对所有登录用户开放 | 组织架构与菜单权限结构对内网全员可见，是否符合预期需确认 |
| 死代码 | `UPLOAD_MIMETYPES`（见 ①）、`netdisk/`、`sse/`、`todo/`、`tasks/` 空目录或未挂载模块 |
| 前端 token 存 localStorage | 配合 ① 的 XSS 可直接窃取；若改成 httpOnly Cookie 需处理 CSRF |

## 八、怎么复现

```bash
# 1. 起一个关闭验证码的测试实例（不要动 3000 的开发实例）
cd E:/project/oneself/concise-server-node
PATH="/d/projram/nodejs:$PATH" PORT=3460 CAPTCHA_ENABLED=false node dist/main.js

# 2. 另开一个终端跑冒烟（默认打 127.0.0.1:3460）
PATH="/d/projram/nodejs:$PATH" node scripts/smoke-test.cjs

# 3. 指定别的目标
SMOKE_BASE=http://127.0.0.1:3000/api node scripts/smoke-test.cjs
```

脚本约定：

- 管理员令牌从 `.env` 的 `JWT_SECRET` 现签，**不需要在脚本里写任何密码**；
- 临时账号密码用 `crypto.randomBytes` 生成，只在内存里存在；
- 所有临时数据带 `smoke_` 前缀 + 时间戳，末尾统一清理并断言无残留；
- 有 FAIL 时进程退出码 1，可直接挂 CI。

> 注意：③ 那个缺陷会让脚本的「清理角色」稳定失败（角色被已删用户卡住），需要在库里手动删一次 `sys_user_role` 才能恢复；这正是需要修的地方，不是脚本 bug。

## 九、没覆盖到的部分（下次补）

- **并发**：没有做并发写同一资源的用例（如两个请求同时改同一用户、并发批量删除），乐观锁/唯一约束下的竞态未验证。
- **长事务 / 大数据量**：导入 2000 行、导出 5 万行的边界没压测（只测了空模板与单行）。
- **Redis 故障降级**：验证码已确认会 503，但在线会话、黑名单在 Redis 挂掉时的降级行为没测。
- **定时任务真实执行**：只验证了「立即执行」接口返回 200，没核对任务是否真跑出了日志（handler 全被占用，无法新建测试任务）。
