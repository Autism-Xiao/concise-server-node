## 二、角色批量删除

**为什么逐条结算**

后端 `DELETE /api/v1/roles/:id` 是单条接口，且内置 `admin` 角色、仍有用户绑定的角色都会被拒。批量场景下如果用一个事务包住，只要有一个不合格就整批回滚，用户还得自己一个个试。所以前端用 `Promise.allSettled` 逐个发，最后统一汇报：

```ts
const results = await deleteRoles(targets.map(role => role.id))
const succeeded = results.filter(r => r.status === 'fulfilled').length
const failed = results.length - succeeded
if (succeeded) toast.success(`已删除 ${succeeded} 个角色`)
if (failed) toast.error(`${failed} 个角色删除失败，请检查角色是否仍被用户使用`)
```

**交互细节**

- 勾选列用 `useDataTable` 的 `rowSelection` + `getRowId: role => role.id`（按业务 id 而不是行索引，避免筛选/排序后错位）
- 表头 checkbox 支持半选态（`indeterminate = getIsSomePageRowsSelected()`）
- 「批量删除（N）」按钮只在 `selectedCount > 0` 且具备 `system:role:delete` 时出现，不会常驻占位
- 确认弹窗打开期间用 `batchBusy` 锁住：`onOpenChange={v => !batchBusy && setBatchDeleting(v)}`，防重复提交
- 删除完成后 `setRowSelection({})` + 重拉列表，避免残留已删行的勾选

## 三、标签页按需挂载

**原行为**：`TabPageRenderer` 把 `tabs` 里的每个标签都渲染成 `<TabPage>`，非活动的用 `display:none` 隐藏（keep-alive）。好处是切回标签保留滚动位置和表单状态，坏处是**刷新页面时被恢复的所有标签会同时挂载并发请求**——几个列表页一起打接口，首屏明显变慢。

**现行为**：维护 `visitedPaths`，初始只放当前路径，访问过才加入：

```ts
const [visitedPaths, setVisitedPaths] = useState<ReadonlySet<string>>(() => new Set([pathname]))
useEffect(() => {
  if (!isRegisteredPage(pathname)) return
  setVisitedPaths(prev => (prev.has(pathname) ? prev : new Set(prev).add(pathname)))
}, [pathname])
const mountedPaths = paths.filter(path => path === pathname || visitedPaths.has(path))
```

- 只有「当前页 + 本轮已访问过的页」挂载，其余标签等首次点进来才挂
- keep-alive 语义不变：一旦挂上就不再卸载（除非点「刷新」触发 nonce 变化）
- 用 `ReadonlySet` + 返回原引用（无变化时不新建 Set）避免多余重渲染

## 五、注意

- 批量删除没有走后端批量接口，N 个角色就是 N 次请求。角色数量级小（几十个）可以接受；如果以后要一次删上百个，建议后端补 `DELETE /api/v1/roles` + `{ids}`，前端换成单请求
- 被拒的角色（内置 `admin`、仍绑定用户）只会体现在「N 个删除失败」的提示里，不指明具体是哪个；需要精确提示时可以在 `errors` 里带上 id → 名称的映射
- 标签页按需挂载后，未访问的标签在刷新后需要**重新进入一次**才恢复原状态（原本就没挂载过，属于预期行为）
