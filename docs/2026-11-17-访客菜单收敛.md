# 访客菜单收敛：组织架构 / 字典 / 文件库 + 空目录清理

> 2026-11-17 · 承接前两轮「租户访客用户权限收紧」「租户角色权限收敛」

## 结论

把 `viewer`（访客）从「除管理页外几乎全能看」收敛成「**只读业务数据 + 个人工作台**」：

| | 收敛前 | 收敛后 |
|---|---|---|
| 租户 1 访客授权 | 21 条 | **10 条** |
| 侧边栏分组 | 仪表盘 / 系统管理 / 数据管理 / 协同办公 / 安全审计（空） | **仪表盘 / 协同办公** |
| 可见页面 | 13 个 | **7 个** |
| editor | 55 条 | 55 条（**不动**） |
| admin | 97~98 条 | 97~98 条（**不动**） |

## 为什么收这几个模块

前两轮收的是管理类页面（用户/菜单/角色）。这一轮收的是**配置数据**和**全租户文件库** —— 它们不是管理页，但同样不该给只读访客：

| 模块 | 拿到的权限 | 问题 |
|---|---|---|
| 部门 / 岗位 / 职级 | `:list` | 组织架构属配置数据，管理职责 |
| 数据字典 | `:list` `:export` | 配置入口，且能整表导出 |
| 行政区划 | `:list` | 公共数据，访客无实际用途，白占侧边栏 |
| **文件管理** | `:list` + **`:download`** | 🔴 `system:file:list` 能列出该租户**所有人上传的附件**，`:download` 能下载任意一个，而文件没有按人隔离 —— 这是访客权限里唯一能拿到具体文件内容的洞 |

根因还是同一个：`acceptsByLevel` 对这些模块**只能按权限码后缀判断**，后缀 `list`/`export`/`download` 在白名单里，所以「页面挂一个 `:list` 按钮 → 整页自动给访客」。

## `levels` 字段为什么必须存在

第一版想直接把这 6 个模块塞进黑名单，但 `TENANT_RESTRICTED_MODULES` 对 `read` 和 `write` 两档同时生效 —— 会把 `editor` 打瘸：

- 编辑者要**维护基础数据**（改部门名、加岗位、维护字典项），收掉就没有维护入口
- 编辑者要**上传/下载任务附件**，收掉文件管理就没法交作业

所以引入 `levels`：管理类三件套（用户/菜单/角色）不写 `levels`（读写两档都排），业务基础设施六件套只写 `levels: ['read']`。

## 空目录是怎么产生的、怎么修的

「安全审计」不是孤立目录 —— 它下面有 6 个租户级子页面（登录日志 `/system/log/login`、操作日志、变更审计…），只是访客一个都没拿到（日志页面的权限码不是 `:list` 后缀），于是目录变空。

而目录节点本身**没有权限码**，`acceptsByLevel` 一律放行，所以它一直留在访客的授权表里。前端 `treeToGroups` 把无子项的分组当普通菜单项渲染 → 侧边栏出现「安全审计」，点进去 `/audit` 是 404（前端根本没这个路由）。

`pruneEmptyDirs()` 的判定规则：**有子节点、但过滤后一个子节点都不剩** → 剔除。

不能用 `menu_type` 判：仪表盘是 `menu_type=0` 的顶级**单页**菜单，按类型判会被当空目录误删；按「有子节点但全丢」判则绝不会碰它（它压根没有子节点）。

多层目录要自底向上迭代：A 装 B，B 的子页面全丢后 B 该删，B 删了 A 才变空。函数用 `while (changed)` 迭代到稳定；迁移里跑 3 轮。

## 实测（3461 测试实例，临时访客账号，已删除）

```
侧边栏：仪表盘 | 协同办公(通知公告、日历管理、消息中心、供应商管理、任务管理、订单管理、客户管理)
权限码：6 个（notice/message/supplier/task/biz_order/customer :list）

保留 → 200：/dashboard/overview  /notices  /tasks  /messages  /suppliers  /customers
收回 → 403：/depts  /posts  /levels  /dicts  /regions  /files  /users
不受影响 → 200：/users/me  /users/lookup  /depts/tree  /dict-items/code/sys_task_priority
```

后两条最关键 —— 证明「收回」没有误伤基础能力：

- **选人控件**走 `/users/lookup`（不挂 `@Perms`），仍 200
- **选部门控件**走 `/depts/tree`（不挂 `@Perms`），仍 200
- **所有表单下拉**走 `/dict-items/code/:code`（不挂 `@Perms`），仍 200

## 踩的坑

1. **MySQL 1093**：`DELETE ... JOIN sys_role_permission` 的子查询里再 `JOIN sys_role_permission` 会报「can't specify target table」。改成先 `SELECT` 出待删的 `(roleId, permissionId)`，再逐条 `DELETE`（每角色每目录几条，量很小）。
2. **TypeORM 1.1 的 `queryRunner.query` 不接受泛型**，返回 `any`，必须 `as Array<{...}>` + `Array.isArray` 兜底。
3. **`grant()` 只补差集不删**：改模板对存量租户完全无效，收回必须写迁移。这是第二次踩，已在两份文档里重复标注。
4. **`concise` 账号密码实测不是 123456**（可能被改过）。为了不锁号，用 admin 建临时账号验证，测完 `DELETE /users/:id` + 手工清 `sys_user_tenant`（软删会留 `del_flag=1` 行）。

## 怎么扩展

**再收一个模块**：在 `TENANT_RESTRICTED_MODULES` 加一行，按需写 `levels`。新建租户自动生效，存量要补迁移（照抄 1794890000000 的 `VIEWER_MODULES` 数组）。

**反过来放宽**（比如让编辑者也能看文件管理）：把该模块的 `levels` 改成 `['read']` 以外 —— 注意 `write` 档本就不该被排除的业务模块，干脆别进这个数组。

**给访客加回某个页面**：不要改模板（会波及所有租户），用角色页手工给该租户的 `viewer` 勾单个节点；或者直接建一个自定义角色。

**彻底改「访客」的产品定位**：改 `TENANT_ROLE_TEMPLATES` 里 `viewer` 的 `level`（现在是 `read`）。若改成更严格的自定义档，`TenantRoleLevel` 联合类型与 `acceptsByLevel` 都要跟着扩展。
