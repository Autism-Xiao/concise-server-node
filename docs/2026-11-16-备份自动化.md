# 备份自动化：定时导出 + 导入校验 + 保留策略 + 一键恢复

> 2026-11-16 · 底座补全三期 · 兜住「备份靠人手跑」这个洞

## 为什么做

当天上午刚发生过一次：手工 `mysqldump` → 手工 `DROP` → 手工导入 → 手工建临时库验证 → 手工删临时库。这套流程既容易漏步骤，也没人保证每天都跑。**没验证过的备份等于没有备份**，所以这次做成流程。

## 流程细节

1. **导出**：`mysqldump --single-transaction --quick --result-file=...`，文件名精确到毫秒（`..._130750_123.sql`）。失败会删掉半截文件，避免「看起来有备份但打不开」。
2. **校验**：建 `concise_verify_<ts>` 临时库 → 真导入 → 比对源库表数 → 删库。表数不一致直接抛错，不让坏备份留在目录里。
3. **保留**：只留最近 N 份（默认 7，可在参数配置里改），当前这份永远保留。
4. **调度**：`sys_quartz_job` 里一行 `backupDbJob` / `0 0 2 * * *`，复用原有 cron + Redis 分布式锁（多实例只有一个在跑）。
5. **恢复**：`node scripts/restore-sql.mjs <file> [--yes]`，交互式要求输入 `YES` 才动手。

## 踩的坑

- **`DataSourceOptions` 是联合类型**：直接 `this.db.username` 报 `Property 'username' does not exist on AuroraPostgresDataSourceOptions`。要定义 `MySqlConn` 接口再 `as unknown as` 收窄。
- **文件名只到秒会互相覆盖**：同一秒内两次备份，`--result-file` 会覆盖前一个文件，保留策略就变成了「留 2 份但其实是 1 份」。补毫秒解决。
- **pnpm 布局下 `require('node:fs')` 写在函数里**也能用，但风格上应提到顶部；顺手改成 `import { createReadStream }`。

## 如何扩展

- 改时间：改 `sys_quartz_job.cron_expression`（页面「定时任务」里就能改，无需发版）
- 改保留份数：参数配置里 `ops.backup.keepCount`
- 关掉校验（磁盘紧张、库很大时）：`ops.backup.verify = false`
- 异地备份：`DbBackupService.dump()` 之后接一段上传逻辑（OSS/S3），storage-provider 已有抽象可复用
