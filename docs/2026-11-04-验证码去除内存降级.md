# 2026-11-04 验证码去除内存降级，改为 Redis 单一模式

## 改了哪些文件

| 文件 | 类型 | 说明 |
| --- | --- | --- |
| `src/modules/auth/services/captcha.service.ts` | 重写 | 删除内存 Map 降级逻辑，只走 Redis；未启用 Redis 时统一抛 `BusinessException`（HTTP 200 + code 503） |

## 为什么去掉内存降级

内存降级在多实例部署下是假安全：A 实例生成的验证码落在 A 的内存里，用户下一次请求被负载到 B 实例时必然校验失败，行为不可预期且难排查。与其保留「单实例才能用的隐式模式」，不如显式失败——Redis 不可用时直接报「验证码服务不可用」，提示运维去检查 `REDIS_ENABLED`/Redis 连接。

## 现在的行为

| 场景 | 行为 |
| --- | --- |
| `REDIS_ENABLED=true` 且 Redis 正常 | 验证码写 `captcha:{id}`（EX 300），MULTI 内 GET+DEL 原子一次性校验，多实例共享 |
| `REDIS_ENABLED=false` | `GET /api/auth/captcha` 与登录校验均返回 `{ code: 503, message: "验证码服务不可用，请检查 Redis 配置（REDIS_ENABLED）" }` |
| Redis 中途故障 | SET/MULTI 抛出的错误由全局异常过滤器兜底返回 500，不做静默降级 |

## 怎么使用/扩展

- 上线前确认 `.env` 中 `REDIS_ENABLED=true`，否则登录功能整体不可用（这是预期行为，fail-loud）。
- 若想统一把「Redis 不可用」的提示收敛到一处，可在 `RedisService` 加 `requireClient()` 方法供后续使用 Redis 的模块复用。
