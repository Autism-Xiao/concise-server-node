# 缓存监控：key 前缀分组修复

> 日期：2026-11-04
> 关联接口：`GET /api/v1/monitor/cache`

## 一、改动文件

| 文件 | 类型 | 说明 |
|---|---|---|
| `src/modules/ops/monitor/monitor.service.ts` | 修改 | 新增 `prefixOf(key)` 做前缀归属判断，替换 `groupKeys()` 里原来的一级前缀截断；补充方法注释 |
| `docs/README.md` | 修改 | 追加本轮变更索引 |

## 二、问题现象

调用 `GET /api/v1/monitor/cache` 时，`keys` 分组返回：

```json
{ "name": "online:", "count": 3, "ttl": "最长 2 小时", "description": "业务缓存" }
```

三个问题：

1. **分组过粗**：`online:session:`（在线会话）和 `online:revoked:`（强制下线黑名单）被合并成一行 `online:`，看不出各自数量
2. **描述永远匹配不上**：`PREFIX_DESCRIPTIONS` 配的键是 `online:session:` / `online:revoked:` / `captcha:`，而分组名是 `online:`，`PREFIX_DESCRIPTIONS[prefix]` 永远 undefined，全部落到兜底的「业务缓存」
3. **`captcha:` 前缀被切断**：原实现 `key.split(':')[0]` 对 `captcha:abc123` 得到 `captcha:` 没问题，但一旦 key 只有一段（无冒号之外的业务段）就会退化成整 key

## 三、修复方案

原实现：

```ts
const prefix = key.includes(':') ? `${key.split(':')[0]}:` : key
```

改为「已知业务前缀最长匹配 + 一级前缀兜底」：

```ts
private prefixOf(key: string): string {
  const known = Object.keys(PREFIX_DESCRIPTIONS).find(prefix => key.startsWith(prefix))
  if (known) return known
  return key.includes(':') ? `${key.split(':')[0]}:` : key
}
```

为什么不用「取前两段（`a:b:`）」：

- `online:session:<token>` 按冒号切是 `['online','session','<token>']`，前两段拼成 `online:session:` —— 正确
- 但 `captcha:<codeId>` 只有两段，前两段拼成 `captcha:<codeId>:` —— 错误，每个验证码会自成一类

所以必须按「已知前缀」匹配，而不是按段数切。已知前缀集合直接用 `PREFIX_DESCRIPTIONS` 的键（`online:session:` / `online:revoked:` / `captcha:` / `job:`），新增业务前缀时只要往这个映射里加一行即可，分组和描述同时生效。

## 四、验证结果

往 Redis 造 5 个不同前缀的 key 后调用服务：

```
online:session:aaa  (600s)
online:session:bbb  (900s)
online:revoked:ccc  (3600s)
captcha:ddd         (300s)
foo:bar:eee         (60s)
```

返回：

```json
{
  "mode": "Redis 3.0.504",
  "keyCount": 6,
  "memoryUsed": "738.13K",
  "hitRate": 59.8,
  "keys": [
    { "name": "online:session:", "count": 3, "ttl": "最长 1 小时", "description": "在线会话（登录令牌）" },
    { "name": "foo:",            "count": 1, "ttl": "最长 1 分钟", "description": "业务缓存" },
    { "name": "captcha:",        "count": 1, "ttl": "最长 5 分钟", "description": "图形验证码" },
    { "name": "online:revoked:", "count": 1, "ttl": "最长 1 小时", "description": "强制下线令牌黑名单" }
  ]
}
```

- 已知前缀正确拆分并命中中文描述
- 未知前缀 `foo:bar:eee` 退化为 `foo:` 并标「业务缓存」
- `count` 按数量倒序

## 五、注意

- `ttl` 是**抽样估算**：每个前缀最多抽 20 个 key 取最大 TTL（`pipeline.ttl`），不是全量遍历，避免大 key 空间拖慢接口
- `count` 也做了上限保护：单前缀最多统计 5000 个 key
- 分组统计走 `SCAN`（游标 200/批），不会像 `KEYS *` 那样阻塞 Redis
- 本机是 Redis 3.0.504：不支持多字段 `HSET`、`MEMORY USAGE`，所以 TTL 只能 pipeline 逐 key 取

## 六、扩展方式

新增一类业务缓存前缀（例如以后接文件上传的临时分片缓存）：

1. 在 `PREFIX_DESCRIPTIONS` 里加 `'upload:chunk:': '上传分片临时数据'`
2. 如果是需要被「清理缓存（不传 prefix）」一并清掉的，再加到 `APP_PREFIXES` 数组
3. 不用改 `prefixOf`，分组与描述自动生效
