# 导入导出 / 批量删除 —— 页面需求分析

> 分析时间：2026-11-05
> 范围：`concise-server-node`（后端 v1 接口）+ `concise-admin`（前端页面）
> 目的：按「真实使用场景 + 改造成本 + 风险」给各页面排优先级，避免为了凑功能而加按钮。

## 一、判断标准

一个页面要不要做，先过这四个问题，全否就不做：

| 维度 | 判定问题 | 命中才做 |
| --- | --- | --- |
| 导入 | 这批数据是不是「新项目起步 / 换环境」时需要一次性灌进去的配置类数据？ | 是 → 导入 |
| 导出 | 这批数据是否需要留档、交给外部（审计/甲方/运维交接）或跨环境比对？ | 是 → 导出 |
| 批量删除 | 数据是否由用户持续产生、会过期、清不动就是垃圾？ | 是 → 批量删除 |
| 风险闸门 | 是否树形父子引用、是否被其他表强关联、是否有内置数据不可删？ | 命中越多，越倾向「只导出不删除」或「必须后端真接口」 |

反面清单（明确不做的类型）：
- 只读的运维观测页（服务器监控、缓存详情）——没有"数据"可导可删。
- 仍在用 mock 的页面（租户、区域、日历、文件、任务看板）——先接后端，再谈导入导出。
- 强结构化配置（菜单树）——导入的维护成本远高于收益。

## 三、分级建议

### P0 本期做（收益明确、改动可控）

**1. 字典管理 + 字典项 —— 导入导出 + 批量删除**

- 导入导出：最有价值的一个。新项目起步要灌几十上百条字典（性别、状态、类型…），现在只能一条条点；交付/迁移时也要整包带走。
- 建议形态：一个工作簿两个工作表——`字典类型` + `字典项`，字典项用 `dictCode` 关联，避免导出两份文件再人工对齐。
- 批量删除：字典项才是真正会膨胀的数据；删字典类型必须连带校验「下面是空」。批量删字典类型 → 建议只允许删无项的，有项的返回失败原因而不是级联删。
- 难点：`dictCode` / 同类型下 `value` 都是唯一键，软删记录仍占索引（用户导入已踩过），导入预检必须查全表而不带 `del_flag = 0`。

**2. 岗位管理 —— 导入导出 + 批量删除**

- 组织初始化时岗位是成套的（部门 × 职级），导入是刚需；导出用于花名册/编制核对。
- 删除风险低：只有 `deptId` 弱引用，无中间表。
- 注意：`postCode` 唯一 + 部门必须存在的行级校验。

**3. 层级管理 —— 导入导出 + 批量删除**

- 字段最少、无任何关联，是「验证统一导入框架」成本最低的试验田。
- 建议先做这个，把导入模板 + 错误收集 + 批量删除的公共件跑通，再复制到字典/岗位。

### P1 第二批（价值高但要先补设计）

**4. 部门管理 —— 导出必做；导入可选；批量删除慎做**

- 导出：带「完整路径」（研发部/前端组）和负责人，用于组织架构留档，成本低。
- 导入：能做，但必须按「先父后子」排序，父级不存在要报行级错误；`orgCode` 与用户表有同步逻辑（`UPDATE sys_user ... org_code`），导入后要触发同步，改动面比字典大。
- 批量删除：树形 + 有子部门/用户保护，批量只会得到一堆失败。建议退一步做「按选中节点批量删叶子节点」，且必须后端真接口逐条校验 + 返回失败清单，不要让前端并发单删。

**5. 菜单管理 —— 只做导出，不做导入、不做批量删除**

- 导出：权限快照，换环境/交接时能对着看，也能做「环境差异比对」。
- 不做导入：`parentId` 是自增 ID，跨库对不上；权限码与角色关联、与后端 `@Perms` 硬编码强耦合，导错一次就是整站权限错乱。
- 不做批量删除：有子菜单保护，批量删必然大面积失败，收益接近零。

**6. 通知公告 —— 补导出；批量删除改后端真接口**

- 导出：已发布公告需要留档/呈报，之前删掉导出接口属于砍过头。
- 批量删除现状是前端 `Promise.all` 打 N 次单删，跨页勾选时「部分成功」提示很难说清，也刷 N 条操作日志。应改为后端一次事务内校验状态（已发布需先撤销）+ 批量软删，返回 `{success, failed:[{id,title,reason}]}`。

**7. 在线用户 —— 批量强退**

- 运维场景刚需（清僵尸会话、封禁异常账号），后端只要把 `DELETE :sessionId` 扩成接收 `ids`。
- 成本极低，但不属于「导入导出」，单独归到批量操作。

**8. 作业调度 —— 导出配置；批量启停优先于批量删**

- 导出：任务配置备份、跨环境迁移对照，价值中等。
- 不做导入：`handler` 是后端代码里注册的字符串，导入了也跑不起来。
- 批量操作优先做「批量暂停 / 恢复」，比批量删更贴合实际使用。

### P2 观察（暂不动）

- 登录/操作日志：导出与真批量删除已完备，且导出已透传筛选条件，不动。
- 文件管理 / 任务看板：仍走 `/mock`，等接真实后端时顺手补批量删（`tools/storage` 后端接口已具备）。
- 用户/角色：能力已完整。真要优化，方向是「导入失败行回写成 Excel」而不是再加新按钮。

### 明确不做

- 租户、区域、日历：纯 mock，无后端实体。
- 服务器监控、缓存详情：只读观测。
- 字典项之外的所有「一行一个配置」的小表如果只有 <20 条，导入收益都不如手填。

## 四、横切建议（比逐个页面更重要）

1. **批量删除统一成后端接口**
   现状：用户/角色/公告/部门都是前端 `Promise.all` 并发单删，问题有四——N 次 SQL、N 条操作日志、无事务（删一半失败留下脏状态）、失败提示靠前端拼接。
   建议统一为 `POST /v1/{resource}/batch-delete`，body `{ ids: string[] }`，返回 `{ deleted: number, failed: [{ id, name, reason }] }`，单次上限 200 条。前端只需要一个「部分成功」结果面板。

2. **软删 + 唯一索引的组合必须显式处理**
   `dict_code` / `post_code` / `role_code` / `username` 都是唯一键，软删记录仍占索引。批量删完再导入同编码会直接失败。二选一：删除时把唯一字段改写为 `code__deleted_{timestamp}`，或这些表改用硬删 + 关联表清理。

3. **导入做成一个公共件**
   已有 `buildImportTemplateXlsx` + 用户模块的 `result.errors` 模式，把「读表 → 表头定位（剔除 `*`/全角）→ 行级校验 → 部分成功汇总」抽成 helper，后续字典/岗位/层级只写各自的字段映射，不重复造轮子。

4. **导出统一走 `buildXlsx` 且必须透传列表筛选**
   角色/日志已这么做。新加的导出别写成「全量导出」，否则用户筛了条件点导出得到的数据对不上，是高频投诉点。

5. **权限点同步**
   每个新接口配 `@Perms('system:xxx:import' | 'export' | 'delete')`，并在菜单表的按钮权限里补行（参照 menu_75/76/78 的 seed 方式），否则前端按钮不显示。

## 五、实施顺序

1. 层级（试验田，跑通公共件）
2. 字典类型 + 字典项（收益最大）
3. 岗位
4. 批量删除后端接口统一改造：公告 → 部门 → 用户/角色（顺手把前端并发单删收掉）
5. 部门导出、菜单导出
6. 在线用户批量强退、作业调度导出

前 3 步是「加功能」，第 4 步是「还债」，建议不要跳过第 4 步直接铺量——否则每加一个页面就多一处前端并发单删。
