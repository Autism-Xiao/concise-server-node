# CI 流水线：构建 + Lint + 单测 + 接口冒烟

> 日期：2026-11-16 ｜ 范围：`.github/workflows/ci.yml`、`tests/`、`package.json`
> 关键词：GitHub Actions、MySQL service、快照还原、node:test、健康探针

## 一、为什么做

之前所有验证都靠"本机手动跑一遍"：`nest build` → 起 3459 → 挨个跑 15 个冒烟脚本。问题在于：

1. **没人保证每次提交都跑过**。改一个 `PermissionCacheService`，可能只有 tenant 冒烟会炸，而那天你恰好只跑了 dashboard。
2. **本机环境是唯一副本**。`dist` 是手动 build 的，谁都能在没 build 过的状态下提交（代码和产物不一致，线上 `node dist/main.js` 跑的是旧逻辑）。
3. **没有单元测试入口**。`npm test` 指向 jest，但 jest 30 在 Node 22 上加载 NestJS 12 的 ESM 包会直接崩（见下），等于没有测试。

CI 解决的是这三件事：**编译能不能过、lint 有没有脏点、接口还能不能跑通**。

## 二、文件清单

| 文件 | 类型 | 说明 |
| --- | --- | --- |
| `.github/workflows/ci.yml` | 新增 | 两个 job：`quality`（构建 + ESLint + 单测 + 非阻断检查）、`smoke`（MySQL 8.4 + Redis 7 服务容器 → 导入快照 → 跑迁移 → 起服务 → 跑 3 个冒烟脚本） |
| `tests/password-policy.test.cjs` | 新增 | 首批单测，10 个用例覆盖密码策略的长度 / 字符种类 / 空白 / 弱模式 / 含用户名 |
| `package.json` | 修改 | `test` 从 jest 改为 `node --test tests/*.test.cjs` |

## 三、每个 job 在干什么

### 3.1 `quality`：编译 + 静态检查（约 2 分钟）

1. `pnpm install --frozen-lockfile` —— 只认 lockfile。lockfile 和 `package.json` 不一致时**直接失败**，防止本地手改版本悄悄进主干。
2. `pnpm run build` —— `nest build` 产 `dist`。这一步同时兜住了"类型错误但没 build 就提交"。
3. `pnpm run lint` —— ESLint（项目是一套 flat config，含 `src/**/*.ts` 与 `test/**/*.ts`）。
4. `pnpm test` —— 单测。**必须排在 build 之后**，因为 `node --test` require 的是 `dist/*.js`，不是 `src/*.ts`（原因见 3.3）。
5. `lint:ox`、`format:check` —— `continue-on-error: true`，只报警不拦合并。oxlint 的 type-aware 规则集还在演进，Prettier 也还没全库对齐，这时候拿它们卡合并只会逼人 `--no-verify`。

### 3.2 `smoke`：接口冒烟（约 4 分钟）

按顺序做五件事，任何一步失败都会打印服务端日志：

1. **拉服务容器**：`mysql:8.4`（`MYSQL_ROOT_PASSWORD=root`、预建 `concise_server`）+ `redis:7-alpine`，都带 healthcheck。
2. **导入快照**：`docker run --rm --network host -i mysql:8.4 mysql ... < sql/concise_server_full_2026-11-15.sql`。借容器里的客户端导入，省一次 `apt-get install`（runner 上 docker 一定有，mysql-client 不一定）。导完数表，**少于 30 张直接失败**——表没导全的话后面所有冒烟都会红，早点拦住更省时间。
3. **现场生成 `.env`**：本机 `.env` 不入库，CI 现写一份（密钥是 CI 专用值，见文件里的注释）。
4. **跑迁移**：`pnpm exec typeorm migration:run -d dist/shared/database/data-source.js`。快照停在 55 号迁移，之后新增的 `sys_config`、`sys_user_backup_code` 必须在这里补建，否则 CI 等于在跑一个缺表的库。
5. **起服务 + 探针**：`node dist/main.js` 后台起在 3461，轮询 `GET /api/v1/health`（`@Public`，返回 `{status,db,redis}`），120 秒内没就绪就 `tail server.log` 并失败。
6. **跑冒烟**：`smoke-dashboard`（60 断言）、`smoke-user-setting`（18）、`smoke-batch-io`（31）。三个脚本默认 BASE 就是 `127.0.0.1:3461`，不用额外传环境变量。

## 四、坑（都踩过）

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| jest 跑不了 Nest 12 | `Must use import to load ES Module: .../@nestjs/common/index.js` | NestJS 12 的包是纯 ESM；jest 30 的 runtime 即使 Node 支持 `require(esm)` 也自己先抛错。改用 `node:test`，断言用 `node:assert/strict` |
| 单测 require 的是 `dist` 不是 `src` | 写完测试直接跑，报 `Cannot find module '../dist/...'` 或跑的是旧逻辑 | 约定：`tests/*.test.cjs` 只 require `dist`，所以 **先 build 再 test**。好处是不需要 ts-node/ts-jest 那套加载器 |
| 快照不含新表 | 快照只到 55 号迁移，`sys_config` 等表不在里面 | 导入后必须补跑迁移（第 4 步）。只导入不迁移 = 冒烟一碰配置中心就 500 |
| mysqldump 没带 `--databases` | 快照里没有 `CREATE DATABASE` / `USE`，直接 `mysql < file` 会报 "No database selected" | 导入命令后面显式给库名 `mysql ... concise_server < snapshot.sql` |
| 冒烟脚本 BASE 约定不统一 | `smoke-dashboard` 默认 `.../api`，其余默认 `.../api/v1`；`smoke-batch-io` 用 `BASE_URL` 而不是 `SMOKE_BASE` | CI 里不传 BASE，全靠各自默认值（都指向 3461），避免踩这个不一致 |
| CI 密钥写死 | workflow 里有 `JWT_SECRET` / `DB_PASSWORD` | 都是**一次性实例**的假值，文件里已注明"不要照抄到任何真实环境"。真要接生产用 `secrets.*` |
| 后台起服务后忘记收尾 | 进程留着占端口 | 最后一步 `if: always()` 里 `kill $(cat server.pid)` |

## 五、顺带发现的两个问题

1. **`isSequential` 实际不生效**。它现在的实现是把**整串**拿到 `0123456789 / a-z / qwertyuiop / asdfghjkl / zxcvbnm` 里找连续片段，也就是只有"密码整体就是一段序列"（比如纯小写 `qwertyui`）才会命中；而那种密码在复杂度规则那关（要求至少三类字符）就已经被拒了。所以它等于死规则：`Abcde123!`、`Abcd1234!` 这类都能过。
   - 没有在这轮改它的原因：真正的"连续 4~5 位"检查会拒掉大量测试夹具（`Smoke1234!` 之类），需要连带复核 6 个冒烟脚本，属于独立改动。
   - 当前防线靠 `WEAK_PASSWORDS`（`Password1`、`abcd1234` 这类在名单里）+ 字符种类 + 重复字符占比。
2. **单测覆盖面很小**。目前只有密码策略一个文件。`totp.service` 的备份码生成/摘要/一次性消费、`tenant-scope.util` 的三种 scope 分支、`db-error.util` 的 `ER_DUP_ENTRY` 映射，都是纯逻辑且最容易写错，值得下一轮补。

## 六、怎么扩展

- **加一个冒烟脚本到 CI**：在 `smoke` job 末尾加一个 `- name: 冒烟 · xxx` + `run: node scripts/smoke-xxx.mjs`。脚本必须满足：BASE 默认指向 3461、自己准备和清理测试数据、失败时 `process.exit(1)`。
- **加服务依赖**（比如要 Elasticsearch）：在 `smoke.services` 下加一个容器，`ports` 映射到 127.0.0.1，`options` 里写 healthcheck；job 会把服务容器映射到 runner 的 localhost。
- **想让冒烟覆盖验证码**：`smoke-captcha` 要求 `CAPTCHA_ENABLED=true`，和现有 3 个脚本冲突。做法是再加一个 job（或同 job 内重启一次实例），单独设该环境变量。
- **跑得更快**：`quality` 与 `smoke` 目前是串行（`needs: quality`），因为 `smoke` 要复用 build 产物；如果装了 `actions/cache` 存 `dist`，可以去掉 `needs` 并行。
- **私有仓库**：GitHub Actions 免费额度对私有仓库按分钟计费，本项目两个 job 合计约 6 分钟/次；只想在 PR 上跑就把 `on.push` 去掉，只留 `pull_request`。

## 七、验证方式

本机无法跑 GitHub Actions，所以用"等价步骤"逐项验过：

| CI 步骤 | 本机等价验证 | 结果 |
| --- | --- | --- |
| `pnpm run build` | `npx nest build` | 通过 |
| `pnpm run lint` | `npx eslint "src/**/*.ts" "test/**/*.ts"` | 退出码 0 |
| `pnpm test` | `npm test`（`node --test tests/*.test.cjs`） | 10/10 通过 |
| 迁移 | `npx typeorm migration:run -d dist/...` | `No migrations are pending` |
| 起服务 + 探针 | `PORT=3461 node dist/main.js` → `curl /api/v1/health` | `{"status":"ok","db":true,"redis":"ok"}` |
| 三个冒烟 | 依次跑 | 60/60、18/18、31/31 |

首次真实运行仍需推上去看一次（pnpm 在 Linux 上装 `@node-rs/argon2` 的平台包、`--frozen-lockfile` 行为这两点本机测不了）。
