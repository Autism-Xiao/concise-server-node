## 一、在线用户租户隔离（修复前：租户管理员可看/踢全平台会话）

`online.service.list` 原来直接 SCAN 全部 Redis 会话返回，无租户条件；`kick` 也没有归属校验——只要租户管理员有该菜单权限，就能看到并强制下线全平台任意用户（包括平台超管）。

修法：

- **会话登记打标**：`OnlineSession` 新增 `tenantId` 字段，`touch()` 时记录当次请求的 `TenantContext.filterTenantId() ?? 0`（JwtStrategy 在中间件上下文内执行，拿到的就是本次请求的租户视角）。
- **列表过滤**：租户视角（filterTenantId > 0）只显示 `session.tenantId` **精确等于**当前租户的会话——注意**不含 0**：0 是平台视角的会话，属于平台数据而非共享数据；平台视角（null）看全部。
- **踢人校验**：`kick()` 加载会话后校验归属，跨租户按 404 处理（不泄漏会话是否存在）。`batchKick` 逐条走 `kick`，自动覆盖。
- **旧会话兼容**：本字段上线前的 Redis 会话没有 `tenantId`，视同 0（accessToken 2 小时自然过期，无需迁移）。

## 二、通知公告租户边界（修复前：知道 id 就能改/删任何公告）

四个入口统一收紧：

1. **`findOneActive` 补 `applyTenantScope`**——它是 update/publish/revoke/delete 的前置校验，也是详情接口；不带租户条件就是 IDOR。
2. **`batchDelete` 目标集合收窄**——批量删除先按租户范围筛目标，不可见的 id 按「不存在」计入失败。
3. **`patchById` 挂 `tenantWriteCondition`**——读范围含共享行（平台公告租户要能看）是正确语义，但**写**必须严格只命中本租户行；租户改/删平台共享公告（tenant_id=0）在 UPDATE 的 WHERE 上被挡掉，命中不了按 404 报（`affected=0` 判定，mysql2 FOUND_ROWS 语义下相同值更新 affected 也是 1，判定可靠）。
4. **导入收窄**——公告按 id/标题匹配更新只能命中本租户可见的公告；「指定用户」解析加 EXISTS 收窄到本租户有归属的账号（与 user.service 的 `applyTenantToUsers` 同口径），防止借导入把公告挂到其他租户用户头上。

## 三、连带发现并修复：租户列默认值 = 1 的历史遗留（重要）

冒烟时发现「平台视角创建的公告被租户改成功了」——根因不在公告代码，而是 **`sys_announcement.tenant_id` 列默认值是 1**（单租户时代「默认租户」遗留），而 `stampTenant` 在平台视角（tenantId=null）**不打标**，落库走列默认值 → 超管创建的公告被错归租户 1，其他租户看不见。全库排查后 9 张表都有此问题（biz_order/customer/supplier/sys_announcement/sys_file/sys_log/sys_message/sys_watermark_setting/task）。

修三层：

1. **`stampTenant` 平台视角显式打 `SHARED_TENANT_ID`(0)**——平台视角创建 = 共享数据，不再依赖列默认值（防御纵深）。
2. **迁移把 9 张表列默认值统一改 0**（`ALTER TABLE ... ALTER COLUMN tenant_id SET DEFAULT 0`，不动数据）。
3. **存量修正只做公告表**：`UPDATE sys_announcement SET tenant_id=0 WHERE tenant_id=1 AND create_by='admin'`——公告语义就是「发给全平台」，错归影响所有租户可见性；customer/task/message 里 tenant_id=1 的历史行**无法区分**「平台视角意外落库」还是「超管切租户视角创建」，保持现状，发现再逐行人工判定。

## 五、踩的坑与扩展要点

- **「读可见 ≠ 可写」**：租户范围含 tenant_id=0 共享行是读语义；写路径必须用 `tenantWriteCondition`（严格本租户），否则租户能改平台数据。公告因为「共享公告要给租户看」天然踩这个坑。
- **列默认值是有语义的**：stampTenant 不打标时列默认值兜底，历史遗留的 default=1 会静默错归数据。新增带 tenant_id 的表必须 `default: 0`。
- **在线会话不是共享数据**：列表过滤用精确等于（不含 0），与业务表的「本租户 ∪ 共享」口径不同。
- **旧 Redis 会话兼容**：新字段缺失视同 0，靠 TTL 自然淘汰，不做迁移。
- 扩展：后续做「套餐/配额」「代维审计标记」时，在线用户模块的会话结构已带 tenantId，可直接复用做租户级在线统计。
