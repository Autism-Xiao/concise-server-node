# 超管角色授权收口：统一判定 + 禁止写入 + UI 提示

日期：2026-11-05

## 问题（用户反馈）

给 `admin` 角色分配权限时，即使一个都不勾，权限依然全部生效。

## 根因

不是权限校验漏了，而是**超管硬编码绕过 + 授权入口没关门**：

| 位置 | 改造前 | 后果 |
| --- | --- | --- |
| `auth.service.getPermissions` | `SUPER_ROLES = ['admin','superadmin']` → 直接返回 `['*']` + 全量菜单树 | 菜单/按钮完全不读 `sys_role_permission` |
| `common/guards/perms.guard.ts` | `roleCode === 'admin'` → `return true` | `@Perms()` 接口全放行 |
| `common/guards/roles.guard.ts` | 无超管判定，只按 `@Roles()` 名单匹配 | 三处判定标准各不相同 |
| 前端 `lib/permissions.ts` | `permissions.includes('*')` → 不做路径过滤 | 侧边栏全开 |

实测（`dist` 运行、真实库）：admin 角色在 `sys_role_permission` 只绑了 **2 条**，但接口返回 `['*']` + 全部 69 个菜单；普通角色 viewer 绑 1 条就只返回 1 个菜单。也就是说授权弹窗对 admin 的勾选**从未生效过**，保存还提示"已更新"。

三个具体缺陷：
1. **交互误导**：授权弹窗对超管开放、可保存，结果零效果 —— 用户以为收权成功。
2. **展示失真**：角色列表"已授权"列对 admin 显示 `2 项`，实际全权。
3. **判定三套标准**：`SUPER_ROLES` 认 admin/superadmin，`PermsGuard` 只认 admin，`RolesGuard` 一个不认。真建 `superadmin` 角色会出现「前端全开、后端 403」。

## 方案（保留超管不可被锁死，但把规则做实）

选的是"统一判定 + 拒绝写入 + UI 提示"，而不是"取消硬编码、完全 DB 化"：
后者需要迁移全部菜单绑定并实现防自锁，一旦误删绑定就把管理员锁在门外，风险和收益不成正比。

### 改动文件

| 文件 | 类型 | 说明 |
| --- | --- | --- |
| `src/utils/super-role.util.ts` | 新增 | `SUPER_ROLE_CODES = ['admin','superadmin']`、`isSuperRole(code)`、`hasSuperRole(roles)`，全项目唯一判定 |
| `src/modules/auth/services/auth.service.ts` | 修改 | 删掉本地 `SUPER_ROLES`，改 `hasSuperRole(user.roles)` |
| `src/common/guards/perms.guard.ts` | 修改 | `roleCode === 'admin'` → `hasSuperRole(roles)`（superadmin 也能过） |
| `src/common/guards/roles.guard.ts` | 修改 | 新增超管直接放行，与上两处一致 |
| `src/modules/role/role.service.ts` | 修改 | `assignMenus` 对超管角色抛 400；`createRole`/`updateRole` 禁止占用超管编码；`createRole`/`deleteRole`/`updateRole` 的超管保护改用 `isSuperRole`；新增 `getMenuIds()` |
| `src/modules/role/role.v1.controller.ts` | 修改 | `GET :id/menu-ids`、`PUT :id/menus` 统一走 `roleService.getMenuIds()` |
| `concise-admin: src/lib/permissions.ts` | 修改 | 导出 `SUPER_ROLE_CODES` / `isSuperRoleCode()` |
| `concise-admin: src/features/system/role/index.tsx` | 修改 | 超管行的"分配权限""删除"按钮禁用 + tooltip；"已授权"列显示「全部（内置）」 |

### 每个东西干什么

- **`isSuperRole` / `hasSuperRole`**：一进一出两种形态（单角色码 / 用户角色数组），auth 汇总、两个守卫、角色服务全部走它。以后只改这一处，不会再出现"某层认、某层不认"。
- **`assignMenus` 拒绝写入**：超管权限来自内置规则，写入既不生效又会产生误导数据，所以直接 `400 + 内置超级管理员拥有全部权限，无需也不允许分配，修改不会生效`。
- **`createRole` / `updateRole` 禁占用超管编码**：否则新建一个 `roleCode=superadmin` 的角色会**静默继承全部权限**，等于开后门。
- **`getMenuIds` 对超管返回全部未删除菜单 id（69 个）**：让回显与真实权限一致。之前返回关联表那 2 条，弹窗只勾 2 个、列表显示 2 项，全是假信息。
- **前端按钮禁用 + 文案**：把"能点但没用"变成"点不了且说明原因"，`已授权` 列不再显示假数字。

## 验证（`dist` 运行 + 真实库 + 自签 token）

| 场景 | 结果 |
| --- | --- |
| `GET /v1/roles/{admin角色}/menu-ids` | `code=0`，返回 **69** 个 id（= 菜单树全部节点） |
| `PUT /v1/roles/{admin角色}/menus`（清空） | `code=1001`，`内置超级管理员拥有全部权限，无需也不允许分配，修改不会生效` |
| `GET /v1/roles/{viewer角色}/menu-ids` | 返回 1 个（普通角色仍按关联表） |
| `POST /v1/roles` `roleCode=admin` / `superadmin` | 均 `code=1001`，提示不允许创建 |
| `GET /v1/auth/permissions`（admin） | `permissions=["*"]`，6 个顶级菜单（69 个节点）—— 行为未变，超管仍全权 |

`tsc --noEmit`（前后端）、eslint 均通过。

## 坑

1. **不要只在前端禁用**：接口仍可被 curl 直接调用，写入脏数据。前端禁用只是体验，后端拒绝才是约束。
2. **`RolesGuard` 加超管放行改变了语义**：以前 `superadmin` 角色访问 `@Roles('admin')` 接口会被拒；现在放行。这是修正不是放宽 —— 与 `getPermissions` 给 `['*']` 的行为对齐。若将来不想要 `superadmin` 这个别名，只改 `SUPER_ROLE_CODES` 一处。
3. **`getMenuIds` 要过滤 `delFlag=0`**：菜单实体有软删，`find()` 不过滤会返回 71 条，比菜单树多 2 个已删节点（勾不上，但数字对不上）。
4. **库里 admin 的历史关联行（2 条）没删**：现在既不参与鉴权也不参与回显，属无害残留。要清理可执行（两库都跑过 `sys_role` 表）：
   ```sql
   DELETE rp FROM sys_role_permission rp
   JOIN sys_role r ON r.id = rp.role_id
   WHERE r.role_code = 'admin';
   ```
   建议先 `SELECT` 确认再删；即使不删也不会影响任何逻辑。

## 如何扩展

- 想彻底 DB 化（admin 也走授权表）：删掉三处 `hasSuperRole` 短路 → 迁移把全部菜单绑给 admin → 必须同时实现"不允许移除自己最后一个含 `system:role:update` 的角色"的防自锁校验，否则会锁死。
- 想加新的超管别名（如 `root`）：改 `src/utils/super-role.util.ts` 的 `SUPER_ROLE_CODES` 与前端 `lib/permissions.ts` 的同名常量，两处保持一致。
