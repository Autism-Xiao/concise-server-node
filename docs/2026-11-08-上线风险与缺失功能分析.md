## 二、上线风险

### 🔴 阻断

1. **测试账号与弱口令**：`admin/admin123`、`guest/guest123`、`auditor1`、demo 供应商及冒烟临时账号。上线前必须：改超管强密码、禁用/删除其余账号（用户管理里操作），或提供初始化脚本只保留超管。
2. **明文 HTTP**：JWT 双令牌走 HTTP 可被链路截获。必须 HTTPS（Nginx/Caddy 反代 + 证书），并设置 `TRUST_PROXY` 为反代网段（否则限流按反代 IP 计数，全站共享阈值互相误伤）。

### 🟠 高

3. **没有部署物**：无 Dockerfile / docker-compose / CI 流水线；迁移靠手动 `npm run migration:run`。建议最小集：`docker-compose`（app + mysql + redis）+ 启动脚本里先跑迁移再起服务，或 GitHub Actions 跑 build + smoke。
4. **无健康检查接口**：负载均衡/K8s 探活没有目标。建议加 `GET /api/v1/health`（@Public，检查 DB ping + Redis ping，不泄内部信息）。
5. **单实例假设**：SSO 一次性登录 code 存**进程内存 Map**（验证码/限流/锁已 Redis 化，唯它没有）。单实例部署无碍；**要多副本必须先换 Redis**（约 20 行改动）。

### 🟡 中

6. **可观测性为零**：Nest 内置 Logger 只打 console，无日志落盘/轮转、无慢查询/耗时埋点、无告警。最低配：pm2/容器日志收集 + `TRUST_PROXY` 正确 + MySQL slow log 打开。
7. **无备份方案**：MySQL（mysqldump 定时 + 异地）与上传文件目录（`FILE_STORAGE_DIR`，内容寻址不可变，rsync 即可）都没有备份脚本。
8. **CORS 未配置**：当前前后端同源（反代同域）无碍；一旦分域名部署要加 `enableCors` 白名单，不能开 `*`。
9. **前端 token 在 localStorage**：XSS 面较大，属框架现实；缓解 = 保持依赖审计 + 上 CSP，规划中可迁 httpOnly cookie（改动大）。

### ⚪ 低

10. **测试覆盖**：后端 0 个单测（全靠冒烟脚本），前端 7 个。核心 util（密码、锁、租户 scope、db-error）值得先补。
11. **后端文案中文硬编码**，无 i18n（前端已有中英双语）。

## 三、缺失功能（底座视角，按优先级）

| 优先级 | 功能 | 说明 |
| --- | --- | --- |
| P1 | 消息渠道中心 | 站内信注释里已预留：邮件/短信/webhook 通知模板 + 发送渠道，通知类需求（任务指派、公告、告警）都靠它 |
| P1 | 健康检查 + 就绪探针 | 同风险 4，半天工作量 |
| P2 | 系统设置中心 | 站名/Logo/注册开关/密码策略等目前散在 env 与硬编码，运营改不了 |
| P2 | 登录方式扩展 | 手机验证码登录、LDAP/企业微信扫码（OIDC 已就位，接其他 IdP 是配置活） |
| P2 | 数据大屏/报表导出 | 管理端统计目前只有首页概览 |
| P3 | 通用 Excel 导入 | 用户导入已有专用实现，可抽象成通用导入（模板下载 + 校验 + 异步任务） |
| P3 | 文件预览增强 | 当前图片可预览，office/pdf 走下载 |
| P3 | 任务调度界面增强 | job 有 CRUD + 启停，缺执行历史图表与失败告警联动 |

## 四、建议的上线动作顺序

1. 改密 + 清账号（半小时）
2. HTTPS + TRUST_PROXY + 反代（半天）
3. `GET /v1/health` + docker-compose + 迁移自动化（一天）
4. MySQL/文件备份脚本 + cron（半天）
5. 日志收集与慢查询（半天）
6. 多副本需求出现时：SSO code 换 Redis（20 行）
