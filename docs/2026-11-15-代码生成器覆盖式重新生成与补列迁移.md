# 代码生成器：覆盖式重新生成 + 补列迁移

> 2026-11-15 · 增强 · 后端 + 前端 + 生成脚本

## 背景

上一轮把「继续生成」的死路拆了（见 [代码生成器继续生成死路修复](./2026-11-15-代码生成器继续生成死路修复.md)），但 force 的语义定为「只补齐缺失文件」。用户实际点完拿到的是：

```
数据表 biz_order 已存在：本次不生成迁移，旧表结构不会被修改；要改字段请手写 ALTER 迁移
所有文件都已存在，本次没有写入任何文件；要完全重新生成请先删除对应目录
```

对已经生成过的模块来说，等于按钮按下去什么也没发生。**要的是「重新生成一遍」**，所以本轮把 force 升级成真正的覆盖式重生成。

## 关键判断：覆盖代码必须同时补表

只覆盖文件、不动表会产生更糟的结果：entity/DTO 里多了新字段，数据库里没有 → 一查询就 `Unknown column`。

所以覆盖必须和 ALTER 成对出现。生成器是纯文件生成器（不连库），因此由 service 查 `information_schema` 把现有列名塞进 spec：

```ts
const existingColumns = await this.tableColumns(tableName)
writeFileSync(specFile, JSON.stringify(this.toSpec(dto, existingColumns), null, 2))
if (dto.force) cliArgs.push('--overwrite')
```

脚本据此判断哪些字段是「新增」的，只给这些生成 ALTER 片段。

## 实现要点

### 1. `--overwrite`：先备份再覆盖

```js
if (!OUT_ROOT && fs.existsSync(file)) {
  if (!OVERWRITE) { /* 老行为：跳过 */ }
  const backupFile = path.join(backupRoot, rel.replace(/[\\/]/g, '__'))
  fs.mkdirSync(path.dirname(backupFile), { recursive: true })
  fs.copyFileSync(file, backupFile)
  overwrittenFiles.push(rel)
  writeFile(file, content)
}
```

- 备份根目录 `.codegen-backup/<ISO 时间戳>/`，相对路径里的分隔符压平成 `__`（`src__modules__x__x.entity.ts`），避免子目录重名
- 已加进 `.gitignore`（可再生，不入库）
- manifest 回传 `overwritten` + `backupDir`，前端直接展示「备份在哪，怎么回退」

### 2. 补列迁移：全部走「现查现判」

生成的迁移里不写死假设，而是运行时查 `information_schema` 再决定，所以重复执行也安全：

```ts
const columnRows: Array<{ c: string }> = await queryRunner.query(
  "SELECT COLUMN_NAME AS c FROM information_schema.COLUMNS WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'biz_order'"
)
const existingColumns = new Set(columnRows.map(row => row.c))
if (!existingColumns.has("channel")) {
  await queryRunner.query("ALTER TABLE `biz_order` ADD COLUMN `channel` VARCHAR(128) NULL DEFAULT NULL COMMENT '来源渠道'")
}
```

唯一索引单独补（`CREATE TABLE` 里的 UNIQUE KEY 对已存在的表不生效，静默丢失约束比缺列更危险）：

```ts
const indexRows: Array<{ n: string }> = await queryRunner.query(
  "SELECT DISTINCT INDEX_NAME AS n FROM information_schema.STATISTICS WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'biz_order'"
)
const existingIndexes = new Set(indexRows.map(row => row.n))
if (!existingIndexes.has("uniq_biz_order_channel")) {
  await queryRunner.query("ALTER TABLE `biz_order` ADD UNIQUE KEY `uniq_biz_order_channel` (`tenant_id`, `channel`)")
}
```

SQL 用 `JSON.stringify` 生成字符串字面量，绕开模板字符串里反引号的转义地狱。

**只加列，不改列**：已有列的类型/默认值/注释一律不动（改类型可能截断数据），差异只体现在 warnings 文案里。真要改类型得手写迁移。

### 3. 迁移去重：内容相同就不写第二份

覆盖模式下反复点生成，每次都会产一份带新时间戳的迁移 → `migrations` 表累积同表重复记录。现在写入前先比对：

```js
const normalizeMigration = text => text.replace(/\d{13}/g, '<timestamp>')
const sameMigrationExists = siblingMigrations.some(
  name => normalizeMigration(readFileSync(...)) === normalizeMigration(migrationContent)
)
```

只差时间戳的视为同一份，直接跳过并提示。改了字段 → 内容不同 → 正常写新迁移（补列）。

### 4. 前端

- 确认框标题改「模块已存在，重新生成并覆盖？」，按钮「重新生成」，正文说清「先备份再覆盖、迁移只补列、手改的代码会被替换」
- 结果卡：`写入 N 个文件（其中覆盖 M 个）` + 补列清单 + 备份路径
- 标题按 `created` 数量分三档：`没有写入文件` / `已重新生成` / `生成完成`
- toast：覆盖时是「已重新生成，覆盖 M 个文件」

## 踩的坑

- **只覆盖代码不补表 = 制造 500**。覆盖和 ALTER 必须绑定，否则用户改完字段发现页面直接报 `Unknown column`，比不生成更糟。
- **`CREATE TABLE` 里的 UNIQUE KEY 对已存在的表完全无效**，不单独补索引的话唯一约束会静默消失（业务上表现为「查重没生效」）。
- **迁移文件的时间戳让「内容相同」判断失效**：直接用文件是否存在判断会把每次重新生成都当成新迁移。必须把 13 位时间戳归一化后比较内容。
- **`JSON.stringify` 生成 SQL 字面量**：ALTER 语句里全是反引号和单引号，手写模板字符串要套三层转义；用 `JSON.stringify` 直接产出合法的双引号字符串，一次性绕开。
- **备份路径压平分隔符**：`src/modules/x/a.ts` 和 `concise-admin/src/modules/x/a.ts` 如果只取 basename 会撞名，压平整条相对路径才唯一。

## 如何扩展

- **支持改列类型**：在 `missingFields` 之外再算一份 `typeChanged`，生成 `MODIFY COLUMN`。**必须放在人工确认之后**：截断风险实打实，建议只对 varchar 加长、decimal 精度提升这类安全变更自动做，反过来一律 warning 不自动执行。
- **支持删列**：不建议自动。生成器删列等于删数据，最多在 warnings 里列出「表里有但定义里没有」的列，让人自己决定。
- **备份清理**：`.codegen-backup/` 目前只增不减。要自动清理的话按时间保留最近 N 份，别按大小（备份很小，但删错就找不回来）。
