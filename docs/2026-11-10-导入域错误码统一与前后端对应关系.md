# 导入域错误码统一 + 前后端 code 对应关系核查

> 起因：核查「前后端 code 是否一一对应」，发现导入类接口的码是分裂的——同样的「表头不对」在角色导入返回 6103，在职级/岗位/公告/用户/日志导入却返回 1001；`6104 导入文件没有数据行` 定义了很久但**一个地方都没用**（空文件全部落到 1001）。本轮把导入域收敛到 6103/6104 两个码，并删掉一个零消费的死码。

## 一、改了哪些文件

| 文件 | 类型 | 说明 |
| --- | --- | --- |
| `src/helper/import/excel-import.ts` | 修改 | `assertImportRows()` 的「表头下方没有数据行」改抛 `BizException(IMPORT_EMPTY, …, 400)`。这是所有导入入口的公共校验，改一处覆盖职级/岗位/日志等 |
| `src/common/enums/biz-error-code.enum.ts` | 修改 | ① 删除 `PASSWORD_EXPIRED = 2103`（强制改密功能未实现，零引用＝死码）；② `IMPORT_EMPTY` 注释写明消费方 |
| `src/modules/role/role.service.ts` | 修改 | 空文件、表头下无数据行 → `6104` |
| `src/modules/system/dict/dict.service.ts` | 修改 | 两张表都空、解析完 `total === 0` → `6104`；删掉不再使用的 `BadRequestException` 导入 |
| `src/modules/system/level/level.service.ts` | 修改 | 空文件 → `6104`；缺「职级名称」列 → `6103`；补 `BizErrorCode/BizException/HttpStatus` 导入 |
| `src/modules/system/post/post.service.ts` | 修改 | 空文件 → `6104`；缺「岗位编码」列 → `6103`；补导入 |
| `src/modules/system/notice/notice.service.ts` | 修改 | 空文件、表头下无数据行 → `6104` |
| `src/modules/system/log/log.service.ts` | 修改 | 缺「用户名」列 → `6103`；删掉不再使用的 `BadRequestException` 导入 |
| `src/modules/user/user.service.ts` | 修改 | 空文件、表头下无数据行 → `6104` |

> 「单次最多导入 N 行」保持 `BadRequestException`（→ 1001 参数校验失败）：它是参数超限，不是文件结构问题，不该和「表头不对」混用同一个码。

## 二、每个东西是干什么的

### 6103 / 6104 各自负责什么

| 码 | 语义 | 覆盖场景 |
| --- | --- | --- |
| `6103 IMPORT_HEADER_MISMATCH` | **文件结构不对**：找不到关键列 | 角色缺「角色编码」、职级缺「职级名称」、岗位缺「岗位编码」、公告缺「标题」、用户缺「登录账号」、日志缺「用户名」、字典缺「字典编码」 |
| `6104 IMPORT_EMPTY` | **文件没内容**：空文件、只有表头、解析后 0 行 | 上述所有导入入口的首行判空 + 公共 `assertImportRows()` + 字典的 `total === 0` |

两者都是 HTTP 400 + `success: false`，前端 `http.ts` 走 `ApiError('business', …, code)`：message 直接展示，code 透传给调用方。

### 前后端 code 到底怎么「对应」

审计结论：**不需要也不存在一一对应**，真实关系是「后端 43 个码 : 前端 2 个显式分支」：

| 前端位置 | 认的码 | 为什么必须是码 |
| --- | --- | --- |
| `features/auth/login.tsx` | `1009` | 锁定要禁用提交按钮 + 显示倒计时，UI 结构变了，不能靠文案 |
| `lib/http.ts` | `401`（兼容分支） | 个别网关用 HTTP 200 + code 401 表达认证失效，要踢下线；被 `tests/http-unauthorized.test.cjs` 锁定 |

其余码前端一律不分支，只展示后端 message —— 因为后端 message 本身就是人话（「该字典下存在 3 个字典项，请先删除字典项」），把它们逐个映射成前端文案等于维护两份真相。判断「这个码该不该加」的标准始终是**有没有消费者**，而不是「前端有没有对应的 if」。

## 三、遇到的坑

1. **`assertImportRows` 是隐藏的单点**：职级/岗位/日志三个模块的空行校验都在这个公共函数里，只改各模块自己的 `if (!rows.length)` 会漏掉「有表头没数据」这一半场景。改导入域的错误码，先 grep 这个 helper。
2. **补码之后立刻被 eslint 抓出未使用导入**：`dict.service.ts` / `log.service.ts` 换掉最后一处 `BadRequestException` 后，import 里的 `BadRequestException` 就成了未使用变量（`--max-warnings=0` 直接红）。换码时顺手核对文件里还有没有别处在用。
3. **判断死码要先看有没有被间接引用**：`2103` 我用 `grep -rn "PASSWORD_EXPIRED\|2103"` 全仓 + docs 扫过，确认零引用才删。上一轮就吃过亏（`json.code === 401` 看着是死码，其实是单测锁定的契约）。
4. **3461 上的旧测试实例会冒充新代码**：直接 `node dist/main.js` 撞 `EADDRINUSE` 时，`curl /api/docs-json` 仍然 200（旧进程在答），很容易误判「已经是新代码」。启动前先 `PORT=3461 node scripts/serve.mjs --dry-run` 看占用者。

## 四、怎么扩展 / 使用

- **新增导入模块**：解析完表格后调 `assertImportRows(dataRows)`（空行→6104、超限→1001），缺关键列时抛 `BizException(BizErrorCode.IMPORT_HEADER_MISMATCH, '未找到「X」列，请使用导入模板的表头', HttpStatus.BAD_REQUEST)`，不要新造码。
- **前端要按导入错误做差异化 UI**（例如只在 6103/6104 时高亮「下载模板」按钮）：`catch (e) { if (isApiError(e) && (e.code === 6103 || e.code === 6104)) … }`，不要去 match 中文文案。
- **查码**：唯一定义处 `src/common/enums/biz-error-code.enum.ts`；HTTP 状态→码的兜底规则在 `src/common/filters/any-exception.filter.ts`。
