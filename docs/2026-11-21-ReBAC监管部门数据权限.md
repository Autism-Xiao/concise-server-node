# ReBAC 监管部门数据权限（数据级「本部门/本区域」补齐）

日期：2026-11-21
类型：增强 + 测试

## 背景

四级权限对照（见 `2026-11-21-SaaS底座六维对比与优化路线.md`）里，数据级此前只有四层：租户隔离、`data_scope`、owner 行权限、套餐交集。**部门档(2/3)在业务数据上被显式降级为「仅本人」**——因为 `customer` / `biz_order` 没有 `dept_id` 列，无法写 `dept_id IN (...)`。这导致「区域经理只能看本区域数据」这个典型场景做不到，是四级权限里唯一有实质能力缺口的一级。本轮按 P2 清单第 11 项落地轻量版 ReBAC，不引入通用关系图。

## 每项作用与设计决策

### 1. 关系表存「已展开的有效部门」

`assignSuperviseDepts(userId, deptIds)` 在**写入时**把入参部门的所有子孙部门一并展开落库（内存 BFS，`select(['id','parentId'])` 拉全量 + `applyTenantScope`），查询期直接 `IN (:...deptIds)`，不做递归 SQL、不依赖请求携带部门树。

- 取舍：部门树调整后需要重新配置一次相关用户的监管范围；换来的是热路径零递归、actor 只带一个字符串数组。
- 与「所属部门」（`sys_user_depart`）是两套关系，互不改写；前者是「我在哪」，后者是「我管哪些」。
- 租户级资产：不能把 A 租户用户授权去监管 B 租户部门（平台共享 `tenant_id=0` 允许）；写路径用 `tenantWriteSql` 严格按当前租户收窄，避免 A 的一次全量覆盖删掉同账号在 B 的监管行。

### 2. actor 携带与缓存

`findOneWithRoles`（JwtStrategy 每次鉴权都走、已有 30s 的 `AuthUserCacheService`）顺带 `loadSuperviseDeptIds(id)` 挂一个非列属性 `superviseDeptIds`，经 `{...user}` 展开进 `req.user`。不写进 `UserEntity` 列：它是权限上下文不是用户资料，避免随用户接口外泄。`assignSuperviseDepts` 写后调 `authUserCache.invalidate(id)`，授权变更立即生效。

### 3. 可见范围口径（写进 owner-scope.util）

| 角色 data_scope | 可见范围 |
| --- | --- |
| 平台管理员 / ALL(1) | 全部，不加条件 |
| 部门档 2/3 + 有监管授权 | `owner = self` ∪ `owner ∈ 监管部门成员`，用 `EXISTS (SELECT 1 FROM sys_user_depart ...)` 从 owner 反查所属部门 |
| 部门档 2/3 + 无授权 | 仅本人（保持原保守降级） |
| 仅本人(4) | 始终仅本人，**监管授权不放大** |

- 多角色沿用 `Math.min(dataScope)`（数值越小权限越大）。
- 不区分 2（本部门及以下）与 3（本部门）：两者的差别已由配置时的「展开子孙」表达；若要「只看本部门」，配置时只选该部门且不去改树即可（当前展开策略统一含子孙，见下方挂账）。
- 列表 `listByQuery` 与详情 `findOneScoped` 共用同一个 `applyOwnerScope`，保证「列表看不见 = 详情也进不去」。

## 验证结果

- build / lint / format:check 全绿；单测 **49/49**（新增 4 例）。
- 新冒烟 `smoke-supervise-dept` **12/12**，覆盖：授权前只看自己 → 授权部门 A 后能看到 A 与 A 子成员的客户 → 仍看不到 B 成员 → B 客户详情 404 → 改 `data_scope=4` 后监管授权不放大。
- 回归冒烟无退化：tenant-isolation 23/23、file-recent 7/7、dashboard 60/60、user-setting 18/18、P1 25/25。
- 迁移 179500 已在本地库执行；新路由PUT 探测 401（需鉴权）非 404，确认新代码加载。

## 踩的坑

- 表名是 `sys_depart` 不是 `sys_dept`；`sys_user` 没有 `dept_id`（早已改多对多 `sys_user_depart`），所以业务表无法直接按部门列过滤，只能从 owner 反查。
- `tenantWriteSql(tenantId, column)` 的参数顺序是「租户在前、列在后」，一开始写反导致条件拼错。
- 冒烟数据准备：`sys_user` 用 `login_tenant_id` + `sys_user_tenant`，且 `sys_user_tenant.status` 必须 **0** 才算有效成员（写 1 会被租户切换判为「不属于该租户」403）；`sys_role` 用 `status` 不是 `del_flag`。
- 冒烟用户名后缀正则 `^sup\w+_` 会贪婪吃掉整个用户名，生成的 user_id 重复；改成自增序号。
- `SMOKE_BASE` 要传 `http://host:port/api`（脚本内部自带 `/v1/...`），传 `/api/v1` 会拼成 `/api/v1/v1/...` 404。

## 如何扩展

- **接更多业务模块**：在对应 service 的 `listByQuery` / `findOneScoped` 调用点传入带 `superviseDeptIds` 的 actor（controller 的 `OwnerRequest` 类型同步加字段），无需改数据库。
- **区分「本部门」与「本部门及以下」**：`OwnerScopeActor` 增加一个 `superviseScope` 字段，`applyOwnerScope` 按档位决定是否展开子孙；或在 `assignSuperviseDepts` 加 `includeChildren` 参数（需要同步调整关系表语义，当前表存的都是展开后的 id）。
- **撤销授权**：`PUT .../supervise-depts` 传空数组即可全量清空；会即时失效 authUserCache。
- **前端配置界面**：本轮只提供后端接口，用户管理页尚未加「管辖部门」的选择控件；可参照现有「绑定部门」抽屉扩展。
- **注意**：`@OperLog` 目前会把配置请求体（部门 id 列表）写进 `sys_log.params`；部门 id 不是敏感信息，但若要审计「谁改了谁的监管范围」需单独建模。
