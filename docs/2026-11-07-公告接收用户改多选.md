# 公告「接收用户」改为多选（2026-11-07）

> 反馈：上一版做成了「一个输入框 + `<datalist>` 候选」，那玩意儿天生**一次只能选一个**，还得手敲逗号 —— 公告接收人需要的是**多选**。
> 存储契约不动：`sys_announcement.user_ids` 仍存用户 ID 的逗号串，多选只发生在表单层。

## 交互设计

| 环节 | 行为 |
| --- | --- |
| 已选展示 | 输入框内是 chips：`账号（姓名）`，每个带 ×；已删用户显示红色 `#id` |
| 选择 | 点输入框展开候选，**点一项加入、再点移除**，面板不关闭，可连续勾多个 |
| 搜索 | 输入即搜，服务端 `keyword` 匹配账号 / 姓名 / 电话（`/v1/users?keyword=`），**覆盖全量用户**，不再受「前 100 个」限制 |
| 键盘 | `↑` `↓` 移动高亮、`Enter` 勾选/取消、`Esc` 收起、输入框为空时 `Backspace` 删最后一个 |
| 底部 | 「已选 N 人」+「清空」 |
| 回显 | 打开编辑时用 `GET /v1/users/lookup?ids=` 批量把存量 ID 翻译成账号（一次请求，最多 100 个） |
| 边界 | 用户已被删除 → chip 红色 `#id`，保存时**原样保留该 ID**，不静默丢配置 |
| 容错 | 用户列表拉不到（缺 `system:user:list`）时面板提示「无法加载用户列表」，已选 chips 靠 lookup 仍能显示、仍可保存 |

## 遇到的坑

1. **`<datalist>` 天生单选**：它的候选一次只能填一个值，想多选只能自建 combobox（chips + 下拉），别指望它改改属性就行。
2. **路由顺序**：`@Get('lookup')` 必须写在 `@Get(':id')` **之前**，否则 `lookup` 会被当成 id 吃掉（Nest 按注册顺序匹配）。
3. **chips 不能只靠搜索结果**：下拉只有当前页 100 条，已选人的账号必须单独缓存；`lookup` 查不到的 ID 要记进 `attemptedRef`，否则「查不到 → 依赖变化 → 再查」会**死循环**。
4. **选中后 placeholder 被清空**（避免和 chips 挤在一起），导致自动化按 placeholder 找输入框失败 —— 已给 input 加 `data-multiselect-input` + `aria-label`。
5. **面板是 `absolute` 浮层**，会压住下方「生效开始/结束」日期框（点外部即收起）；多选必须保持面板打开，所以不能像单选那样选完就关。
6. **调前端先确认端口**：本机 5173 被另一个项目（「普通话口语测评管理系统」）占着，headless 一路打在那个站上，表现为「注入登录态无效 + 总是跳 /login」，差点误判成权限守卫问题。`curl <host>/ | grep title` 一行就能排除。

## 怎么扩展

- 「按部门 / 按角色」批量选人：在面板里加 Tab，选中集合仍换算成 ID 数组，后端契约不变。
- 已选超过 100 人：`lookup` 截断 100，chip 会退化成 `#id`；需要更大规模时把 `lookup` 改成 POST 分批或做成分页回显。
- 该控件是通用的（`features/users/components/`），日程参与人、任务指派等场景可直接复用 `value: string[]`。

## 补充修复：保存后重新编辑，已选人全变红色 `#ID`

**现象**：保存公告后再打开编辑，4 个已选用户全是红色 `#1714471285016895490` 这种裸 ID，账号没翻译出来（截图报障）。

**根因**：回显 effect 用 `attemptedRef` 做「已尝试」去重 ——

```tsx
const missing = ids.filter(id => !attemptedRef.current.has(id))
if (!missing.length) return
missing.forEach(id => attemptedRef.current.add(id))   // ← 请求还没回来就登记了
lookupUsers(missing).then(...)                        // ← cleanup 里 alive=false 会丢弃结果
```

开发环境 React StrictMode 把 effect 跑两遍：第一遍发出请求 → 立刻 cleanup（`alive=false`，结果被丢）→ 第二遍因为 ID 已进 `attemptedRef` **直接 return**。于是 `briefs` 永远是空，chip 全部退化成红色 `#id`（生产构建只跑一次，所以只在 dev 暴露）。

**修复**：

1. 去重依据从「ref 记录已尝试」改成「`briefs` 里有没有这个 ID」，effect 依赖加 `briefs`；只有**真正拿不到账号**（账号已删/接口不可用）才写 `failedRef` 阻断，避免无限重试。
2. 顺手加降级：`lookup` 抛错或返回空时退回 `fetchUsers()`（前 100）翻译一遍，后端还没升级到带 `/users/lookup` 的版本时也能显示账号。

**验证**（headless 真实点击编辑 `notice_user_demo`）：

- chips：`ceshi（测试用户）` `zhangsan（张三）` `admin（管理员）` `jeecg（concise）` —— 4 个全蓝，无红色 `#id`
- `lookup` 两次 200（StrictMode 双发，仅 dev），`briefs` 正常写入

> 教训：**在 effect 里做「已尝试」标记，必须放在请求成功之后**；放在发请求之前 + cleanup 丢弃结果 = dev 下永久丢数据，而生产环境看不出来。
