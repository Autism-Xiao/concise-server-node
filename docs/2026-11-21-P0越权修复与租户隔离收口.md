# P0 越权修复与租户隔离收口（2026-11-21）

## 背景

落地 `docs/2026-11-21-SaaS底座六维对比与优化路线.md` 的 P0 六项。这几项不是"优化"，是已经能被真实触发的越权/数据串味：

1. `assignRoles` 全量覆盖会删掉同一账号在别的租户的角色绑定；
2. owner 数据范围只守列表，详情/编辑/删除按 id 就能绕过；
3. `file.recent` 只按 owner 查，同账号跨租户的最近文件互相可见；
4. 旧 `/upload` 把整个 `public/` 静态托管，文件名可预测，且记录无租户归属；
5. `cleanLogJob` 原生 SQL 删全库日志，ALS 上下文兜不住裸 SQL；
6. `jobClassName` 唯一性跨租户，第二个租户建不了同名任务。

## 每项作用（为什么这么改）

### 1. assignRoles 跨租户解绑 → tenantWriteSql

原实现 `SELECT role_id FROM sys_user_role WHERE user_id = ?` 取该用户在**所有租户**的角色，再把不在入参里的全删。同一账号同时属于 A/B 时，A 租户管理员调一次"改角色"就会把 B 租户的角色绑定清掉（B 的编辑/管理员权限凭空消失）。

新增 `tenantWriteSql` 生成 ` AND tenant_id = ?`（位置参数，给 `em.query()` 用），读取和删除都带上；`TenantContext=null`（超管平台视角）才不加条件，保留运维能力。注意**共享角色绑定（tenant_id=0）也被排除在 A 租户视角外**，重绑时 `INSERT IGNORE` 撞唯一键自动跳过，不会重复插。

### 2. owner 权限扩到详情/编辑/删除

不在基类 `findOne` 上直接加 owner 条件——它被 `update/softDelete`、定时任务、租户开通等内部路径复用，收窄会误伤平台代维。新增 `findOneScoped`，与 `listByQuery` 共用 `applyOwnerScope`，保证"列表看不见 = 详情进不去 = 改不了"。customer/biz_order 的详情、PUT、DELETE 三个入口都传 `req.user`。

### 3. file.recent 补租户条件

原用 `repository.find({ where: { ownerId, ... } })`，owner 是全局 user id，A 租户能看到同账号在 B 租户的最近文件。改成 QB + `applyTenantScope('f')`，与 list/stats/detail 同口径。

### 4. 旧 /upload 收口（取舍说明）

彻底方案是旧上传整体迁到文件中心的鉴权下载接口，但头像/富文本插图用 `<img src>` 直连，无法带 Authorization；强改会波及前端所有头像展示。本次做**风险可控的最小收口**：

- 静态托管根目录从整个 `public/` 收窄为 `public/upload/`，URL 前缀不变（前端零改动）；
- `fileRename` 加 8 位随机 hex，文件名不再可预测；
- `tool_storage` 加 `tenant_id` 归属留痕 + 索引，为后续鉴权下载/按租户清理铺路；
- 保留位图白名单、文件头验真、`nosniff` + CSP + 非位图 `attachment` 的既有防线。

**静态直出的公开读语义未变**（这是 `<img>` 场景的必然），敏感文件必须走 `/api/v1/files/:id/download` 鉴权下载，不能放进 upload 目录。

### 5. 后台任务上下文与 cleanLogJob

`JobScheduler` 虽然已用 `withTenant(job.tenantId)` 包住执行体，但 `cleanLogJob` 里是裸 `dataSource.query('DELETE FROM sys_log ...')`，ALS 管不到原生 SQL——租户级任务会删掉全库日志。改用 `tenantWriteSql` 拼条件，平台级任务（tenantId=0 → 上下文 null）保持全库清理。

`FileCleaner.sweep()` 原本依赖"cron 线程 ALS 为空 → filterTenantId()=null → 全租户"的**隐式**行为，改成显式 `withTenant(null, ...)`，将来从请求链直接调用也不会泄漏单租户上下文。`ReminderScheduler` 的表刻意不带 tenant_id（日程跟随人），加注释说明不是漏传。

### 6. jobClassName 唯一性

执行器是全局注册的，每个租户本来就该有自己的 `cleanLogJob`；全局唯一会让第二个租户建不了同名任务。改走 `createTenantQb`，租户视角自动收窄（读范围含共享行）。

## 踩的坑

1. **冒烟登录路径**：`SMOKE_BASE` 已含 `/api`，登录要写 `/v1/auth/login` 而非 `/auth/login`（否则 404 `Cannot POST /api/auth/login`）；租户接口同理 `/v1/tenants`。
2. **`sys_role` 没有 `del_flag` 列**：专项脚本按旧习惯加该条件报 `ER_BAD_FIELD_ERROR`，去掉即可。
3. **冒烟数据自清**：新脚本用 `finally` 删 `sys_file` 元数据行、软删临时租户；site 清失败只 warn 不掩盖断言。
4. **format**：5 个文件被 Prettier 判不合规（`job.handlers.ts`、`user.service.ts`、新冒烟与两个测试），`prettier --write` 已修；注意 `format:check` 脚本只覆盖 `src/` 和 `test/`，`scripts/` 要手动 check。
5. **构建后必须重跑单测**：测试读的是 `dist/`，`prettier --write` 后没重新 build 会测到旧代码。

## 如何扩展

- **owner 权限扩到新业务模块**：实体须有 `createBy`，service 加 `findOneScoped` 包装并让详情/编辑/删除的 controller 传 `req.user`；`supplier` 无 createBy，补列+迁移后照做。
- **原生 SQL 的租户条件**：凡是 `manager.query()` / `dataSource.query()` 拼出来的写路径，一律用 `tenantWriteSql` 而不是手拼 `AND tenant_id = ?`；单测已有守门。
- **旧上传彻底鉴权化**：`tool_storage.tenant_id` 已就位，下一步是新增 `GET /v1/upload/:id/file` 鉴权下载、前端头像改走该接口，再把 `useStaticAssets` 整个摘掉。在此之前不要把敏感文件写进 `public/upload`。
- **delete() 的边界（本次未改，挂账）**：账号软删是全局身份动作（会清该用户所有租户的 `sys_user_tenant`），真正的越权面在"谁有权全局删号"，需要按 actor 的租户归属设计，属于产品决策，不在 P0 范围。
- **P1/P2 未做**：租户级配额、per-tenant 限流、MeteringService、字段级脱敏、ReBAC、feature flag、租户导出、指标与审计哈希链——见对比报告第七节。
