# 从零上手这个项目：阅读路线图

> 面向「接手 / 重学」这个仓库的人。按顺序读，**不要从最大的文件开始**（`user.service.ts` 1588 行会直接劝退）。
> 每个阶段都给了「读完该能回答什么」和「怎么动手验证」，读完不验证等于没读。

---

## 0. 先把它跑起来（30 分钟，别跳过）

| 事 | 怎么做 |
| --- | --- |
| 装依赖 | `pnpm install --force`（**禁用 `npm install`**，会崩 arborist） |
| 起后端 | `npm run build` → `node scripts/serve.mjs`（端口 3459） |
| 起前端 | `cd ../concise-admin; npm run dev` → http://localhost:5173 |
| 看接口 | http://localhost:3459/api/docs （Scalar，脚本已本地化，断网可开） |
| 登录 | `admin` / 见 `.env` 或数据库；库里还有 `guest`（无角色）、`auditor1`（只读日志） |
| 数据库 | MySQL 8.4，库 `concise_server`，账号在 `.env` |

**验收**：能登录进后台，点开「系统管理 → 用户管理」看到列表。

## 1. 启动链路：一个请求进来之前发生了什么

| 顺序 | 文件 | 行数 | 读什么 |
| --- | --- | --- | --- |
| 1 | `src/main.ts` | 281 | 全局前缀 `api`、helmet、静态目录、`ValidationPipe`、文档三件套、`/` 与 `/favicon.ico` 兜底 |
| 2 | `src/app.module.ts` | 137 | `ConfigModule.forRoot`、`TypeOrmModule`、**6 个全局 provider 的注册顺序**（`APP_GUARD` 是数组顺序执行） |
| 3 | `src/config/index.ts` + `app|database|jwt|redis.config.ts` | — | 配置怎么按命名空间注册、`.env` 怎么被校验（`env.validation.ts`） |

**动手**：把 `main.ts` 里 `Swagger` 那段注释掉，重启，看 `/api/docs` 变成什么。

## 2. 一次请求的完整生命周期（用最小的模块当标本）

`health` 模块全加起来不到 80 行，是最干净的教材。

| 顺序 | 文件 | 行数 | 重点 |
| --- | --- | --- | --- |
| 1 | `src/modules/health/health.controller.ts` | 65 | Controller / Service 分离、`@Public()` 放行的位置 |
| 2 | `src/common/interceptors/transform.interceptor.ts` | 31 | 统一响应 `{ code, message, result, success, timestamp }` 就是这里包出来的 |
| 3 | `src/common/filters/any-exception.filter.ts` | 86 | 异常 → 业务码的三条映射规则（业务异常 / 已知 HttpException / 未映射 4xx） |
| 4 | `src/common/exceptions/biz.exception.ts` | — | `BizException(code, '人话文案')` 怎么抛 |
| 5 | `src/common/enums/biz-error-code.enum.ts` | — | 码分段规则（冻结段 / 21xx 认证 / 31xx 角色 / …） |
| 6 | `src/common/interfaces/api-result.interface.ts` | — | 类型定义（注意**是 `result` 不是 `data`**） |

**读完该能回答**：业务失败为什么返回 HTTP 200？`result` 什么时候是 `null`？

**动手**：在 health 里 `throw new BizException(BizErrorCode.PARAM_INVALID, '测试')`，用 curl 看响应体。

## 4. 认证与鉴权（这个项目最值得学的部分）

| 顺序 | 文件 | 行数 | 重点 |
| --- | --- | --- | --- |
| 1 | `src/modules/auth/controllers/auth.v1.controller.ts` | — | 10 个路由：登录/刷新/改密/2FA/SSO |
| 2 | `src/modules/auth/dto/login.dto.ts` + `change-password.dto.ts` | — | DTO 校验规则 = 前端校验规则的来源 |
| 3 | `src/modules/auth/services/auth.service.ts` | 475 | 登录主流程：滑块验证码 → 密码校验（bcrypt 历史格式就地升级 Argon2id）→ 锁定计数 → 双令牌 → 2FA 门禁 |
| 4 | `src/modules/auth/strategies/jwt.strategy.ts` | 90 | **每次请求都查库核对用户状态**（不只是验签） |
| 5 | `src/modules/auth/guards/jwt-auth.guard.ts` | — | 结合 `@Public()` 的放行逻辑 |
| 6 | `src/common/guards/roles.guard.ts` | 40 | `@Roles()` 粗粒度 |
| 7 | `src/common/guards/perms.guard.ts` | 65 | `@Perms()` 按钮级权限，实时查 `menu.permission`，admin 直通 |
| 8 | `src/common/guards/rate-limit.guard.ts` | 74 | 全局限流 + `@RateLimit()` 收紧 |
| 9 | `src/shared/permission-cache/` | — | 权限集合缓存，改授权必须 `invalidate` |
| 10 | `src/shared/totp/totp.util.ts` | — | 纯 `node:crypto` 的 RFC6238 实现（可选读） |

**读完该能回答**：① 双令牌各自有效期与用途；② 守卫执行顺序为什么是限流 → 认证 → 角色 → 权限点；③ 为什么 2FA 输错不计入登录锁定。

**动手**：curl 登录拿 `accessToken`，再带 `Authorization: Bearer xxx` 调 `/api/v1/auth/profile`；把 token 改一个字符，看返回码。

## 按目的抄近路

| 你的目标 | 只读这几段 |
| --- | --- |
| 加/改一个业务接口 | 2 → 3 → 6 |
| 动登录、权限、密码 | 4（+ 2 的异常过滤器） |
| 做租户相关功能 | 5（+ 3 的 BaseService） |
| 写前端页面 | 2 → 7（+ 6 找对应后端） |
| 排查线上问题 | 1 → 2 → 8（看日志/冒烟脚本） |
| 只想快速跑通 demo | 0 → 7 的 1、2 两个文件 |

## 三条「不要」

1. **不要**从 `user.service.ts`（1588 行）开始，也不要通读 `migrations/`（52 个）。
2. **不要**先看 `routeTree.gen.ts` 和 `sql/*.sql` —— 一个自动生成、一个是快照。
3. **不要**只读代码不看 `docs/`：155 篇变更说明里写清了「当时为什么这么做、踩了什么坑」，遇到看不懂的设计先去 `docs/README.md` 搜关键词。
