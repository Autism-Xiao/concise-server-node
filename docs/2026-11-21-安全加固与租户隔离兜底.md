# 安全加固与租户隔离兜底（2026-11-21）

## 背景

对照两篇多租户最佳实践（共享表 + tenant_id、RLS + RBAC 双层隔离）逐条审计本项目后，落地用户选定的全部七项改动：4 个确定 bug + 租户隔离兜底 + 越权冒烟接 CI + owner 级行权限。审计结论是项目水位已高于文中平均值，真正缺口集中在"应用层强制"而非"设计缺失"。

## 每项作用（为什么这么改）

### 1. applySort 原型链（P2 稳定性）
原实现 `allow[query.sortBy]` 用普通对象直接索引。`sortBy='__proto__'/'constructor'/'toString'` 会命中 `Object.prototype` 上的成员，`if (!column)` 判断为真，拼出 `alias.function Object()...` 之类非法列名，TypeORM 抛错 → 列表接口稳定 500（可反复触发的 DoS）。改为 `Object.prototype.hasOwnProperty.call` 后，非白名单键一律不命中。列值仍不经前端直拼，无 SQL 注入面。

### 2. 2FA 失败计入锁定（H2 安全）
`recordLoginFailure` 原先只对 `LOGIN_FAILED(1007)` 计数，`TOTP_INVALID(2106)` 不计数。攻击者掌握正确密码后，2FA 是最后一道防线，却可无限在线爆破（IP 限流换代理可绕）。现在 1007 与 2106 都计入同一账号失败阈值；达阈值统一转 `ACCOUNT_LOCKED(429)`，未达阈值保留各自错误码与文案（2FA 失败用 `totpFailureMessage` 带"验证码"语义，不冒充"密码错误"）。`TOTP_REQUIRED(2105，缺码)` 仍不计——那是漏填不是猜错。现有冒烟对密码文案的断言完全不受影响。

### 3. 备份码并发竞态
`consumeBackupCode` 原是 findOne → 判 `usedAt` → update 三步，两个并发登录可同时读到 `usedAt=null` 并都通过。改为单条带条件 UPDATE：`{ userId, codeHash, usedAt: IsNull() } → { usedAt: now }`，由数据库行锁保证只有一个连接改到行，`affected===1` 者胜出。

### 4. refreshToken 账号状态（纵深）
`findOneDetailForAuth` 只过滤 `delFlag=0`，冻结用户理论上仍能换发令牌。虽然冻结时 `setStatus` 已 `kickUser` + 写用户级吊销标记（正常路径拦得住），但手工改库/历史数据可能绕过。refresh 前显式校验 `status===NORMAL`，作为最后一道闸门。与登录口径一致，不影响既有测试。

### 5. 租户隔离兜底（应用层等价防线）
关键认知：**TypeORM 没有 MyBatis-Plus 那种解析 SQL 自动追加 `AND tenant_id=?` 的全局拦截器**，项目 ESLint 也未开 type-aware（无实体类型信息），因此"ESLint 规则禁裸调 createQueryBuilder"会误伤 123 处调用且无法判断实体是否带 tenantId。改用三层等价防线：
- **安全入口**：`createTenantQb(repo, alias)` 内部调 `applyTenantScope`，调用方拿到就已带条件，杜绝"忘记加"。三个手写 QB 的业务服务（customer/biz_order/supplier）已迁入。
- **单测**：3 个工厂用例验证租户/平台/共享三种视角的注入行为。
- **CI 门禁**：隔离冒烟脚本接入 CI（见下）。

### 6. 越权冒烟 + CI
`smoke-tenant-isolation.mjs` 建号用 `iso123456`（小写+数字两类），被 `requireComplexity`（四类至少三类）拦成 400，导致整个脚本在"建用户"处中断——这正是上次审计报告里"脚本与代码脱节"的那一项。改用 `Sm0ke@Iso2026`（四类齐全、非常见、非序列、不含用户名），脚本 23/23 全绿。CI 冒烟 job 新增该脚本，隔离回归失败即拦合并。

### 7. owner 级行权限
复用项目已有的 `sys_role.data_scope`（1 全部 / 2 本部门及以下 / 3 本部门 / 4 仅本人），不另造权限模型：
- `needsOwnerScope(actor)`：平台管理员或 data_scope=ALL(1) 不收窄；多角色取 `Math.min`（数值越小权限越大，与 `user.service.applyDataScope` 同口径）。
- `applyOwnerScope(qb, alias, actor, ownerColumn)`：受限时加 `createBy = 当前用户 id`。
- customer / biz_order 的列表接口接入（两表有 `createBy` 审计字段，天然是 owner 语义）。
- 部门档(2/3)因业务表无 `dept_id`，保守退化为"仅本人"（宁可少看不可越权）。

## 踩的坑

1. **本地 dev 库缺列导致登录 500**：迁移 `1794950000000-TenantAdminFlagAndIndexes`（加 `sys_user.is_tenant_admin` + 3 个复合索引）一直没在本地执行，旧 dist 没带该字段所以没暴露，重新 build 后登录直接 `Unknown column 'user.is_tenant_admin'` 500。跑 `npm run migration:run` 补齐即可。CI 本来就有迁移步骤，不受影响。
2. **owner 冒烟脚本跑不通**：customer 模块的按钮权限点 `customer:list` 未录入菜单系统（工作记忆里挂账的"部分业务模块按钮权限未录入"），受限角色拿不到该权限，无法做端到端 owner 验证。该临时脚本已移除；owner 逻辑由 7 个单测 + controller→service 静态链路保证。残留的 1 个用户 + 1 个客户已手工清理干净。
3. **多角色 data_scope 语义**：`Math.min` 取的是"最大权限"（数值小=权限大），初版单测误以为"含仅本人则收窄"写反了期望，已修正为"含全部(1) 则放行"。
4. **prettier**：多行 `repository.update(filter, value)` 的折行格式被 Prettier 判不合规，`prettier --write` 自动修复。
5. **oxlint 既有 3 error**：`reminder.scheduler.ts:50` / `webhook.service.ts:324` / `file.cleaner.ts:33` 的 `no-floating-promises`，是上次审计已记录的既有问题，与本次改动无关，CI 里为非阻断。本次未改（避免范围蔓延）。

## 如何扩展

- **新业务模块要 owner 权限**：实体需有 `createBy` 列（写入时 BaseService 不自动填，参照 customer 在 create 里 `createBy: TenantContext.userId()`），列表 query 调 `applyOwnerScope(qb, alias, actor)`，controller list 传 `req.user`。`supplier` 目前无 `createBy`，补列+迁移后即可接入。
- **owner 权限扩到详情/导出/编辑**：目前只做列表（最主要泄露面）。详情 `findOne` 被 BaseService 的 update/delete 复用，直接改会影响写路径；建议新增独立的 `findOneScoped(id, actor)` 供读接口使用。
- **部门档(2/3) 精确化**：给业务表加 `dept_id`，在 `applyOwnerScope` 里扩展为部门集合过滤（参照 `user.service.applyDataScope` 的父子展开）。
- **真正的框架级强制**：若未来迁 PostgreSQL，可用 RLS 在数据库层兜底（本工具保留为业务层第二道）；或在 TypeORM 之上封装统一 Repository，强制所有查询经工厂创建。
- **新增白名单排序字段**：在对应 service 的 `*_SORTABLE` 表里加映射即可，`applySort` 的原型链防护对所有调用方生效。
