# 职级 / 岗位示例数据（对齐 jeecg 职务职级字典）

> 日期：2026-11-04
> 目的：给 `sys_level`（职级）和 `sys_position`（岗位）灌入可溯源的初始化数据，来源为 JeecgBoot 官方「职务职级」字典 `position_rank`

## 一、改动文件

| 文件 | 类型 | 说明 |
|---|---|---|
| `scripts/seed-level-post.cjs` | 新增 | 职级/岗位示例数据灌入脚本，幂等（可重复执行），按业务唯一键判断新增或更新 |
| `docs/README.md` | 修改 | 追加本轮变更索引 |

本次**没有改任何业务代码**，也没新增迁移——`sys_level`、`sys_position` 两张表在上一轮（部门职级岗位 V1 接口）已经建好，这里只补数据。

## 二、数据来源

JeecgBoot 官方 SQL 里「职务职级」是一套字典 `position_rank`（`sys_dict` + `sys_dict_item`），原始 4 项：

| position_rank | 名称 |
|---|---|
| 1 | 员工 |
| 2 | 小组长 |
| 3 | 部门经理 |
| 4 | 副总经理 |

再往上 jeecg 组织架构里的最高职务是「总经理」（v3.8.3 后为「董事长 → 总/副总 → 部长/副部长 → 职员」体系），这里补成第 5 级，凑成完整阶梯。

注意：本表 `level_rank` 的语义是**数字越大级别越高**，和 jeecg `position_rank` 的序号方向一致，所以直接沿用 1~5，没有做翻转（早期项目里日志表的 `status` 才是反的，那边要取反，这里不用）。

## 三、写入的数据

### 职级 `sys_level`（5 条）

| level_name | level_rank | status | remark |
|---|---|---|---|
| 员工 | 1 | 1 | JeecgBoot position_rank=1，基础执行岗 |
| 小组长 | 2 | 1 | JeecgBoot position_rank=2，带领小组完成既定任务 |
| 部门经理 | 3 | 1 | JeecgBoot position_rank=3，部门负责人 |
| 副总经理 | 4 | 1 | JeecgBoot position_rank=4，分管业务条线 |
| 总经理 | 5 | 1 | JeecgBoot 组织架构最高职务，全面负责经营管理 |

### 岗位 `sys_position`（5 条，与职级一一对应）

| post_code | post_name | post_sort | dept_id | 部门 | 说明 |
|---|---|---|---|---|---|
| `general_manager` | 总经理 | 1 | `dept_1` | 总公司 | 全面负责公司经营管理，向董事会汇报 |
| `deputy_general_manager` | 副总经理 | 2 | `dept_1` | 总公司 | 分管研发/测试等业务条线，向总经理汇报 |
| `dept_manager` | 部门经理 | 3 | `dept_1` | 总公司 | 负责本部门目标达成与团队管理，向分管副总汇报 |
| `team_leader` | 小组长 | 4 | `dept_2` | 研发部 | 带领小组完成研发任务，向部门经理汇报 |
| `staff` | 员工 | 5 | `dept_2` | 研发部 | 承担具体研发/测试执行工作 |

主键用可读固定值（`lvl_1`~`lvl_5`、`post_<code>`）而不是 32 位随机串，方便脚本幂等定位，也和 `menu_*` 这套种子数据的风格保持一致。

## 四、怎么用

```bash
# 需要先有 dist（脚本走 Nest 应用上下文拿 DataSource）
npm run build
node scripts/seed-level-post.cjs
```

输出示例（首次执行 / 重复执行）：

```
职级：新增 5 条，更新 0 条
岗位：新增 5 条，更新 5 条
```

幂等规则：

- 职级按 `level_name` 判断（该列有唯一索引 `uk_sys_level_name`）
- 岗位按 `post_code` 判断（唯一索引 `uk_sys_position_code`）
- 已存在则更新 `level_rank`/`post_sort`/`dept_id`/`status`/`remark`/`description` 与 `update_by/update_time`，不会覆盖主键，也不会产生重复行

灌完后两个列表接口立即能查到（数据无缓存）：

- `GET /api/v1/levels` → 按 `level_rank` 降序，顺序是 总经理 > 副总经理 > 部门经理 > 小组长 > 员工
- `GET /api/v1/posts` → 按 `post_sort` 升序，每条带 `dept` 对象（总公司 / 研发部）

## 五、扩展方式

### 加职级

在 `scripts/seed-level-post.cjs` 的 `LEVELS` 数组里追加一项即可，`rank` 保持递增（越大越高）。例如加「技术专家」：

```js
{ name: '技术专家', rank: 6, remark: '专业序列最高级，对标副总经理' }
```

### 加岗位

在 `POSTS` 数组里追加，`code` 必须唯一且用英文/下划线（`post_code` 是唯一索引）：

```js
{ code: 'dev_engineer', name: '研发工程师', sort: 6, dept: 'dept_2', desc: '负责服务端/前端研发' }
```

`dept` 填 `sys_depart.id`；脚本会先校验该部门存在且 `del_flag='0'`，不存在时把 `dept_id` 置空（不会因外键式脏数据中断灌数）。

### 注意

- 岗位的 `dept_id` 只做存在性校验，**不校验部门是否真的是「部门」类型**（jeecg 的 `sys_depart.org_category` 区分公司/部门/岗位，本项目 dept 模块暂未细分）
- 如果后续想把这些岗位派给用户，走 `sys_user_depart` 关联，别直接改 `sys_user`

## 六、踩坑

1. **脚本路径**：`scripts/` 下的脚本用 `require('../dist/app.module')`，如果把脚本临时放在项目根目录，必须改成 `require('./dist/app.module')`，否则 `MODULE_NOT_FOUND`
2. **必须用 `createApplicationContext`**：`NestFactory.create()` 会拉起 HTTP 服务，seed 里用 `createApplicationContext(AppModule, { logger: false })` 拿到上下文后 `app.get(getDataSourceToken('default'))` 即可，跑完记得 `app.close()`，否则进程不退出
3. **rank 方向别搞反**：`sys_level.level_rank` 是「越大越高」，jeecg `position_rank` 的序号也是越大越高（1 员工 → 4 副总经理），直接沿用；如果照搬 jeecg 文档里「数字越小职位越高」那句话去反转，页面上就会倒过来
4. **不要复用 `sys_position` 的 jeecg 原生字段名**：jeecg 原表是 `code/name/post_rank/company_id/sys_org_code`，本项目建表时用的是 `post_code/post_name/post_sort/dept_id`（RuoYi 风格 + 补部门），灌数时按本项目的列名写
