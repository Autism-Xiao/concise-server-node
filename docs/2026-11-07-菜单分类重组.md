# 菜单分类重组：一份平铺菜单拆成 5 个职责分组

日期：2026-11-07
提交：后端 `feat(menu): 菜单重组为 5 个职责分组 + 补齐缺失权限节点`

## 一、为什么要动

重组前 18 个真实页面全铺在两个顶层节点下：

- 系统管理（`menu_1`）：13 个直接子项，其中还夹着「日志管理」这个二级目录
- 运维管理（`menu_38`）：4 个

侧边栏已经要滚动，而且「业务属性完全不同的东西」挤在一起：账号权限（用户/角色/菜单）、基础数据（字典/区划）、资源（文件）、审计（日志）、内容（公告/日历）全是平级兄弟。

## 二、重组后的结构

| 顶层分组 | 页面 | 判定标准（以后新增菜单按这个归） |
| --- | --- | --- |
| 仪表盘 `/dashboard` | 仪表盘 | 单页入口，恒置顶 |
| 系统管理 `/system` | 用户、角色权限、菜单、部门、岗位、职级、租户（7） | 改这里会改变「谁能看到什么」 |
| 数据管理 `/data` | 数据字典、行政区划、文件管理（3） | 被别的模块引用的基础数据与资源 |
| 运维管理 `/ops` | 定时任务、在线用户、服务监控、缓存监控（4） | 看系统当前状态、跑后台批处理 |
| 安全审计 `/audit` | 登录日志、操作日志（2） | 事后追溯「谁在什么时候做了什么」 |
| 协同办公 `/collab` | 通知公告、日历管理（2） | 人与人之间发消息、约时间 |

两个刻意为之的决定：

1. **日志不并进运维。** 运维看的是「现在跑得怎么样」，可清缓存、可重启；审计看的是「过去发生过什么」，只读。现实里这两个权限也常给不同角色（运维工程师 vs 合规/安全）。塞一起会逼审计岗拿运维权限。
2. **租户先留在系统管理，不独立成「平台运营」。** 目前租户少、单人运营，单开一组只有一个子项，反而更碎。等出现套餐/配额/计费/开通审核，再连同租户一起拆出去。

## 四、顺带修的四类数据问题

### 1. 行政区划「看得见点不开」

接口要 `system:region:*` 五个权限码，但菜单节点 `menu_45` 的 `perms` 是 `NULL`：

- 所有登录用户都能看到菜单
- 点进去每个接口 403（只有 admin 靠超管旁路能用）
- 角色权限页根本没有区划按钮可勾，等于永远授不了权

修法：`menu_45.perms` 设成 `system:region:list`，另补 `system:region:add/update/delete/import` 四个按钮节点（`menu_96~99`）。

### 2. 三个权限码有代码、没节点

前端 `hasPermission()` 在控这些按钮：

| 权限码 | 用在哪 | 症状 |
| --- | --- | --- |
| `system:user:reset-password` | 用户列表「重置密码」 | 非 admin 永远看不到按钮 |
| `system:user:restore` | 用户回收站「恢复」 | 同上 |
| `system:watermark:edit` | 设置中心「水印策略」 | 非 admin 打不开水印策略页 |

修法：补 `menu_93`（重置密码）、`menu_94`（恢复用户）、`menu_95`（水印策略）。前两个挂用户管理下，水印策略挂系统管理目录下（它是全局策略，不属于某个账号）。

### 3. 审计员有接口权限、看不到页面

`menu_3`「日志查询」和 `menu_4`「操作日志查看」是挂在「日志管理」目录上的**按钮**，`perms` 与「登录日志」「操作日志」两个子菜单完全重复。

审计员（auditor）角色被授了这两条按钮、却没授任何日志菜单 —— 权限码有了（能调接口），但菜单树里没有日志节点（界面看不到）。

修法：先给 auditor 补 `menu_46`/`menu_47` 的菜单授权，再删掉 `menu_3`/`menu_4` 与「日志管理」目录（`menu_18`），日志两个页面直接挂到「安全审计」下。

### 4. sort_no 是跨组连号

旧值：系统管理 6，子项 7-14 与 22-26；运维 17，子项 18-21。

同级比较其实没错，但像一个被打断的序列，插新菜单极易撞号。改成：顶层 10/20/30/40/50/60，组内 1..n。

## 五、遇到的坑

### 1. `tools:*` 三条按钮不是垃圾，别手贱删

原本判断文件管理下 8 个按钮里有 3 个残留（`tools:upload`、`tools:storage:list`、`tools:storage:delete`）。核实后发现：

- `modules/tools/storage/storage.controller.ts` 和 `modules/tools/upload/upload.controller.ts` 仍是**无条件注册**的（不像其他旧控制器受 `LEGACY_ROUTES_ENABLED` 控制），路由 `/api/upload`、`/api/storage/*` 现在就在跑
- 删掉节点后这两个旧接口就没人能授权了

所以保留。代价是角色权限树里「文件上传」会出现两次（`tools:upload` 与 `system:file:upload`）。要彻底消除，得先把这两个旧控制器也接进 `LEGACY_ROUTES_ENABLED` 开关。

### 2. 新分组不需要给角色补授权

`AuthService.getPermissions()` 里有「祖先链补齐」：

```ts
for (const menu of allMenus) {
  if (menu.menuType === 2 || !allowedIds.has(menu.id)) continue
  let current = menu
  while (current) { keepIds.add(current.id); current = ... }
}
```

角色只要被授了子页面，「数据管理」「安全审计」「协同办公」这些新父级自动出现在菜单树里，不用逐个授权。反过来 `permissions` 权限码只认 `allowedIds`，补齐出来的目录不产出权限码 —— 所以目录节点的 `perms` 必须是 `NULL`，不然会给角色凭空多出权限。

### 3. `is_leaf` 必须归位

`is_leaf` 为 1 的目录，前端会按叶子渲染成不可展开项。第一次写这段更新时用了「相关子查询 + 派生表」：

```sql
-- 错：MySQL 不让派生表引用外层列（没有隐式 LATERAL）
UPDATE sys_permission p SET is_leaf = CASE WHEN EXISTS (
  SELECT 1 FROM (SELECT id, parent_id FROM sys_permission) c WHERE c.parent_id = p.id
) THEN 0 ELSE 1 END
```

改成 `UPDATE ... JOIN (SELECT DISTINCT parent_id ...) c ON p.id = c.parent_id SET p.is_leaf = 0`，先把全部置 1 再把有子级的置 0。

### 4. 菜单树缓存在前端 localStorage，改库不会自动刷新

`GET /v1/auth/permissions` 只在**登录时**调用一次，菜单树写进 localStorage 后不再拉取。所以改完数据库，已登录的浏览器还显示旧结构 —— **要退出重新登录**（刷新页面不够）。

### 5. 权限集合按角色缓存在内存

迁移是在应用进程外跑的，`PermissionCacheService` 里的旧缓存不会被自动失效。所以跑完迁移要重启后端（`npm run restart`），否则 auditor 的权限要等缓存过期才更新。

### 6. 侧边栏压根没读 `icon` 字段

之前图标只从 `PAGE_REGISTRY[url]?.icon` 取，菜单管理里用图标选择器配的 `icon` 存进了库但没人消费 —— 目录节点一律显示成圆点。这次把 `ICON_MAP` 从 `icon-picker.tsx` 导出，`menuIcon(iconName, path)` 按「后端 icon → 登记表 icon → 圆点」降级。

不额外增加体积：`page-registry.ts` 静态引了菜单页，`ICON_MAP` 本来就在包里。

## 六、怎么用 / 怎么扩展

### 新增一个页面并归到某个分组

1. 前端建页面 → 在 `src/config/page-registry.ts` 登记 `path → 组件/标题/图标`
2. 建对应路由文件 `src/routes/_authenticated/**`
3. 后端「菜单管理」新增节点：父级选对应分组，`url` 必须是登记表里的 path，`perms` 填 `模块:页面:list`
4. 需要按钮级权限的，在同页面下加 `menu_type=2` 的子节点
5. 给角色授权：只要授页面节点，父级分组会自动补齐

### 想再拆一个分组

例如「平台运营」：

```sql
INSERT INTO sys_permission (id, parent_id, name, url, menu_type, sort_no, icon, status, is_route, is_leaf, hidden, perms_type, del_flag, rule_flag)
VALUES ('menu_platform', NULL, '平台运营', '/platform', 0, 45, 'Building2', '1', 1, 0, 0, '1', 0, 0);
UPDATE sys_permission SET parent_id = 'menu_platform', sort_no = 1 WHERE id = 'menu_44';
```

排序插在运维（40）与审计（50）之间就写 45。这是数据操作，直接走「菜单管理」界面也行，不必写迁移。

### 回滚

```bash
npx typeorm migration:revert -d dist/shared/database/database.js   # 实际路径见 data-source
```

`down()` 会把 18 个页面挂回原父级与原 sort_no、恢复「日志管理」目录与两条重复按钮、删掉本轮新增的 3 个目录与 7 个按钮。角色授权不回滚（属运行期数据）。
