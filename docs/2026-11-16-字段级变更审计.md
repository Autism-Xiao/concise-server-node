# 字段级变更审计（sys_log_change）

## 这是什么

「操作日志」回答"谁调了哪个接口、耗时多少"；这张表回答"**数据本身变了什么**"——
哪张表的哪条记录、哪个字段、改之前是什么值、改之后是什么值、谁在什么时候改的。

排查场景：「这个客户的电话号码什么时候被谁改坏的？」「用户状态怎么变成禁用了？」——操作日志只知道"调过一次 PUT"，这张表才知道前后的值。

## 核心设计

1. **采集点收敛在 `BaseService.update()`**：十几个业务 Service 继承基类，改数据几乎都走 `super.update()`，在基类里加采集 = 一次接入全站生效。
2. **注册槽而不是依赖注入**：`change-recorder.ts` 是一个纯模块（进程内单例），日志模块启动时把自己注册成 sink。业务基类不依赖任何 Nest 注入器，没注册时是空操作（脚本、单测里 `new Service()` 也不会炸）。
3. **审计失败绝不影响业务**：`emitChanges` / `record` 全程吞异常，写库失败只打 warn。审计挂了顶多少记几条，业务改数据不能被拖死。
4. **敏感字段黑名单先行**：`/passw|salt|secret|token|credential|codehash|privatekey/i` 命中的字段**根本不进采集**，宁可漏记也不能把密码哈希写进权限更宽的审计表。
5. **同值不记、噪音不记**：payload 里没变的字段跳过；`updateTime/updateBy` 这类每次更新必变的自动字段跳过。

## 踩的坑

- **用户表不走 `super.update()`**：用户的更新是事务直写（重绑角色/部门/岗位），基类里的采集够不到。所以在 BaseService 上开了 `auditUpdate(before, patch)` 受保护方法，让这类子类事务提交后手动调。**新增覆盖 update 的 Service 时记得同样处理**。
- **重置/修改密码不产生审计行是故意的**：`updatePasswordOnly` 走 repository 直写不经过采集；即使哪天接上了，`password/salt` 也会被黑名单拦下。密码变更的留痕由操作日志（接口层）负责。
- **查询 DTO 的 endTime 只给 `2026-11-16` 会漏当天**：`new Date('2026-11-16')` 是当天 00:00，前端必须补到 `23:59:59`。
- **分页 total 不能用 `toPagination()`**：它按传入数组长度算 total，而这里分页在库侧做了（`getManyAndCount`），直接 `new Pagination(rows, total, ...)`。
- **值统一成字符串再比较**：Date → ISO、对象 → JSON.stringify、null/undefined → 空串。不统一的话"改成 null"和"改成空串"没法区分，Date 字段每次都比出假 diff。

## 如何扩展

- **让新模块自动接入**：Service 继承 `BaseService` 且更新走 `super.update()` → 什么都不用做；自己写 update → 在写库成功后调 `this.auditUpdate(before, patch)`（before 必须是**更新前**查出的实体）。
- **不想被审计的字段**（如大规模同步写入）：直接用 repository 直写（不经 BaseService），或在 `change-recorder.ts` 的 `NOISY_FIELDS` 加属性名。
- **查询端新增过滤条件**：`change-log.service.ts` 的 `list()` 加 `andWhere` + `log.v1.controller.ts` 的 `QueryChangeLogDto` 加字段（记得 `@MaxLength`）。
- 表已经 500 字截断单值，超大文本（富文本正文）只看到前 500 字 + 省略号——够定位"改了"，全文看业务表。
