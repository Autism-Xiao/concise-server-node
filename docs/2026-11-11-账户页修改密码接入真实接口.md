# 系统设置-账户：修改密码接入真实接口（前端接通）

> 仓库：`concise-admin`（提交 `b843b27`）
> 时间：2026-11-11
> 后端：无改动 —— `PUT /api/v1/auth/password` 早已存在（auth.v1.controller 92 行），本轮只把账户页从 mock 接上

## 背景

系统设置 → 账户页的「修改密码」表单是 mock（提交只 toast「密码已更新（mock）」）。后端其实有完整的自助改密接口：`AuthService.changePassword`（验旧密码 → 写新密码 → 清强制改密/过期标记 → 踢其他端登录态、保留当前会话），强制改密弹窗（`forced-change-password-dialog`）已经在用同一个封装 `changeMyPassword` —— 账户页是唯一没接上的入口。

## 改动文件

| 文件 | 类型 | 说明 |
|---|---|---|
| `src/features/settings/account/index.tsx` | 修改 | `handleSubmit` 改为调用 `changeMyPassword`（`PUT /v1/auth/password`）；提交中禁用按钮；错误直接展示后端 message；成功 toast 提示「其他设备已自动退出登录」 |

前端接口层零改动：`users/api.ts` 290 行的 `changeMyPassword` 是现成的，强制改密弹窗与账户页共用。

## 行为链路

1. 前置校验（前端，省一次往返）：8~32 位、含字母和数字、两次一致、不与当前密码相同 —— **与后端 `ChangePasswordDto` 完全对齐**
2. `PUT /v1/auth/password`（Bearer）
3. 后端：`verifyPassword`（Argon2id / jeecg 历史格式就地升级）→ `updatePasswordOnly` → `clearPasswordFlags` → `onlineService.kickUser(userId, { keepToken })`
4. 失败码：`2104` 原密码不正确 / `1001` DTO 校验（「新密码至少 8 位」等）/ 账号不存在走 `UNAUTHORIZED`

## 实测（本地 3459 实例，非破坏性）

| 场景 | 结果 |
|---|---|
| 新密码 `a1`（太短） | HTTP 400 · code=1001 · 「新密码至少 8 位」 |
| 原密码 `definitely-wrong-1` | HTTP 400 · code=2104 · 「原密码不正确」 |

成功路径未在本轮实测（会真的改 admin 密码），但该路径由强制改密弹窗复用同一封装，已在既有功能中验证过。验证脚本用的是「滑块验证码 → ticket → 登录」全流程（复用 smoke-captcha 的 Redis 取答案方式），验完即删。

## 坑

1. **本地实例开了滑块验证码**（`CAPTCHA_ENABLED=true`）：裸调登录接口只会拿到 `417 请先完成滑块验证`，想脚本化登录必须先 `captcha → Redis 读答案 → verify → ticket`；答案在 `captcha:<captchaId>` 的 JSON `.x` 里。
2. **不要拿 admin 试成功路径**：改密会踢掉其他端登录态，改回失败就把管理员锁在门外了。要测成功路径就建临时用户。
3. **前端校验必须和 DTO 对齐**：后端是 `@Matches(/[A-Za-z]/)` + `@Matches(/\d/)`，前端少一个「含数字」的判断就会出现「前端放行、后端 1001」的割裂体验。
4. **routeTree.gen.ts 会被构建自动改动**：提交前注意别把无关的生成文件混进功能提交（本轮构建产生，一并提交了，无碍）。

## 怎么扩展

- **改密后强制重新登录**：现在保留当前会话（keepToken）；想全下线就把 `keepToken` 去掉，前端 catch 401 自动跳登录页即可，无需改账户页。
- **密码强度可视化**：加 zxcvbn 打分条，别动 DTO 规则（规则改了要同步两处：前端 account/index.tsx 与后端 change-password.dto.ts）。
- **两步验证卡片**：还是 mock，接通时参照本页模式 —— 接口在 `auth.v1.controller` 挂 `@Post('2fa/…')`，前端复用 `changeMyPassword` 的调用样式。
