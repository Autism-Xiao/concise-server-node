# 代理端口错配与「Unexpected end of JSON input」可读化

日期：2026-11-07
涉及仓库：`concise-admin`（前端，主要改动）、`concise-server-node`（仅文档）

## 一、现象

本地打开 `http://localhost:5174`（concise-admin 的 dev server）后，所有接口都失败，页面提示：

```
Failed to execute 'json' on 'Response': Unexpected end of JSON input
```

用户疑问：后台连不上，不该返回 500 服务器错误吗？为什么是这句 JSON 解析错误？

## 二、根因（两处叠加）

### 1. vite 代理目标端口与后端实际端口不一致

`concise-admin/vite.config.ts` 里：

```ts
const BACKEND_URL = process.env.BACKEND_URL ?? 'http://127.0.0.1:3000'
```

默认指向 **3000**，而 `concise-server-node/.env` 里 `PORT=3459`。3000 上没有任何服务，代理转发失败。

实测代理层返回：

```
HTTP/1.1 502 Bad Gateway
Content-Type: text/plain; charset=utf-8

upstream connect failed: 由于目标计算机积极拒绝，无法连接。 (os error 10061)
```

### 2. 前端无条件 `res.json()`

`src/lib/http.ts` 的 `getApiResult` 直接：

```ts
const json = (await res.json()) as ApiEnvelope<T>
```

代理返回的是 `text/plain`（甚至空 body），`.json()` 必然抛解析异常，把真正的「后端连不上」掩盖成一句无意义的 JSON 报错。

## 三、为什么不是 500

**请求根本没到后端**。代理在转发阶段就失败了，NestJS 没有参与，自然不会有 `500 + JSON`。

后端本身的异常兜底是完整的，`src/common/filters/any-exception.filter.ts` 分三类处理：

| 异常类型 | HTTP 状态 | 响应体 |
|---|---|---|
| `BizException` | 异常自带（默认 200） | `{ code: 业务码, message, result: null, success: false, timestamp }` |
| `HttpException` | 保留原状态（400/401/403/404/429…） | 同上，code 映射业务码 |
| 未知异常 | 500 | 同上，`code=INTERNAL_ERROR`，message 固定「服务器内部错误」 |

所以只要请求进到后端，任何异常都会是 JSON。看到「JSON 解析错误」，第一反应应该是**请求没到后端**：查代理端口、查后端进程。

## 四、改动清单

| 文件 | 类型 | 说明 |
|---|---|---|
| `concise-admin/vite.config.ts` | 修改 | `BACKEND_URL` 默认端口从 3000 改为 3459（与后端 `.env` 的 `PORT` 对齐），新增 `BACKEND_PORT` 只改端口的覆盖方式，注释写明「写错不会报错，只会让代理 502」 |
| `concise-admin/src/lib/http.ts` | 修改 | 新增导出函数 `parseJsonBody(res, path)`：先读 `text()`，再按「空响应 / 非 JSON / 502·503·504 / JSON 解析失败」分别给中文可读提示；`getApiResult` 与 `getJson` 全部改用它，不再裸 `.json()` |
| `concise-admin/src/lib/download.ts` | 修改 | 错误分支改为先 `res.text()` 再尝试 `JSON.parse`；502/503/504 单独提示「后端服务不可用」，并把代理原文带出来 |
| `concise-admin/tests/http-unauthorized.test.cjs` | 修改 | mock Response 补齐 `headers.get` / `text()`；新增两个回归用例：502 + 非 JSON 文本、502 + 空 body |

### 报错文案对照

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 代理连不上后端（502 + text） | `Unexpected end of JSON input` | `后端服务不可用（HTTP 502）：upstream connect failed: ... 请检查后端是否启动、代理端口是否与后端 PORT 一致` |
| 网关返回空 body | `Unexpected end of JSON input` | `没有收到后端响应（HTTP 502）：/backend-api/v1/users。请确认后端服务已启动，且 vite 代理 BACKEND_URL 指向正确端口` |
| 后端返回非 JSON（含 HTML 错误页） | 解析异常 | `后端返回了非 JSON 响应（HTTP 200）：<前 160 字>` |
| 后端正常业务失败 | 原文案 | 不变（后端 message 优先） |

## 五、验证方式

前端 dev server 会监听 `vite.config.ts` 变更并自动重启，无需手动重启。验证走 `[::1]:5174`（vite 只监听 IPv6 回环）：

| 用例 | 结果 |
|---|---|
| `GET /backend-api/v1/auth/captcha` | 200，返回 `captchaId` + SVG |
| `POST /backend-api/v1/auth/login`（不带验证码） | 200，`code=417`「请先完成滑块验证」 |
| `GET /backend-api/v1/users`（无 token） | 401，`code=1003`「未授权，请先登录」 |
| `GET /` | 200，HTML 正常 |

后端 `PORT=3459`、`CAPTCHA_ENABLED=true`，验证码链路正常。

## 六、踩坑记录

1. **curl 会被系统代理劫持**：本机 `http_proxy=http://127.0.0.1:61096`，直接 `curl 127.0.0.1:5174` 会走代理并返回代理自己的 502（`upstream connect failed`），看起来像应用错误。本地探活一律加 `--noproxy '*'`。
2. **vite 只监听 IPv6 回环**：`[::1]:5174`，用 `127.0.0.1:5174` 在 IPv4 上连不上，容易误判成服务挂了。
3. **`Start-Process` 起后端会失败**：Windows 环境同时存在 `https_proxy` 与 `HTTPS_PROXY`（大小写重复），PowerShell 构造环境字典时报「已添加项」。需要先 `Remove-Item Env:https_proxy` 再启动；且 `Start-Process` 起的进程会随会话结束被回收，长期服务应改用后台任务方式启动。
4. **代理端口写错不会报错**：vite 不会校验 target 可达性，配置错了只会在运行时表现为 502。改完 `BACKEND_URL` 一定要实际请求一次接口确认。

## 七、后续可扩展点

- 若前端要部署到非本机后端，只需设环境变量 `BACKEND_URL=http://<ip>:3459`，不用改代码。
- 生产环境由 Nginx/网关转发时，同样建议保留「非 JSON 响应」的可读提示，避免网关错误页被当成业务错误。
- 可考虑给 `parseJsonBody` 加一个 `context` 参数（模块名），把报错定位到具体页面。
