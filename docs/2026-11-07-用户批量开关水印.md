# 用户管理：批量开关水印

日期：2026-11-07
涉及仓库：`concise-server-node`（后端）、`concise-admin`（前端）

## 一、需求

用户管理列表里勾选多个账号，一次性给它们开关水印。此前只有「单行 → 水印设置」弹窗，几十号人要开就得点几十次。

## 二、做了什么

一句话：新增 `POST /api/v1/users/batch-watermark`，前端在用户列表的批量操作区加「批量水印（N）」按钮 + 一个三档动作弹窗。

### 后端

| 文件 | 类型 | 说明 |
| --- | --- | --- |
| `src/modules/system/watermark/dto/batch-user-watermark.dto.ts` | 新增 | `{ ids: string[], mode: 'on' \| 'off' \| 'inherit' }`；ids 上限复用 `BATCH_DELETE_MAX`（200） |
| `src/modules/system/watermark/watermark.service.ts` | 修改 | 注入 `UserService`；新增 `batchUpdateForUsers()` 与结果类型 `BatchWatermarkOutcome` |
| `src/modules/system/watermark/watermark.controller.ts` | 修改 | 新增 `POST users/batch-watermark`，`@Perms('system:user:update')` + `@OperLog('页面水印')` |
| `src/modules/user/user.service.ts` | 修改 | 新增 `findExistingBriefs(ids)`：批量确认用户存在（过滤软删），只回 `id/username` |

### 三档动作怎么落到 `sys_user_watermark`

| mode | enabled | enforced | 效果 |
| --- | --- | --- | --- |
| `on` 强制开启 | 1 | 1 | 全局策略关掉也照样显示；用户自己关不掉 |
| `off` 强制关闭 | 0 | 2 | 全局强制开启也不显示；用户自己开不了 |
| `inherit` 恢复跟随全局 | null | 0 | 并把 `content` / `density` 一起清空，整行回到「跟随全局」 |

**为什么不开放 `enabled` + `enforced` 任意组合**：批量场景下「enabled=1 但 enforced=2」这类矛盾组合没人真的想要，给三个成品档位比给两个下拉框更难配错。单用户的精细组合继续走 `PUT /v1/users/:id/watermark`（弹窗未改动）。

交互细节：

- 按钮只在**有勾选**时出现，文案带数量，和「批量启用/停用/批量分配角色」并排
- 弹窗每次打开都重置为「开启水印」，避免沿用上次选的「关闭」把人不小心关掉
- 选「关闭水印」时提交按钮变红（destructive）+ 下方红字提醒「截图不再带身份信息」
- 选「恢复跟随全局」时提示自定义文案/密度会被一并清除、不可撤销
- 提交成功：`toast` 说明更新条数并提示「用户刷新页面后生效」；随后清空勾选、刷新列表（水印列立刻变成「已关闭（强制关）」）
- 不存在/已删除的用户由后端跳过并回传，前端逐条 `toast.warning`

## 三、接口

```http
POST /api/v1/users/batch-watermark
Authorization: Bearer <token>      # 需要 system:user:update
Content-Type: application/json

{ "ids": ["1714471285016895490", "3d464b4ea0d2491aab8a7bde74c57e95"], "mode": "off" }
```

```json
{
  "code": 200,
  "result": {
    "mode": "off",
    "updated": 2,
    "skipped": [{ "id": "deadbeef...", "reason": "用户不存在或已删除" }]
  }
}
```

约定与项目既有批量接口一致：**一次请求、逐条结算**，单条失败不阻断其他条；`ids` 去重后为空或超 200 → 400。

## 四、验证

后端（`PORT=3461 CAPTCHA_ENABLED=false` 实例，自签 admin token）：

| 用例 | 结果 |
| --- | --- |
| `mode=on`（含 1 个不存在的 id） | `updated=2`，`skipped` 回传该 id；两人 `enforced=1`、`effective=true` |
| `mode=off` | 两人 `enabled=0/enforced=2`、`effective=false` |
| `mode=inherit` | 两人 `enabled=null/enforced=0`、`effective=true`（全局开着） |
| `ids=[]` | 400 `请选择要操作的用户` |
| `mode=xxx` | 400 `mode 只能是 on / off / inherit` |
| 无 token | 401 `1003` |

前端（headless Chrome + CDP 在 5180 实跑）：勾选 ceshi/zhangsan → 按钮显示「批量水印（2）」→ 打开弹窗（标题「批量设置水印（2 个用户）」「已开启 2 人 / 已关闭 0 人」）→ 选「关闭水印（强制关闭）」→ 提交。抓到请求体 `{"ids":["1714…","3d46…"],"mode":"off"}`、响应 201、toast「已为 2 个用户关闭水印，用户刷新页面后生效」、列表两行变成「已关闭（强制关）」、弹窗关闭。测完已把两个账号的水印配置还原成测试前的值。

## 五、坑与注意

1. **`inherit` 是「整行清空」**：只把 `enabled` 置 null 会留下「跟全局但文案还是自定义的」半截状态，所以 `content`/`density` 一并清。这个动作不可撤销原值，弹窗里已明确提示。
2. **批量不复用单条接口循环调用**：N 个 id 就是 N 次 HTTP + N 条操作日志 + 无事务边界，中间失败会留下半开半关。现在是 1 次请求 + 1 个事务 + 1 条日志。
3. `batchUpdateForUsers` 走 `normalizeBatchIds()`，因此空数组/超上限的 400 文案与批量删除、批量启停完全一致。
4. `UserService.findExistingBriefs()` 用默认仓库查询（与 `batchUpdateStatus` 同款写法），不走 `BaseService` 的租户自动过滤——批量勾选的行本身就来自当前列表，用户看得见的才勾得到。
5. 事务里必须 `manager.getRepository()`，用默认连接看不到未提交数据（项目老坑）。
6. **改完别人的水印，对方要刷新页面才看到**：水印是进入后台时拉取一次，没有推送。若要即时生效，可接 WebSocket（`ReminderScheduler.emitter` 那种模式）。
7. 前端本地验证时 **5173 可能被别的项目占用**，先 `curl -s http://127.0.0.1:5173/ | grep title` 确认，别对着别人的站调试。

## 六、后续可扩展

- 水印列支持按状态筛选（已开启/已关闭/强制关）+ 头部「全选当前筛选结果」批量设置（现在只能勾当前页可见行）
- 批量弹窗加「统一自定义文案」（对应 `content`），目前只动开关，不动文案
- 若加上「批量水印」按钮权限点（如 `system:user:watermark`），需同步菜单管理的按钮节点；现在复用 `system:user:update`，与单行水印弹窗门槛一致
