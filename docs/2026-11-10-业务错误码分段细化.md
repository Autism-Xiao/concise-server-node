# 业务错误码分段细化 + 前端按码分支

> 起因：审前后端 code 定义时发现四个真问题（前端靠 `message.includes('已锁定')` 判锁定、`code === 401` 是死分支、三个验证码死码还在 Swagger 里宣传、未知 4xx 被伪装成 1006「内部错误」）。
> 顺着往下做，把「code 体系只在后端闭环、前端消费端没接上」这件事一次解决，并按域给码表分段。

## 二、每个东西是干什么的

### 1. 码表分段（一眼看出新码还是老码）

```
0                 成功
41x               验证码（412 位置错误 / 413 过期 / 417 参数缺失）
1001~1009         通用与账号（冻结段：参数/不存在/未授权/禁止/业务失败/内部错误/登录失败/停用/锁定）
429 / 503         HTTP 语义直接沿用
21xx              认证与账号（refresh / SSO / 密码过期 / 原密码错）
31xx              权限与角色（内置角色保护 / 编码冲突 / 菜单 ID）
41xx              组织架构（父级不存在 / 防环 / 有子部门 / 有用户）
51xx              字典与公告（编码冲突 / value 冲突 / 状态冲突 / 有字典项）
61xx              文件与导入（上传类型 / 签名不符 / 表头不符 / 空数据 / CSV 编码 / 文件丢失）
71xx              协作（日程越权 / 接收人 / 任务状态机）
81xx              多租户（编码冲突 / 角色越界 / 无 admin 模板）
91xx              运维（cron / 会话）
```

**为什么冻结旧值**：1007~1009 已被前端判断、冒烟断言、Swagger 文档、jeecg 惯例四处引用，改值是纯亏不赚。新码用四位数，与三位老码在日志里天然可辨。

### 2. 一码一消费者的筛选标准

新增前必须能回答「谁在用它分支」：

| 场景 | 编不编 | 为什么 |
| --- | --- | --- |
| 账号锁定 1009 | 已有 | 登录页要禁用提交按钮 —— UI 分支 |
| 导入表头不匹配 6103 | 新增 | 导入弹窗要弹「下载模板」—— UI 分支 |
| 文件签名不符 6102 | 新增 | 安全事件，监控单独聚合告警 |
| 「缺用户名列」vs「缺角色编码列」 | **不细分** | 都是 6103，message 已能区分，前端行为完全一样 |
| 跨租户角色分配 8102 | 新增 | 安全边界（防提权），值得单独监控 |

没写消费方的码 = 下一批死码（参考被删的 414/415/416）。

### 3. 过滤器兜底规则

```
BizException        → 用枚举 code，HTTP 状态由异常自身决定
已知 HttpException  → 查映射表（1002/1003/1004/1001…）
未映射的 4xx        → code = HTTP status 本身（409 就是 409）
未映射的 5xx        → code = 1006 INTERNAL_ERROR
```

原来是「未知状态一律 1006」——HTTP 说客户端冲突、body 说服务器内部错误，自相矛盾。

### 4. 前端消费闭环

`ApiError` 带上 `code` 之后，调用方终于可以按码分支：

```ts
// 之前：文案一改就静默失效
setLockedOut(message.includes('已锁定'))

// 现在：按码分支，文案随便改
setLockedOut(isApiError(err) ? err.code === 1009 : message.includes('已锁定'))
```

## 三、遇到的坑

### 坑 1：`json.code === 401` 是死分支

`http.ts` 里判断 body 的 `code === 401` 来踢登录，但后端 401 时 body code 是 **1003（映射表）或 1007（登录失败）**，永远不等于 401。这个分支是从 jeecg 时代抄来的双保险，实际起作用的只有 `res.status === 401`。
死代码本身无害，**有害的是它暗示「401 会出现在 code 里」这个错误心智模型**，后来者会照着写更多错误判断。已删。

### 坑 2：414/415/416 是短信验证码时代的遗产

- 415「验证码已使用」——现在由 413「过期」覆盖（Redis `GET`+`DEL` 原子消费，拿不到就是过期）
- 416「发送过于频繁」——滑块验证码不发送，限流走全局 429

grep 确认全项目零使用，但 Swagger 描述还在写 415，会误导后来者。已从枚举与文档里彻底删除。

### 坑 3：`smoke-file.mjs` 的清理被管道截断，残留卡住下一次运行

现象：跑 `smoke-file` 报「移动到根目录」失败，重跑一次又通过，再跑又失败。

排查链：
1. 断言只写 `check('移动到根目录', moved.json?.result?.parentId === 0)`，失败时**不打印原因** —— 先补上诊断，才看到是 `1001 当前目录下已存在「改名后.md」`
2. 根目录确实有残留文件（上一次运行把文件 move 到根后，进程被中途杀掉，结尾的 `purge` 没执行）
3. 为什么会中途被杀：**命令接了 `| head -12`，管道读满后 node 收到 SIGPIPE 提前退出** —— 这个坑在验证码那轮已经踩过一次（启动服务接 `| head` 导致子进程被杀）
4. 修法：脚本开跑前先按冒烟专用命名（`冒烟文件夹-*` / `改名后.md` / `中文报告.txt`）清根目录残留

### 坑 4：`/v1/files/purge` 的 `ids` 必须是字符串数组

前置清理第一版传 `it.id`（number），purge 返回 `1001 每个 id 必须是字符串`，**脚本只打印「删掉 N 项」没检查 code，看起来像成功但什么都没删**，于是「残留清了还是撞同名」又绕了一圈。
修法：`map(it => String(it.id))`，并且失败时打印 code + message。

> 这个 DTO 校验风格与其它接口（`@Type(() => Number)` 接受数字）不一致，但属既有约定，本轮不动。

### 坑 5：替换 throw 点时容易留下未使用的 import

`upload.controller.ts` / `upload.service.ts` / `online.service.ts` / `sso.v1.controller.ts` 换掉 `BadRequestException`、`NotFoundException` 后，import 还在，`npx eslint --max-warnings=0` 逐个报 `no-unused-vars`。已清理。

## 四、怎么扩展 / 使用

### 新增一个业务码

1. 先回答「谁在用这个码分支」（前端 UI / 监控聚合 / 重试策略），答不出就别加，用 message 区分
2. 在对应域段里挑一个未占用的序号（如 41xx 已用到 4104，下一个 4105）
3. 注释里写清：**码值 + 一句话语义 + 消费方**
4. 用 `BizException` 抛出：

```ts
throw new BizException(BizErrorCode.DEPT_HAS_USERS, '该部门下存在用户，无法删除')
```

5. 需要非 200 的 HTTP 状态时传第三参：`new BizException(code, msg, HttpStatus.CONFLICT)`

### 前端按码分支

```ts
import { isApiError } from '@/lib/api-error'

try {
  await doSomething()
} catch (err) {
  if (isApiError(err) && err.code === BizCode.IMPORT_HEADER_MISMATCH) {
    showDownloadTemplateButton()   // 6103：表头不对，引导下载模板
  } else {
    toast.error(err instanceof Error ? err.message : '操作失败')
  }
}
```

**顺序原则**：能按 code 分支就别解析 message。message 是给人看的，随时可能改文案；code 是给程序用的契约。

### 保持旧码不变

`1001~1009`、`41x`、`429`、`503` 是冻结段，**只增不改**。若某个旧码语义需要更细，新增一个码，旧码保留（可能还有外部系统在依赖）。
