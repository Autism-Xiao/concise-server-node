# 租户默认角色模板：建租户就自带一套能用的角色

> 上一轮多租户隔离落地后遗留的问题：**新建的租户是空壳**。
> 菜单（`sys_permission`）是平台共享的，角色（`sys_role`）是租户级的，
> 只插一行 `sys_tenant` 的话，租户里一个角色都没有，管理员进去侧边栏空白、每个按钮 403。

## 二、每个东西是干什么的

### 1. 三套默认角色（`tenant-role-template.ts`）

| 编码 | 名称 | 权限档位 | 内置 |
| --- | --- | --- | --- |
| `admin` | 管理员 | `all`：全部 78 个租户级菜单节点 | 是（`is_builtin=1`） |
| `editor` | 编辑者 | `write`：除 `delete / batch-delete / clean / reset-password / restore` 外全给 | 否 |
| `viewer` | 访客 | `read`：仅 `list / query / detail / export / download` | 否 |

判定规则只有一条：**看权限码后缀，不看菜单类型**。

- 目录/页面节点通常 `perms` 为空，一律授予 —— 它们只决定页面可见性，接口校验落在按钮节点上；
- 有 `perms` 的才按后缀区分读写；
- 两者都是**白名单**：将来新增一个 `:approve` 这类权限码，默认只进 `admin`，不会误授权给编辑者。

`admin` 是内置角色，享受既有保护：不可删除、不可停用、编码不可改、不允许走 `RoleService.assignMenus` 改授权。

### 2. 初始化服务（`tenant-provision.service.ts`）

四个入口，都是幂等的（角色按 `(tenant_id, role_code)` 查，授权按差集补）：

| 方法 | 用途 |
| --- | --- |
| `provisionIn(manager, tenantId, operator?, menus?)` | 在**调用方事务内**执行，供 `TenantService.create()` 用 |
| `provision(tenantId, operator?)` | 自己开事务，供接口用 |
| `provisionAll(operator?)` | 逐租户一个事务，单个失败不影响整批 |

返回结构统一为 `{ tenantId, roles: [{ roleCode, roleId, created, added, total }] }`：
`created` 表示本次新建了角色，`added` 是本次新增的授权条数，重复执行时都是 0 / false —— 前端据此提示「已是最新」。

**为什么不复用 `RoleService.assignMenus`**：它见到 `is_builtin=1` 直接抛错（内置角色由平台整体掌控），
而建租户恰恰要给内置 `admin` 写初始授权。所以这里直接操作 `sys_role_permission`，
用 `INSERT IGNORE` 兜住并发重复插入。

### 3. 两个接口

| 接口 | 权限 | 场景 |
| --- | --- | --- |
| `POST /api/v1/tenants/:id/provision` | `system:tenant:edit` | 单个空壳租户补建 |
| `POST /api/v1/tenants/provision-all` | `system:tenant:edit` | 平台新增租户级菜单后，一次把所有租户补齐 |

`:id/provision` 会先 `findOne(id)` 确认租户存在（软删的也拦住），避免往已删租户里插角色。

## 三、遇到的坑

1. **统一响应字段是 `result` 不是 `data`**
   冒烟脚本按记忆里的 `{code, data, message}` 取 token，全部拿到 `undefined`，连锁导致后续 11 项误判失败。
   实际是 `{ code, message, result, success, timestamp }`（见 `transform.interceptor.ts`）。

2. **列表接口返回 `Pagination` 不是数组**
   `GET /v1/roles` 走 `toPagination()`，`Array.isArray(result)` 恒为 false。
   写成 `Array.isArray(payload) ? payload : (payload?.records ?? [])` 才两种形态都兼容。

3. **`assignMenus` 的内置角色闸门会把初始化卡死**
   见上。这是**有意**的设计（防止租户自己改内置角色授权），所以初始化绕开业务服务直接写关联表。

4. **平台级菜单不能进租户角色**
   即使权限码拿不到，关联表里出现 `scope='platform'` 的节点也会让授权界面显示「已勾选」而实际 403。
   模板只取 `scope='tenant'`，`RoleService.assignMenus` 里也有同样的拦截。

5. **`getMenuIds()` 对内置角色返回了 platform 菜单**
   内置角色原本返回「全部未删除菜单」，租户视角下会回显平台级的租户管理/菜单管理，
   看起来能改、点进去 403。改成非平台管理员时过滤 `scope='platform'`。

6. **默认角色不会自动跟随新菜单**
   权限是**落库**的（不是每次动态算全量），所以平台新增租户级菜单后，各租户 `admin` 不会自动获得。
   这是刻意的取舍：落库才能在角色授权界面看到明细、可审计。
   代价是新菜单上线后要调一次 `provision-all`（前端页头「同步全部角色」）。

7. **前端宽表：加一个图标按钮就把操作列挤出 1280 视口**
   实测（无头 Chrome + CDP，`table-container` 的 `scrollWidth - clientWidth`）：

   | 视口 | 改动前 | 隐藏 ID/备注后 | 合并联系人/电话后 |
   | --- | --- | --- | --- |
   | 1440 | 0 | 0 | 0 |
   | 1366 | 0 | 0 | 0 |
   | 1280 | 内滚 31px，操作列不可见 | 内滚 31px | **0，操作列完整可见** |

   根因是「联系人」「联系电话」两列各吃一次单元格内边距。合并成一列（姓名 + 下方电话小字）后正好归零。

## 四、怎么扩展 / 使用

### 加一套新的默认角色

在 `TENANT_ROLE_TEMPLATES` 里追加一项：

```ts
{
  roleCode: 'auditor',
  roleName: '审计员',
  description: '只看日志与审计记录',
  dataScope: 1,
  isBuiltin: 0,
  level: 'read'   // 或自定义 level，并在 acceptsByLevel 里加分支
}
```

已有的租户不会自动获得这个新角色 —— 调一次 `POST /v1/tenants/provision-all` 即可（幂等）。

### 调整「编辑者能做什么」

改 `tenant-role-template.ts` 的 `DANGEROUS_SUFFIXES`。注意这是**黑名单**语义，
新增的权限码如果不加进去，编辑者就会自动获得；只想给管理员的权限，请改造成白名单判断。

### 新租户上线后的例行检查

```powershell
# 1. 看某租户现在有哪些角色、各自多少授权
node scripts/smoke-tenant-provision.mjs   # 会自建临时租户验证全链路并清理

# 2. 平台新增了菜单，想确认是否已同步
#    调一次 provision-all，返回值里的 addedGrants = 0 就说明已是最新
```

### 手动验证租户管理员是否真的能用

1. 平台管理员 → 租户管理 → 给目标租户分配一个用户；
2. 用户管理 → 给该用户绑定该租户的 `admin` 角色；
3. 用该账号登录，顶栏切到该租户，侧边栏应出现仪表盘/系统管理/数据管理/安全审计/协同办公，
   且不出现「租户管理」「菜单管理」「运维管理」。

## 六、验证

```
$ node scripts/smoke-tenant-provision.mjs
结果：27 通过 / 0 失败
```

覆盖：自动建三角色、`isBuiltin` 标记、admin 授权数=菜单总数、viewer<editor<admin、
平台级菜单零混入、viewer 无删除类权限、重复初始化幂等、新增菜单后只补 admin/editor、
租户管理员登录后菜单树非空、按钮权限含 `system:user:list`、不含 `system:tenant:list`。
