## 验证方式：导入临时库逐表比对行数

只看文件大小不够（mysqldump 中途报错也可能留下一个「差不多大」的残文件）。本轮按老规矩实测导入：

```bash
# 1) 建临时库
mysql -h127.0.0.1 -uroot -e "DROP DATABASE IF EXISTS concise_server_verify_20261115;
  CREATE DATABASE concise_server_verify_20261115 COLLATE utf8mb4_unicode_ci;"

# 2) 导入
mysql -h127.0.0.1 -uroot --default-character-set=utf8mb4 \
  concise_server_verify_20261115 < sql/concise_server_full_2026-11-15.sql

# 3) 逐表 COUNT(*) 比对（脚本见下），4) 删库
mysql -h127.0.0.1 -uroot -e "DROP DATABASE concise_server_verify_20261115;"
```

比对结果：**33/33 张表行数一致，不一致 0 张；`migrations` 55 vs 55。**

临时库用完立刻删掉（`concise_server_verify_20261115` 现已不存在），避免有人误连到一份旧数据上调试。

## 踩的坑

- **前端工作区看着干净不代表两个仓库都干净**：前端确实没改动，但后端还挂着一个 `src/modules/biz_order/dto/biz_order.dto.ts` 的多余空行（生成器 `--overwrite` 重写文件后又被编辑器补了一个换行）。这类噪声要 `git checkout -- <file>` 还原，别混进提交里污染 blame。
- **`.workbuddy/memory/` 是跟踪的**（历史 daily log 都在库里），所以新日志必须提交；但它同时又容易忘——`git status` 里一直是 `??` 状态挂了三天。
- **快照里的新表要能对上代码**：`customer` 表在库里但容易被认为是「测试残留」。判据是看 `src/modules/customer` 是否存在 + `migrations` 里有没有对应 `GenCustomer` 记录——两者都在，就是正式产物，快照必须保留。
- **`DROP DATABASE` 前确认库名带 `verify` 后缀**：这条命令打错一个字母就是生产数据没了。本轮所有验证库统一命名 `concise_server_verify_<日期>`，跑完立刻删。
- **密码不进命令行**：`dump-sql.mjs` 已有 `MYSQL_PWD` 机制，手工跑 `mysql` 时也照做（`export MYSQL_PWD=...` + `MSYS_NO_PATHCONV=1`），否则 Git Bash 会把 `/c/Program Files/...` 当路径转换掉。

## 如何扩展

- **定时备份**：`dump-sql.mjs` 目前是手工执行。要自动化就套一层计划任务（Windows 任务计划 / cron），导出到仓库外的目录（`sql/` 在仓库里，天天提交会把 git 撑爆），只把「里程碑级」快照提交入库。
- **只导结构**：`node scripts/dump-sql.mjs --schema-only` → `sql/concise_server_schema_YYYY-MM-DD.sql`，用于对外发布「空库模板」。
- **上传文件备份没做**：`sys_file` / `tool_storage` 里的记录指向 `FILE_STORAGE_DIR` 下的物理文件（内容寻址、不可变），SQL 快照**不含这些文件本体**。恢复到新环境后记录在、文件不在，下载会 404。真要做完整备份得再加一步 `rsync`/`robocopy` 存储目录。
- **旧快照清理**：`sql/` 现在有 4 份共 30 MB。保留最新 + 最近一份历史即可，更早的从 git 历史取。
