# 冒烟部门清理脚本修正（正常态 smoke_ 父/子部门）

## 日期
2026-11-19

## 类型
修复（清理脚本）

## 背景
用户指出 `smoke_父部门_mwavtxnb` 等冒烟部门还在库里没被清掉。排查发现是 `scripts/cleanup-smoke-data.mjs` 的部门清理规则只删 `del_flag = 1` 的软删部门，而冒烟脚本建的父/子部门是 `del_flag = 0` 的正常态，因此全部漏掉（与上次隔离测试租户漏清同类问题）。

## 涉及数据
| 内容 | 行数 | 说明 |
| --- | --- | --- |
| smoke_ 父部门 | 5 | 5 组冒烟各建 1 个父部门（tenant_id=0） |
| smoke_ 子部门 | 5 | 挂在对应父部门下 |
| 合计 | 10 | 全部 `del_flag=0` 正常态，无任何用户/业务表真实关联 |

后缀：`mwavtxnb` / `mwavvu16` / `mwawbbf6` / `mwm1nuv3` / `mwn452a1`。

## 文件清单
| 文件 | 类型 | 说明 |
| --- | --- | --- |
| `scripts/cleanup-smoke-data.mjs` | 修改 | 新增 `SMOKE_DEPART_PREFIXES`/`departWhere`/`DEPART_PARAMS`，部门清理从「只删软删」改为「名字命中 smoke_ 前缀 或 软删」；在删部门前先清 `sys_user_depart` 按 `dep_id` 的关联（防止将来有账号挂在冒烟部门上留孤儿行） |

## 关键改动
```js
const SMOKE_DEPART_PREFIXES = ['smoke_']
const departWhere = likeClause('depart_name', SMOKE_DEPART_PREFIXES) + ' OR del_flag = 1'
const DEPART_PARAMS = SMOKE_DEPART_PREFIXES.map(p => `${p}%`)

// STEPS（按依赖顺序，先子后父）
{ name: '冒烟部门的账号关联', table: 'sys_user_depart',
  where: `dep_id IN (SELECT id FROM sys_depart WHERE ${departWhere})`, params: DEPART_PARAMS },
{ name: '冒烟部门（含正常态 smoke_ 父/子部门与软删测试部门）',
  table: 'sys_depart', where: departWhere, params: DEPART_PARAMS }
```

## 踩的坑
1. **`likeClause` 是 const 箭头函数，定义在常量区之后**——`departWhere` 若写在 `likeClause` 声明前会报 `ReferenceError: Cannot access 'likeClause' before initialization`，必须把 `departWhere` 放到 `likeClause`/`inClause` 定义之后。
2. **`sys_user_depart` 的部门列名是 `dep_id`（不是 `depart_id`）**；`sys_user` 本身没有 `depart_id`，用户—部门是多对多中间表。删部门前要先按 `dep_id` 清关联。
3. **MySQL 类型转换误报**：查 `sys_file WHERE parent_id IN ('<uuid>'…)` 会命中 `parent_id=0` 的行（MySQL 把 `0` 和 uuid 字符串比较时转数字导致相等），不代表真实关联。用 `BINARY` 比较或核对实际值可排除。
4. 冒烟脚本建的**菜单**（`sys_permission` 里 `smoke_菜单改_*`）仍全是 `del_flag=1` 软删态、未纳入本次范围；用户仅点名部门，未清。日志按用户此前选择继续保留。

## 如何扩展
- 冒烟部门若改用新前缀（如 `bs_`），把前缀加进 `SMOKE_DEPART_PREFIXES` 即可，无需改 SQL。
- 想连冒烟菜单一起清：新增一步按 `name LIKE 'smoke_%'` 物理删 `sys_permission`（注意先清 `sys_role_permission` 里的关联），并加到脚本常量区。
- 该脚本仍是默认 dry-run、`--apply` 才删、账号白名单兜底、事务回滚；凭据默认密码与 `.env` 不一致，运行时用 `SMOKE_DB_PASSWORD` 传入 `.env` 的 `DB_PASSWORD`。

- 执行：`--apply` 共删 10 行；复核预览全 0，库里剩 17 个正常部门未受影响。
