# 错误提示全局去英文（纯汉字化）

| 项 | 内容 |
|---|---|
| 日期 | 2026-11-12 |
| 仓库 | concise-admin |
| 触发 | 用户截图：后端挂掉时弹「服务暂时连不上，请稍后重试（/backend-api/v1/dicts → HTTP 502；代理无法连接后端）」，要求**全局**改成不带英文的纯汉字提示 |

## 根因

`src/lib/api-error.ts` 的 `ApiError` 构造函数有一段「开发模式贴身细节」逻辑：

```ts
super(import.meta.env.DEV && detail && !userMessage ? `${base}（${detail}）` : base)
```

- 生产环境：用户只看到人话（设计如此）
- **开发环境（5173 dev）**：把 `detail`（接口路径 + `HTTP 502` + 代理诊断）直接拼进 message 弹给用户——用户是老板/测试时同样被英文糊脸

`detail` 的原文本身就有路径、状态码这类英文/技术词，只要它有机会上页面，就不可能「纯汉字」。

## 改动（两点，全在 `api-error.ts`，一个文件收口全局）

1. **构造函数**：用户可见文案**永远**是人话，不再区分开发/生产把 detail 拼进 message；
   开发环境改为在构造时 `console.debug('[接口错误]', detail)` 打一条到控制台，联调定位能力不丢。
   `detail` 字段本身保留（横幅/控制台证据链仍可用）。
2. **`userMessageOf()` 兜底**：非 ApiError 的原始 Error，若整条消息**不含任何汉字**
   （`/\p{Script=Han}/u` 探测，浏览器原生英文报错、程序异常等），一律替换为人话兜底文案，
   杜绝 `Failed to fetch` 之类漏网英文。

各错误类型的可见文案不变（`KIND_MESSAGE`）：连不上 →「服务暂时连不上，请稍后重试」等，全部纯中文。
技术细节（哪个接口、什么状态码、响应片段）仍然完整地写在浏览器控制台，给开发者排障用。

## 为什么不动那 35 处 `toast.error(e instanceof Error ? e.message : ...)`

这些 catch 里的 `e` 绝大多数就是 `ApiError`（http 层已统一转换），改完后 `message` 即纯人话，
无需逐个替换成 `userMessageOf`。真正的英文泄漏源只有上面两处，收口修掉即可全局生效。

## 如何扩展

- 想改某类错误的可见文案：只改 `KIND_MESSAGE` 表
- 新增错误类型：加 `ApiErrorKind` 分支 + `KIND_MESSAGE` 一行，构造处给好 `detail`（随便带英文，页面上不会出现）
- 控制台细节想更全：在 `detail` 里追加即可，永远不影响用户所见

## 验证

- `tsc -b` 通过、ESLint 干净、前端 7/7 测试通过
- 手工核对：后端 3000 停掉 → 5173 页面 toast 应为「服务暂时连不上，请稍后重试」，
  控制台可见 `[接口错误] /backend-api/v1/dicts → HTTP 502；…` 完整细节

## 坑

- 这条中英混杂提示在**生产环境本来就不出现**，是 dev 专属体验；别为了「去英文」把控制台的
  detail 也删了——排障证据链就断了
- `/\p{Script=Han}/u` 需要 u 标志，普通 `/[\u4e00-\u9fa5]/` 会漏掉扩展汉字区，但判断
  「有没有汉字」用后者也够；选前者是顺手更准
