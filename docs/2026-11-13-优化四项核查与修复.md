# 2026-11-13 优化四项核查与修复

## 背景

上线评估后用户要求「全部修改」之前给出的优化项。实际动手前逐项核查，发现 4 项里 2 项（验证码 Redis 化、日志表索引）**代码里早已实现**，是记忆清单过时导致的误报；真正需要改的是 2 项。

## 核查结论与改动

| 优化项 | 核查结论 | 处理 |
| --- | --- | --- |
| 1. TenantAccessService 用户缓存无界 Map | 确实存在：TTL 只在读时检查，过期条目永不删除，冷用户条目永久滞留 | **已修**：读到过期条目时顺手 `delete`（`src/shared/tenant/tenant-access.service.ts`） |
| 2. 滑块验证码接 Redis（多实例前提） | **早已实现**：`captcha.service.ts` 的 challenge/ticket 均为 Redis `MULTI GET+DEL` 一次性消费 + `EX` 过期，注释明写支持多实例；未启用 Redis 直接抛 503 不降级 | 无需改动 |
| 3. 日志表时间索引 | **早已齐全**：`sys_log` 有 `idx_sys_log_type_time(log_type,create_time)`、`idx_sys_log_tenant_type_time(tenant_id,log_type,create_time)`、`idx_sys_log_user`；`base_schedule_reminder_log` 仅 14 行且有唯一键 | 无需改动 |
| 4. dashboard chunk 364K 偏大 | recharts 只有登录趋势图引用 | **已修**：`LoginTrendChart` 改 `React.lazy` + Suspense（骨架兜底），见前端仓库提交 |

## 关键细节

- **缓存清理**：`loadMembership` 里 `if (cached) { 未过期返回; 否则 delete }`——比只在读命中时跳过更彻底，腾出 Map 空间。
- **懒加载拆包效果**：dashboard 主 chunk 364K → 19K；recharts（348K）独立成 `login-trend-chart-*.js` 异步 chunk，仅在图表真正渲染时加载，首屏骨架阶段不再下载图表库。
- **无头验证踩的坑**（对以后排查有用）：
  - `spawnSync(chrome ...)` 会**阻塞等浏览器退出**，必须用异步 `spawn`；
  - **localStorage 必须先进入目标 origin 再写**——在 `about:blank` 上写入属于另一个命名空间，跳到站点后等于没写（表现为「莫名被踢回登录页」，实际是 storage 压根没进去）；
  - 手签 token 直连后端 200、穿 vite 代理也 200，说明签名与代理都没问题，问题只会在浏览器侧存储；
  - 清理无头 Chrome **严禁 `taskkill /IM chrome.exe`**（会杀掉用户所有 Chrome 窗口，本次已误杀一次），要按独立 `--user-data-dir` 匹配 CommandLine 精确杀。

## 如何扩展

- 后续任何「进程内 Map 缓存」都按同一模式写：读时检查 TTL、过期即删；要更彻底可加容量上限。
- 以后首页再加大体积图表（或重库），一律走 `lazy(() => import(...))` + Suspense 骨架，别静态 import 进路由 chunk。
- 记忆清单里的「遗留项」动手前必须先 grep 核实现状，防止像本轮一样修一个已经修好的东西。
