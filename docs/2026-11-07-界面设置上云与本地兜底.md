# 界面设置上云 + 接口失败本地兜底

> 起因：设置页（字号 / 主题色 / 侧边栏样式 / 布局 / 方向 / 灰度和色弱）以前只在开发环境能持久化
> —— vite dev server 读写项目根目录的 `settings.json`。生产部署后，`/api/settings` 这个中间件不存在，
> 一刷新就回到默认值；换台电脑、换个浏览器同样丢。

这轮把它改成**按用户存服务端 + 本地兜底**：

```
改设置 ──► 立即写 localStorage（同步、立刻生效）
        └─► 400ms 后 PUT /v1/users/me/settings（合并请求）
              ├─ 成功 → 状态「已同步」
              └─ 失败 → 状态「仅本机」+ 设置页显示「重试」
```

关键取舍：**本地永远是第一写入方**。接口挂了、断网了、token 过期了，用户改的设置立刻生效并留在本机，
下一个能联网的时刻再推上去；反之接口回来了、云端比本地新（换了设备），加载时以云端覆盖本地。

## 二、每个东西是干什么的

### 1. `sys_user_setting`：一人一行，主键即用户

```sql
CREATE TABLE `sys_user_setting` (
  `user_id`     VARCHAR(32) NOT NULL,
  `settings`    TEXT        NOT NULL COMMENT '设置JSON(服务端按白名单裁剪)',
  `update_time` DATETIME    NULL,
  PRIMARY KEY (`user_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

**为什么没有 tenant_id**：设置是账号级偏好，跟着人走。同一个人切到另一个租户，
不该突然变成另一套字号和主题色。这也是本轮唯一「故意不隔离」的新表。

**为什么主键就是 user_id**：一人一份、只读自己，天然没有并发插入问题，`upsert(..., ['userId'])`
一条 SQL 搞定；不用自增 id 也就没有「同一用户两行」的可能。

### 2. 白名单裁剪（`user-setting.util.ts`）

服务端定义 8 个键，逐项校验类型与值域：

| 键 | 规则 |
| --- | --- |
| `fontSize` | `small` / `default` / `large` |
| `themeColor` | `custom` 或 `^[a-z][a-z0-9-]{0,31}$`（只校验格式，不锁枚举——主题预设属于前端资源） |
| `customColor` | `^#[0-9a-f]{6}$` |
| `grayscale` / `colorWeak` | boolean |
| `sidebarVariant` | `sidebar` / `floating` / `inset` |
| `layout` | `default` / `compact` / `offcanvas` |
| `direction` | `ltr` / `rtl` |

三个设计点：

- **未知键静默丢弃**，不返回 400。偏好类数据局部容错比整体失败更合适。
- **返回空对象是合法结果**（全传错了），调用方把它当「没有可更新字段」，直接返回旧值，不产生空写。
- **`themeColor` 不锁枚举**：后端写死 `blue/rose/...` 的话，前端每加一个预设就得发一次后端版本。

体积上限 4KB：正常一份不到 200 字节，这行纯粹是防「被当成文件存储桶」。

### 3. 合并语义的 `save()`

```ts
const patch = normalizeSettings(input)
if (!Object.keys(patch).length) return current   // 没有可更新字段 → 不写库
const merged = { ...(current.settings ?? {}), ...patch }
await this.repository.upsert({ userId, settings: JSON.stringify(merged), updateTime: now }, ['userId'])
```

为什么必须是合并而不是整体覆盖：前端有两条写入路径（改主题色、改字号）都在推同一份对象，
但如果哪天只发改动项，整体覆盖就会把其它键冲成默认值。合并语义让「只传想改的」永远安全。

### 4. 读也过一次白名单

```ts
settings: normalizeSettings(this.parse(row.settings, userId))
```

库里的 JSON 可能残留前端已删掉的键（老版本写的）。读出来也裁一遍，保证下发给前端的永远是认识的结构。

### 5. 前端 `loadSettings()` 的判定顺序

```
1. 云端有值 && (本地没有 || 云端 updatedAt >= 本地) → 用云端，并回写本地
2. 云端有值但比本地旧                              → 用本地（本机改过还没推成功，别回滚用户）
3. 云端没有 / 接口失败                              → 本地 → 内置默认值
```

任何一步失败都不抛错。**设置读不到就用默认值，不能因为偏好接口挂了打不开系统。**

### 6. `syncState` 三态

| 状态 | 含义 | UI |
| --- | --- | --- |
| `synced` | 与云端一致 | 不显示（保持干净） |
| `pending` | 已写本地，正在推 | 「正在保存…」+ 转圈 |
| `local` | 推失败，只在本机 | 琥珀色提示「云端保存失败，设置已保存在本机」+ 重试按钮 |

`local` 态刻意做成**明确可见**：用户改完设置，如果接口挂了却什么都不说，他会以为设置没保存上，
下次打开发现是新的又觉得"功能很玄学"。说清楚"已存本机"比静默更可信。

### 7. 首帧不闪（`index.html` 内联脚本）

`applyOverrides()` 每次应用样式会把 CSS 串缓存到 `concise-settings-css`。内联脚本在 head 里读它，
建一个 `style#app-settings-override` 再套 `dir`，这样刷新时 React 还没起来样式就已经对了。

## 三、遇到的坑

### 1. 两处 style 标签抢同一个 id，导致"改了主题色刷新就变回去"

老的 `vite.config.ts` 里 `settingsApi()` 插件会在 `transformIndexHtml` 阶段注入
`style#app-settings-override`（内容取自 `settings.json` 的**静态默认值**），
而新加的 `index.html` 内联脚本又用同一个 id 注入 localStorage 里的**真实设置**。

结果页面上有两个同 id 元素：

- 运行时 `document.getElementById()` 拿到的是 DOM 里**第一个**（vite 注入的那个，在 head 靠前）
- 但它排在前面 → 同特异性下**后面的赢** → 用户保存的主题色被 `settings.json` 的默认值盖掉

修法不是"改 id"而是**删掉 vite 那段**：设置已经上云，静态默认值注入既过时又是冲突源。
连带 `settings.json`、`/api/settings` 中间件、`watch.ignored` 里的它一起清掉。

> 教训：同一个 DOM id 被两个来源写时，先问"还需要前者吗"，而不是想办法让后写的赢。

### 2. `getApiResult` 不能在设置接口上用

`http.ts` 的 `getApiResult` 在 401 时会**强制跳登录页**。设置是"锦上添花"的东西，
在登录页或会话过期时它只该静默回落本地 —— 用 `getApiResult` 会把人踢走。
所以 `settings.ts` 里用裸 `fetch` 自己判 `res.ok` + `success/code`。

### 3. `pushSettings` 不能 throw

`update()` 是在 React 事件里调用的。如果推送失败抛异常，会变成未捕获错误冒到控制台；
更要紧的是 `update()` 里 `persistLocal()` 必须**先于**任何远端调用，否则接口慢的时候用户看不到变化。
现在的写法：先落本地 → `setSyncState('pending')` → 防抖 400ms → `pushSettings().then(ok => ...)`，全程无 try/catch 泄漏。

### 4. 加载完成前用户就动手改

`loadSettings()` 是个异步过程（要等云端）。如果加载结果回来时直接 `setSettings(remote)`，
用户在等待期间调的大小/主题会被"旧数据"覆盖。

用 `dirtyRef` 记录「用户已经有本地改动」，加载回来时若 `dirtyRef.current` 为真就**不覆盖**：

```ts
if (!dirtyRef.current) { settingsRef.current = snapshot.settings; setSettings(snapshot.settings) }
```

### 5. 登出必须清偏好

`localStorage` 是按浏览器不是按账号的。不清的话 A 退出、B 登录，B 第一眼看到的是 A 的主题色和字号，
而且 `update()` 还会把 A 的设置推到 B 的账号里。现在 `logout()` 里 `clearLocalSettings()` 连带清首帧 CSS 缓存。

### 6. 登录用的是 `navigate()`，Provider 感知不到「刚登录」

`SettingsProvider` 挂在 `__root.tsx` 上，整个会话期间不卸载；登录页跳转是 `void navigate({ to: ... })`
而不是整页刷新。也就是说挂载时那次 `loadSettings()` 发生在**登录之前**（没有 token → 直接走本地），
登录完成后不会再拉一次 —— 换台设备登录的用户会看到默认主题，直到手动刷新。

修法：`auth.ts` 在 `login()` / `logout()` 末尾派发 `AUTH_CHANGED_EVENT`
（`window.dispatchEvent(new Event('concise:auth-changed'))`），Provider 监听它：

- 有 token → 重新 `loadSettings()`，并清 `dirtyRef`（换账号后「上一个账号改过」的标记没意义）
- 没 token（登出）→ 直接把界面恢复成默认值，且不写回本地（本地已被 `clearLocalSettings()` 清掉）

### 7. 迁移必须手动跑

项目没开 `migrationsRun` 自动执行，`npm run build` 只编译不建表。新表上线流程是：

```powershell
npm run build
npx typeorm migration:run -d dist/shared/database/data-source.js
```

忘了这步的表现是接口 500（`ER_NO_SUCH_TABLE`）。

### 8. 路由段数决定不冲突

`v1/users/me/settings`（3 段）与 `v1/users/:id`（2 段）不冲突，不会被 `:id` 吃掉。
这和之前水印那次一样，`users/me/*` 一组都不需要额外排序。但如果哪天写 `v1/users/:id/settings`，
就必须声明在 `:id` 之前了。

## 四、怎么扩展 / 使用

### 加一个新的设置项（三步）

1. **前端** `src/lib/settings.ts`：`AppSettings` 加字段 + `DEFAULT_SETTINGS` 给默认值。
2. **后端** `user-setting.util.ts`：`normalizeSettings()` 里加一条校验（**不加就会被静默丢弃**，这是最容易漏的一步）。
3. 设置页加对应控件，`useSettings().update({ 新键: 值 })` 即可，同步与兜底自动生效。

### 排查「设置没保存上」

| 现象 | 先看什么 |
| --- | --- |
| 徽标一直显示「已保存在本机」 | Network 里 `PUT /backend-api/v1/users/me/settings` 的状态码；401 = token 过期 |
| 改了没反应 | DevTools → Application → Local Storage 的 `concise-settings` 是否变了（变了就是渲染层问题） |
| 刷新后恢复默认 | `concise-settings` 与 `concise-settings-css` 是否还在；被什么清了（登出会清） |
| 换设备看不到 | 服务端 `SELECT * FROM sys_user_setting WHERE user_id='...'` 有没有行；`updatedAt` 是否比本地大 |

### 让新表参与用户级隔离（而不是租户级）

照着 `user-setting.entity.ts` 写：主键用 `userId`、**不要加 `tenant_id`**，
service 里所有查询显式带 `where: { userId }`。不要把这类表塞进 `BaseService` 的自动租户隔离
（那套是按实体有没有 `tenantId` 列判断的，没列自然不会隔离，别去加）。

### 冒烟怎么跑

```powershell
# 1. 起一个免验证码的测试实例
$env:PORT="3461"; $env:CAPTCHA_ENABLED="false"
node dist/main.js

# 2. 另开一个窗口
node scripts/smoke-user-setting.mjs
```

脚本用 admin 自己的记录跑，跑前删行、跑完删行，不留垃圾数据。18 项断言覆盖：
未登录 401、未设置返 null、白名单裁剪、未知键丢弃、非法枚举丢弃、合并语义、全非法键不空写、
4KB → 400、主键 upsert 只一行、落库无未知键、`update_time` 非空、账号间隔离。
