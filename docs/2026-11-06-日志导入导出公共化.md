# 日志导入导出公共化（对齐用户管理）

> 日期：2026-11-06　｜　范围：`src/helper/export`、`src/helper/import`、`src/modules/system/log`、`src/modules/user`、`src/migrations`

## 一、这轮到底改了什么

日志模块原来只有导出，而且登录日志、操作日志两个导出的写法是**各抄一份**：`buildXlsx(...)` + `setDownloadHeaders(...)` + `new StreamableFile(...)` 逐段复制，副标题只有一个「导出时间 + 条数」，没有操作人、没有筛选条件；导入则完全没有。

这轮做了两件事：

1. **抽公共件**：把「生成 Excel + 写下载头 + 返回流」和「读导入文件（xlsx/csv 分支 + 编码校验）」两段重复逻辑收敛成 `sendXlsx()` 与 `readImportFile()`，用户管理率先改用，日志紧随其后 —— 这就是「和用户管理一致」的落地方式：不是抄一份用户管理的代码，而是两边都调同一套函数。
2. **补导入**：登录日志、操作日志各补 `import-template`（模板下载）与 `import`（导入）两个接口，导入结果结构与用户导入完全相同（`total/created/updated/skipped/failed/errors`），前端可以直接复用同一个导入结果弹窗。

## 三、每个东西是干什么的

### 1. `buildExportSubtitle()` —— 副标题只有一种写法

```ts
export function buildExportSubtitle({ operator, count, filters = [] }: ExportMeta): string {
  const parts = [`导出时间：${formatDateTime(new Date())}`]
  if (operator) {
    parts.push(`操作人：${operator}`)
  }
  parts.push(`共 ${count} 条记录`)
  const active = filters.filter((item): item is string => Boolean(item))
  if (active.length) {
    parts.push(`筛选：${active.join('，')}`)
  }
  return parts.join(' · ')
}
```

产出形如：

```
导出时间：2026-11-06 20:00:32 · 操作人：admin · 共 68 条记录 · 筛选：用户名=admin，结果=成功，起始=2026-11-01 08:00:00
```

为什么值得单独抽：这份文件经常被转发给别人，**光有数据没有筛选条件，收文件的人不知道这 68 条是怎么筛出来的**。副标题里带全，比在群里补一句「这是筛选后的」靠谱。

### 2. `sendXlsx()` —— 一次调用完成整个导出

```ts
export async function sendXlsx({ res, sheetName, title, columns, rows, notes, cellStyle, meta, filePrefix, displayName }: SendXlsxOptions): Promise<StreamableFile> {
  const buffer = await buildXlsx(sheetName, columns, rows, {
    title: title ?? sheetName,
    subtitle: buildExportSubtitle(meta),
    notes,
    cellStyle
  })
  const today = formatDateTime(new Date()).slice(0, 10)
  setDownloadHeaders(res, `${filePrefix}-${Date.now()}.xlsx`, `${displayName}-${today}.xlsx`)
  return new StreamableFile(buffer)
}
```

控制器里从此只剩一行返回，列定义与数据映射还是各模块自己写（这部分本来就该各写各的）：

```ts
return sendXlsx({
  res,
  sheetName: '登录日志',
  columns: [...],
  rows: rows.map(row => [...]),
  notes: [...],
  cellStyle: (...),
  meta: { operator: req.user?.username, count: rows.length, filters },
  filePrefix: 'login-logs',
  displayName: '登录日志'
})
```

命名约定：`filePrefix` 用英文小写短横线（老浏览器/下载器兜底），`displayName` 用中文（`filename*` 走 RFC 5987，现代浏览器下载下来就是中文名 + 日期）。

### 3. `readImportFile()` —— 导入的前三道关卡

```ts
export async function readImportFile(file: Express.Multer.File | undefined, options: ReadImportFileOptions): Promise<XlsxTable> {
  if (!file) {
    throw new BadRequestException(IMPORT_FILE_REQUIRED)
  }
  const filename = file.originalname ?? ''
  const allowCsv = options.allowCsv ?? true

  if (/\.xlsx$/i.test(filename)) {
    return readXlsxTable(file.buffer, { headerKeys: options.headerKeys })
  }

  if (allowCsv && /\.csv$/i.test(filename)) {
    const text = file.buffer.toString('utf8')
    if (text.includes('\uFFFD')) {
      throw new BadRequestException('CSV 文件编码不是 UTF-8，请改用 .xlsx 导入，或另存为「CSV UTF-8（逗号分隔）」')
    }
    return { rows: parseCsv(text), headerRow: 1 }
  }

  throw new BadRequestException(allowCsv ? '仅支持 .xlsx（推荐）或 .csv 文件' : '仅支持 .xlsx 文件，请下载模板填写后导入')
}
```

`headerKeys` 是关键：导入模板第一行是大标题、第二行是填写说明，表头在第三行。传了 `headerKeys` 后，`readXlsxTable` 会自动找到「第一个命中关键字的行」当表头，并把真实行号带出来（报错时能说「第 4 行」而不是「第 2 条数据」）。

### 4. 日志导入的两个方法

`log.service.ts` 里三种日志共用一套流程，差异只有「列怎么认」和「一行怎么解析」：

```ts
private async importLogRows(
  rows: string[][],
  headerRowNumber: number,
  operator: string | undefined,
  logType: 0 | 1,
  aliases: Partial<Record<LogImportField, string[]>>,
  parseRow: (get: (field: LogImportField) => string, statusOf: (text: string) => number | undefined) => ImportedLogRow | string
): Promise<ImportResult>
```

- `aliases`：同一列允许几种表头写法（`用户名 / 登录账号 / operateusername`），手改过表头的文件也能导
- `parseRow`：返回字符串即视为「这行失败 + 失败原因」，返回对象则落库
- 落库前按 500 条一批 `save()`，2000 行一条 SQL 参数太多容易超包大小
- `status` 语义跟 JeecgBoot 一致：`0` 成功 / `1` 失败；文本写「成功/失败」「正常/异常」都认，留空按成功

## 六、踩的坑

1. **路由顺序**：`login/import-template` 若写在 `login/:id` 后面会被 `ParseIntPipe`/参数路由吃掉，必须前置。
2. **`resolveImportLayout` 的泛型**：`Partial<Record<T, string[]>>` 传进去类型不匹配，必须显式 `as Record<LogImportField, string[]>`（函数内部按 `Object.keys` 遍历，缺键无副作用）。
3. **`rowNumber` 别塞进实体**：一开始把 Excel 行号挂在解析结果上，结果被 `repository.create()` 当实体字段处理；行号只在错误收集时用，不该进实体。
4. **`/tmp` 路径**：Git Bash 的 `/tmp/x.xlsx` 传给 node 的 `readFile` 会「文件不存在」，要用 `cygpath -w` 转成 `C:\...`。
5. **既有 lint 报错**：`job.scheduler.ts` 两处 `job.stop()` 未处理 Promise，是拉取远程代码带进来的，`pnpm lint:ox` 因此直接失败；加 `void` 修复（同步的生命周期钩子里没法 await）。

## 七、以后新增模块怎么接

三步，不用再碰 `buildXlsx` / `setDownloadHeaders`：

```ts
// 1. 导出：控制器里一行返回
return sendXlsx({ res, sheetName: 'XX列表', columns, rows, meta: { operator, count: rows.length, filters }, filePrefix: 'xx-list', displayName: 'XX列表' })

// 2. 模板：buildImportTemplateXlsx（已有）+ setDownloadHeaders
const buffer = await buildImportTemplateXlsx({ sheetName: 'XX导入', title: 'XX导入模板', notes: [...], columns: [...], samples: [[...]] })
setDownloadHeaders(res, 'xx-import-template.xlsx', 'XX导入模板.xlsx')
return new StreamableFile(buffer)

// 3. 导入：先读文件，再交给 Service 做列定位与逐行校验
const table = await readImportFile(file, { headerKeys: ['XX名称', 'name'] })
return this.xxService.importXx(table.rows, table.headerRow, req.user?.username)
```

Service 侧复用 `src/helper/import/excel-import.ts` 里的 `resolveImportLayout` / `pickCell` / `createImportResult` / `failImportRow` / `assertImportRows`，导入结果天然与前端结果面板对齐。

## 八、还没做的

- **前端**：日志页还没有「导入」按钮与导入报告弹窗。后端已就绪，前端照用户管理页的 `导入` + 报告弹窗接即可（同一套 `ImportResult` 结构）。
- **权限分配**：`system:log:import` 只插了权限点，没有默认授权给任何角色（admin 走超管 bypass 不受影响）；需要给具体角色开按钮时去「角色管理 → 菜单授权」勾选。
- **日志导入的业务意义有限**：主要用于迁移历史日志 / 补录。如果后续要做「日志归档导入」，建议在 Service 里加一条「同一时间 + 同一用户 + 同一内容视为重复」的去重规则，目前是纯新增。
