# 代码生成器「继续生成」死路修复

> 2026-11-15 · 修复 · 后端 + 前端 + 生成脚本

## 问题现象

页面上点「执行生成」→ 弹「模块已存在，仍要继续？」→ 点「继续生成」→ 生成不了，报错（或表现为点了没反应、弹框又弹回来）。

## 根因：force 被第二道门挡死

`CodegenService.generate()` 原本有两道判断：

```ts
// 第一道：模块目录已存在且没有 force → 9201
if (existsSync(moduleDir) && !dto.force) throw new BizException(9201, '模块目录已存在…')

// 第二道：只要目录存在，且表存在 → 还是 9201（完全无视 dto.force）
if (existsSync(moduleDir)) {
  if (await this.tableExists(tableName)) throw new BizException(9201, '数据表已存在…')
}
```

只要这个模块之前生成过一次（目录在、表也在），**force 永远过不了第二道门** —— 「继续生成」按钮从设计上就是死路。

更糟的是前端把 9201 当成「需要二次确认」的信号：

```ts
catch (error) {
  if (error instanceof ApiError && error.code === 9201) {
    setForceConfirmed(true); setConfirmOpen(true); return   // 又弹同一个框
  }
}
```

于是「点继续生成 → 又收到 9201 → 又弹框」无限循环，用户看到的就是「点了生成不了、也没说为什么」。

## 修法

### 1. 先想清楚 force 到底该做什么

生成器写文件用的是 `writeIfAbsent`（同名文件一律跳过、绝不覆盖），所以 force 能兑现的语义只有一条：**补齐缺失文件**，不是「重建表」也不是「覆盖重写」。

据此，第二道门直接拆掉，改成**降级处理**而不是报错：

- 表已存在 → 本次**不生成迁移**（`CREATE TABLE IF NOT EXISTS` 对旧表无效，只会往 `migrations` 表塞一条同表记录，纯属污染）
- 该做的其它事照做（补齐缺的 entity/dto/service/controller/module、前端页面、注册点）
- 结果里带 `warnings` 把「没做的事」如实告诉用户

### 2. 生成脚本支持 `--no-migration`

`scripts/gen-module.cjs` 新增旗标，表已存在时由 service 传下去：

```js
if (NO_MIGRATION) console.log('跳过迁移生成（--no-migration）：表已存在，不产生重复迁移')
else writeIfAbsent(migrationFile, `…`)
```

manifest 里多带一个 `migrationSkipped`，日志尾部的「接下来手动做两件事」也按状态改写（不再让人去跑一个没生成的迁移）。

顺带解决了记忆里的待办「生成器对同名模块重复点击会重复产迁移」——现在重复生成根本不产迁移。

### 3. 预览与生成参数对齐

预览原本固定不带 `--no-migration`，于是表已存在时预览里仍有一份实际不会写入的迁移文件。现在两边用同一套判定：

```ts
const cliArgs = ['--spec', specFile, '--out', outDir, '--no-register', '--json']
if (tableExists) cliArgs.push('--no-migration')
```

`tableExists` 只在 preview/generate 各查一次，再作为参数传给 `warnings(dto, tableExists)`（避免同一个查询做两遍）。

### 4. 预览不再被「已存在」吞掉

`writeIfAbsent` 在 `--out` 暂存模式下会检查**真实仓库**是否存在同名文件，命中就跳过 —— 结果对已存在的模块点「重新预览」拿到 0 个文件，看起来像坏了。

预览的语义是「将会生成什么」，改为暂存模式不查真实仓库：

```js
if (!OUT_ROOT && fs.existsSync(file)) { /* 跳过 */ }
```

是否存在、会不会被跳过，交给 `warnings` 用文字讲清楚。

### 5. 前端不再死循环、不再假成功

```ts
// 9201 只在「还没确认覆盖」时转成二次确认；已带 force 仍被拒就正常报错
if (!force && error instanceof ApiError && error.code === 9201) { …二次确认… }
setConfirmOpen(false); setForceConfirmed(false)
toast.error(error.message)
```

结果卡也按「到底写了没有」分色：`created.length > 0` 才是绿色「生成完成」，否则黄色「没有写入文件」，并把 `warnings` 逐条列在卡片顶部。

## 现在的行为对照

| 场景 | 表不存在 | 表已存在 |
| --- | --- | --- |
| 模块目录不存在 | 正常生成（含迁移） | 正常生成（不产迁移，warnings 提示表已存在） |
| 模块目录已存在 + 无 force | 9201 二次确认 | 9201 二次确认 |
| 模块目录已存在 + force | 补齐缺失文件（含迁移） | 补齐缺失文件，不产迁移；若文件齐全则 `created=[]` + 「没有写入文件」 |

## 踩的坑

- **两道门只看第一道**：写判断时把 `force` 只加在第一道，第二道里 `existsSync(moduleDir)` 又把 force 的成果抹掉。同一个方法里出现两次同类校验，必须逐个检查有没有带上同一个放行条件。
- **前端把业务码当状态机用**：`9201 → 弹二次确认` 这个映射隐含「下次带 force 就会成功」的假设。必须加 `!force` 守卫，否则任何「force 也过不去」的后端变化都会变成无限弹框，且吞掉真正的错误文案。
- **预览与生成参数漂移**：两边各自拼 CLI 参数，很容易只改一边。现在两边都从 `tableExists` 派生参数，改一处两处一起变。
- **`writeIfAbsent` 在 --out 下查真实仓库**：预览复用了写盘函数，文件的「是否已存在」判断跟着一起走，导致预览对已有模块返回空。暂存模式要显式区分。

## 如何扩展

- **想支持「覆盖式重新生成」**：不要直接改 `writeIfAbsent` 的默认行为。加独立旗标 `--overwrite`，覆盖前把旧文件复制到 `.codegen-backup/<时间戳>/`，manifest 里单独列 `overwritten`，service 也单独返回一份列表，前端提示「已备份到 …」。默认仍是不覆盖。
- **想改表结构**：生成器不解决 ALTER。手写迁移，或在 `gen-module.cjs` 里加一个 `--alter` 分支按 `information_schema.COLUMNS` 反查差异生成 `ALTER TABLE`（注意 enum→tinyint、可空列要显式 varchar）。
- **新增生成前校验**：都在 `generate()` 顶部按「不满足就 `BizException`」的顺序加，注意每个抛错都要能被前端区分成「可确认继续」还是「硬失败」，否则又会回到这次的两难。
