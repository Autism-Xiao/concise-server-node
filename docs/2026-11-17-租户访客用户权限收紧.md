# 租户访客不再能看全租户成员（用户管理权限收紧）

> 2026-11-17 · 安全 · 影响：所有租户的 `viewer` / `editor` 模板角色

## 问题

访客账号（`concise`，角色「访客」）在「用户管理」页能看到默认租户 1 的全部 4 个账号，含 `admin` 的手机号、邮箱，还能点导出。

排查后确认不是租户隔离失效，而是**授权给多了**：

| 环节 | 实际值 | 应有 |
|---|---|---|
| viewer 拿到的权限 | `system:user:list` + `system:user:export` | 无（成员管理属管理员职责） |
| editor 拿到的权限 | `system:user:list/export/import/add/update` | 无 |
| 模板角色 `data_scope` | 1（全部） | 保持 1（业务数据仍应全租户可见） |

根因：`tenant-role-template.ts` 的只读档靠「权限码后缀」判断，`READ_SUFFIXES = {list, query, detail, export, download}`。用户管理的按钮恰好叫 `:list` / `:export`，于是被当成「只读能力」放给了访客 —— 后缀白名单无法区分「只读业务数据」和「只读人员名录」。

## 修复

只收「用户管理」整棵菜单子树，**不动 data_scope**：访客仍能看到本租户的订单/客户等业务数据，只是不能再进成员管理。这样改动最小，也不会把访客的业务可见范围一并收窄。

### 文件清单

| 文件 | 类型 | 说明 |
|---|---|---|
| `src/modules/system/tenant/tenant-role-template.ts` | 修改 | 新增 `TENANT_RESTRICTED_MODULES`（模块级黑名单）+ `TenantMenuNode` + `restrictedMenuIds()`；`acceptsByLevel` 保持不变，两层判断在 provision 里叠加 |
| `src/modules/system/tenant/tenant-provision.service.ts` | 修改 | `loadTenantMenus` 多查 `parent_id` / `url` 并统一空串为 null；`provisionIn` 先算各档位的排除集合再过滤授权目标 |
| `src/migrations/1794870000000-TightenTenantUserMenu.ts` | 新增 | 递归 CTE 定位「用户管理」子树 → 删除 `tenant_id>0` 且 `role_code IN ('viewer','editor')` 的相关授权；`down` 按旧白名单幂等补回 |

### 每项的作用

- `TENANT_RESTRICTED_MODULES`：`[{ urlPrefix: '/system/users', permsPrefix: 'system:user' }]`。两个特征都留，是为了容错 —— 页面节点 `menu_2` 有 `perms`，但万一将来被清空，还能靠 url 命中；按钮节点 `parent_id` 指向页面节点，靠递归覆盖。
- `restrictedMenuIds(level, nodes)`：`all` 档返回空集（租户管理员必须能管成员），`read` / `write` 档返回整棵子树 id 集合。三个模板角色共用同一棵树，按档位算一次。
- `loadTenantMenus` 的 `parentId` 归一化：库里历史数据 `parent_id` 有 `''` 空串，不转 null 会被当成「一个叫空字符串的父节点」，子树递归直接断链。
- 迁移而非只改模板：`provisionIn` 的 `grant()` 只做「差集补齐」，**从不回收**已有授权。只改模板对存量 3 个租户完全无效，必须迁移显式删。
- 迁移只删 `role_code IN ('viewer','editor')`：租户自建的自定义角色不碰 —— 迁移不该替用户猜业务意图。默认租户 1 的 `auditor`（审计员）仍有 6 条 `system:user:*`，属历史自定义角色，需要人工决定是否收回。

## 验证（3461 实例，`CAPTCHA_ENABLED=false`）

```
admin   : /users 200 total=4    /users/export 200
concise : /users 403 code=1004  /users/export 403   ← 之前是 200
concise : /users/me 200          ← 个人资料不受影响
concise : /users/lookup 200      ← 选人回显不受影响
菜单树  : admin 124 个节点含「用户管理」；concise 19 个节点不含
```

DB 侧：`viewer/editor` 的用户管理授权残留 0 条，`admin` 9/8/8 条完好。

## 踩的坑

1. **页面节点没有 perms 也会被授予**：`acceptsByLevel` 对无权限码节点返回 true（目录/页面必须给，否则侧边栏没菜单）。所以只按 perms 前缀排除按钮是不够的，页面节点会留在侧边栏，点进去才 403 —— 必须把页面节点一起排，并递归到子节点。
2. **url 是 `/system/users` 复数**，不是 `/system/user`；写成单数匹配不到任何节点，迁移会静默什么都不删（`ids.length === 0` 直接 return）。
3. **TypeORM 1.1 的 `queryRunner.query` 不接受泛型**：`query<Array<T>>()` 报 `Expected 0 type arguments`，要 `const raw = await query(...)` 再 `as Array<T>`，并且 `QueryResult` 不保证是数组，得 `Array.isArray` 兜一下。
4. **缓存不会自己知道 DB 被迁移改了**：角色权限集合缓存在 Redis（`perm:role:<roleId>`，TTL 300s），迁移后最多 5 分钟才生效。要立刻生效：重启后端 + 清 `perm:role:*`。
5. **`grant()` 只补不删**是这套 provision 的设计前提（幂等补齐、不覆盖租户自定义授权），所以「收紧授权」永远需要单独的迁移，不能指望重跑 `provision-all`。

## 如何扩展

- 想把「部门管理」也收掉：往 `TENANT_RESTRICTED_MODULES` 加 `{ urlPrefix: '/system/dept', permsPrefix: 'system:dept' }`，再写一个同样的迁移删存量授权。注意部门树可能被业务页（选部门下拉）复用，先确认为它走的是独立无权限接口。
- 想让访客「只能看自己部门的人」而不是完全看不到：那是另一条路 —— 把 `viewer` 的 `data_scope` 改成 3（本部门）并保留 `system:user:list`。但要注意 `scopedQuery` 是首页用户数卡片、列表、导出三处共用的口径，改 scope 会连带影响 dashboard 数字。
- 新建租户自动生效：模板改动对 `provisionIn` 直接生效，无需额外操作；`POST /v1/tenants/provision-all` 只会补新菜单，不会恢复已删的授权。
