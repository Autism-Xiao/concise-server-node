# 用户界面设置：建号即建行 + 默认值上移后端

## 问题

`sys_user_setting` 原来只有一条写入路径 —— `PUT /v1/users/me/settings` 里的 `upsert`。
也就是说新账号创建出来之后，**库里没有它的设置行**，必须等这个人登录、进设置面板改一下主题或字号，才会插入第一行。

后果：

- 数据口径不一致。改造前开发库是「用户表 4 行、设置表 2 行」，`jeecg`、`zhangsan` 两个在用账号查不到设置行；
- 后台「用户管理」无法判断这个账号是「没自定义过偏好」还是「数据漏了」；
- 只要有任何依赖 `JOIN sys_user_setting` 的报表 / 导出，就会漏掉从未登录过的账号。

另外默认值只存在于前端（`lib/settings.ts` 的 `DEFAULT_SETTINGS`），后端 `GET` 对空行返回 `{}`，
等于「谁消费谁负责合并」。只有一个 Web 端时没问题，一旦加小程序 / 移动端，每个端都要各写一份默认值。

## 方案

三件事：

1. **建行时机前移**：创建用户时在同一事务里落一行设置，不再等用户点保存；
2. **默认值上移到后端**：`DEFAULT_USER_SETTINGS` 由后端定义，`GET` 读时把默认值与库里的差异合并，**永远返回完整对象**；
3. **库里只存差异**：后端默认值改版时，老用户不需要任何迁移就能拿到新默认值。

| 文件 | 类型 | 说明 |
|---|---|---|
| `src/modules/system/user-setting/user-setting.util.ts` | 改 | 新增 `DEFAULT_USER_SETTINGS`（服务端权威默认值）、`withDefaults()`（读时补齐）、`stripDefaultSettings()`（写库前剔除等于默认值的键） |
| `src/modules/system/user-setting/user-setting.service.ts` | 改 | 新增 `ensure(userId, manager?)`（`INSERT IGNORE` 建空行）、`readStored()`（原始差异，合并基准）；`get()` 返回补齐后的完整对象；`save()` 合并后剔除默认键 |
| `src/modules/system/user-setting/user-setting.controller.ts` | 改 | Swagger 描述同步：`settings` 恒为完整对象，`updatedAt: null` 表示从未修改 |
| `src/modules/user/user.service.ts` | 改 | `create()` 事务内调 `ensure`；`restore()` 兜底补行；`delete()` 软删时**保留**设置行 |
| `src/modules/user/user.module.ts` | 改 | `imports` 加 `UserSettingModule`（它不反向依赖 `UserModule`，无循环） |
| `src/migrations/1794250000000-BackfillUserSetting.ts` | 新增 | 给存量在用用户一次性补空行 |
| `src/migrations/1794260000000-StripSettingDefaults.ts` | 新增 | 清洗历史整包数据：剔掉「与默认值相同」的键（不动 `update_time`） |
| `concise-admin/src/lib/settings.ts` | 改 | 仅注释：`settings` 不再可能为 `null` |

### 数据长什么样

```jsonc
// 库里的 settings（只存差异，用户只改过字号）
{"fontSize":"large"}

// GET /v1/users/me/settings 下发（补齐后，8 项完整）
{"settings":{"fontSize":"large","themeColor":"default","customColor":"#2563eb",
             "grayscale":false,"colorWeak":false,"sidebarVariant":"sidebar",
             "layout":"default","direction":"ltr"},
 "updatedAt":1762670000000}
```

`updatedAt` 为 `null` = 这个账号从没改过设置（库里是空行）。前端拿它判断「有无自定义」，
但**渲染不需要它** —— 下发的对象已经是完整可用的。

### 为什么必须「只存差异」

如果建号或保存时把当时的默认值整包写进库，`fontSize: 'default'`、`themeColor: 'default'` 这些就会变成
「用户显式选择的值」。将来后端把默认字号改成 `large`，这些人的库里仍然是 `'default'`，
**永远停在建号那天的默认**，而且从数据上完全看不出他们其实从没设置过。

所以约定：

| 场景 | 落库内容 |
|---|---|
| 建号 | `{}`（空差异行） |
| 用户改了字号 | `{"fontSize":"large"}` |
| 用户把字号改回默认 | `{}`（改回默认 = 删除这条差异） |
| 前端推完整 8 项 | 只有与默认不同的键会落库 |

### 软删为什么**不清**设置行（与角色/水印的处理相反）

`delete()` 是软删，会清 `sys_user_role` / `sys_user_depart` / `sys_user_post` / `sys_user_watermark`，
但 `sys_user_setting` **刻意不动**。三者的性质不同：

| 数据 | 软删时 | 理由 |
|---|---|---|
| 角色 / 部门 / 岗位 | 清 | 权限不能「自动复活」，恢复账号时必须由管理员重新确认 |
| 水印个性化 | 清 | 属于安全/合规配置，恢复后应重新确认 |
| **界面设置** | **保留** | 纯个人习惯，恢复出来的就是同一个人，丢了不可逆且没有任何安全含义 |

拿「不清会越积越多」当理由也不成立：软删账号通常是活跃账号的零头，这张表全靠主键查，
多几万行对任何查询都无感；真要清理，将来加「回收站到期物理删除」时一起处理才是正解。

`restore()` 里仍然调了一次 `ensure()`，但它的作用变成**兜底**：改造前就躺在回收站里的老账号没有设置行，
恢复时补一行空设置；已有行的情况 `INSERT IGNORE` 幂等跳过，偏好原样保留。

### 被否决的方案

- **建号时直接写完整默认值**：能让 DBA 打开表直接看到生效配置，但每行多约 120 字节（千万级就是 GB 量级），
  且默认值改版后老用户不跟随。要解决就得读时合并 —— 那还不如库里只存差异。
- **把设置并进 `sys_user` 的 JSON 列**：能天然消灭「没有行」的问题（列默认值就是 `{}`，删号恢复天然带走/带回），
  但 `sys_user` 是千万级热点主表，加 TEXT 列的 DDL 代价和 `SELECT *` 时的额外传输都不划算；
  而且项目已有 `sys_user_watermark` 这种「按用户一行的附属表」先例，拆表更符合现有风格。

## 验证

`PORT=3461 CAPTCHA_ENABLED=false` 起测试实例，16 项端到端检查全部通过：

| 检查 | 结果 |
|---|---|
| 创建用户 → 立即有设置行 `'{}'` + `update_time IS NULL` | PASS |
| 新用户 `GET` → 返回完整 8 项默认值（不再是 `{}`）+ `updatedAt: null` | PASS |
| 老账号（库里只有差异）`GET` → 缺失项用默认值补齐 | PASS |
| `PUT` 单项 → 库里只存 `{"fontSize":"large"}`（默认值未写回） | PASS |
| `PUT` 完整 8 项默认值 → 库里回到 `{}` | PASS |
| `PUT` 完整 8 项其中一项不同 → 库里只留那一项 | PASS |
| 库里残留废弃键（`legacyKey`）→ 不下发给前端 | PASS |
| 完全没有设置行的账号 → `GET` 返回完整默认值 | PASS |
| 无行账号 `PUT` → 差异行重建 | PASS |
| 软删用户 → 差异行与偏好原样保留 | PASS |
| 回收站恢复 → 偏好原样还在（`update_time` 未被重置） | PASS |

单元测试 15 项（`user-setting.util.spec.ts`）另覆盖：

- `DEFAULT_USER_SETTINGS` 每个键都通过白名单（防止「加了默认键却忘了加校验」）
- `withDefaults` 对脏输入（字符串、非法值、未知键）仍然只输出合法结构
- `stripDefaultSettings` 全默认 → `{}`、改回默认 → 删除该差异

## 坑

- **`save()` 的合并基准不能用 `get()`**：`get()` 返回的是补齐后的完整对象，拿它做基准会把 8 个默认键全写回库。
  必须用 `readStored()`（原始差异）。
- **`save()` 合并后必须调 `stripDefaultSettings()`**：前端推的是完整 `AppSettings`，不剔除等于每次保存都整包固化默认值。
- **`ensure` 不能用 `upsert`**：`upsert` 是覆盖语义，恢复账号或并发调用时会把用户已存的偏好冲成空。必须是 `INSERT IGNORE`（TypeORM 的 `.orIgnore()`）。
- **事务内的 `ensure` 必须传 `manager`**：默认连接看不到事务里未提交的数据，跨连接写入还会在回滚时留下孤儿行。
- **迁移的 `down()` 只能删「空行」**：条件是 `settings = '{}' AND update_time IS NULL`。这个组合只可能是系统建的（`save()` 每次都会写 `update_time`，且白名单裁剪后为空时直接返回不写库）。
- **清洗迁移不改 `update_time`**：那是运维清洗不是用户行为，改了会给前端「本地 vs 云端谁更新」的假信号。
- **迁移里的默认值要内联快照**（`1794260000000` 就是这么做的）：迁移是历史记录，行为不能随后续代码改动而变。

## 以后加设置项的顺序

1. `user-setting.util.ts` 的**白名单**（`normalizeSettings`）—— 不加会被静默丢弃；
2. `user-setting.util.ts` 的 `DEFAULT_USER_SETTINGS` —— 不加这一项就永远是 `undefined`；
3. 前端 `AppSettings` + `DEFAULT_SETTINGS` —— 前者是类型，后者只在「未登录 / 接口挂了 / 首帧」时兜底。

第 1、2 步漏了会被单测抓住（「默认值本身必须全部通过白名单」那条）。
