# 用户界面设置：建号即建行（去掉懒创建）

## 问题

`sys_user_setting` 原来只有一条写入路径 —— `PUT /v1/users/me/settings` 里的 `upsert`。
也就是说新账号创建出来之后，**库里没有它的设置行**，必须等这个人登录、进设置面板改一下主题或字号，才会插入第一行。

后果：

- 数据口径不一致。改造前开发库是「用户表 4 行、设置表 2 行」，`jeecg`、`zhangsan` 两个在用账号查不到设置行；
- 后台「用户管理」无法判断这个账号是「没自定义过偏好」还是「数据漏了」；
- 只要有任何依赖 `JOIN sys_user_setting` 的报表 / 导出，就会漏掉从未登录过的账号。

## 方案

把建行时机前移到**创建用户**，并且和账号本身放在同一个事务里。

| 文件 | 类型 | 说明 |
|---|---|---|
| `src/modules/system/user-setting/user-setting.service.ts` | 改 | 新增 `ensure(userId, manager?)`：`INSERT IGNORE` 一行空设置；新增常量 `EMPTY_SETTINGS = '{}'` |
| `src/modules/user/user.service.ts` | 改 | `create()` 事务内调 `ensure`；`restore()` 事务内调 `ensure`；`delete()` 事务内删 `sys_user_setting` 行 |
| `src/modules/user/user.module.ts` | 改 | `imports` 加 `UserSettingModule`（它不反向依赖 `UserModule`，无循环） |
| `src/migrations/1794250000000-BackfillUserSetting.ts` | 新增 | 给存量在用用户一次性补空行 |

### 为什么是 `'{}'` 而不是前端那份完整默认值

前端 `DEFAULT_SETTINGS` 会随迭代变化（加设置项、换默认主题、调整默认字体）。如果建号时把当时的默认值整包写进库，

- 老用户的云端值永远停在「建号那天的默认」，前端改了默认值他们也不会跟随；
- 还会让「用户到底有没有自定义过」这件事彻底看不出来。

所以统一存 `'{}'`：**行存在**（口径一致），**内容为空**（表示没有任何自定义），真正的默认值仍由前端 `DEFAULT_SETTINGS` 提供。
`update_time` 留 `NULL`，表示「从未修改过」——前端 `loadSettings()` 拿它和本地副本比新旧时，不会被一行刚建出来的空设置压掉本机改动。

### 删除 / 恢复的对称处理

`delete()` 是软删，原来已经会清 `sys_user_role` / `sys_user_depart` / `sys_user_post` / `sys_user_watermark`
（理由都是「按 user_id 主键的表不清会越积越多，恢复时旧数据还会自动复活」），本次把 `sys_user_setting` 也纳入同一处。
`restore()` 里调一次 `ensure()` 重建空行，回收站恢复出来的账号才有设置行。

因为 `ensure()` 用 `INSERT IGNORE`，重复调用（并发建号、恢复、迁移回填）都不会报错也不会覆盖已有偏好。

## 验证

`PORT=3461 CAPTCHA_ENABLED=false` 起测试实例，10 项端到端检查全部通过：

| 检查 | 结果 |
|---|---|
| 创建用户 → 立即有设置行 `'{}'` + `update_time IS NULL` | PASS |
| 新用户登录 → `GET /users/me/settings` 返回 `{"settings":{},"updatedAt":null}`（非 `null`） | PASS |
| `PUT` 改字号/主题色 → 落库为用户真实偏好且写了 `update_time` | PASS |
| 软删用户 → 设置行被清（rows=0） | PASS |
| 恢复用户 → 空设置行重建 | PASS |
| 全库口径：在用用户数 == 设置行数（4 == 4） | PASS |

迁移回填结果（开发库）：`jeecg`、`zhangsan` 补上 `'{}'`；`admin`、`ceshi` 原有的真实设置**未被覆盖**；软删账号不补（恢复时再建）。

## 坑

- **`ensure` 不能用 `upsert`**：`upsert` 是覆盖语义，恢复账号或并发调用时会把用户已存的偏好冲成空。必须是 `INSERT IGNORE`（TypeORM 的 `.orIgnore()`）。
- **事务内的 `ensure` 必须传 `manager`**：默认连接看不到事务里未提交的数据，跨连接写入还会在回滚时留下孤儿行。方法签名因此是 `ensure(userId, manager?)`，内部用 `manager.getRepository(...)`。
- **迁移的 `down()` 只能删「空行」**：条件是 `settings = '{}' AND update_time IS NULL`。这个组合只可能是系统建的（`save()` 每次都会写 `update_time`，且白名单裁剪后为空时直接返回不写库），不会误删用户数据。
- **回填只补 `del_flag = 0`**：软删账号补了也是垃圾行，恢复路径已由 `ensure()` 兜住。

## 以后怎么用

- 新增「按用户一行」的表（例如用户偏好、用户看板布局）照这个套路：`ensure()` + 建号事务内调用 + 删除时清理 + 恢复时重建 + 一条回填迁移。
- 设置项本身要加字段，仍然只改 `user-setting.util.ts` 的白名单和前端 `AppSettings`，不用碰表结构。
