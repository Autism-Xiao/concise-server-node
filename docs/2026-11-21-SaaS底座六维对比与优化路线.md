# SaaS 底座六维对比与优化路线（2026-11-21）

## 背景与结论

对照「商业化运营 / 异步链路一致性 / 数据深度隔离 / 权限精细化 / 租户生命周期 / 可观测性」六个维度，逐条核查了当前代码（`src/` + `scripts/` + `ci.yml` + `deploy/sql`），并与提出的建议做对照。结论：**底座水位高于建议假设的起点，但建议的优先级需要重排**。三个关键纠偏：

1. **队列没引入**，所以「BullMQ Worker 丢 AsyncLocalStorage」目前不是现网风险；真实风险是已有 3 个 cron 里有 2 个在无租户上下文下跨租户读写。
2. **缓存键污染面比预期小**：权限缓存 `perm:role:{roleId}` 用全局主键、`sys_config` 已用 `${tenantId}::${key}`；真正该修的是文件存储（旧 `/upload` 静态无鉴权 + `tool_storage` 无 tenant 列 + `file.recent` 漏租户条件）。
3. **发现两个比清单更急的越权 bug**：`assignRoles` 全量覆盖会删掉用户在其他租户的角色绑定；`owner` 权限只守列表，详情/更新/删除可绕过。

| 维度 | 你的定位 | 代码事实 | 调整后 |
| --- | --- | --- | --- |
| 队列/任务上下文 | P0 | 无 BullMQ/Worker；有 3 个 cron，其中 2 个跨租户 | **P0（改写范围：cron，不是队列）** |
| 缓存键隔离 | P0 | `perm:role` 全局主键安全、`sys_config` 已含 tenantId | 降为 P2（只需统一口径） |
| 文件存储隔离 | P0 | 旧上传无鉴权静态直出、`tool_storage` 无 tenant、`file.recent` 漏条件 | **P0（最实在的一条）** |
| 资源配额 | P1 | `plan` 字段是死字段；Seats/API 无配额；Storage 按 owner 不按租户 | P1（但口径必须先定为租户级） |
| Per-tenant 限流 | P1 | 仅 IP+路由(+可选 account)，守卫在 JWT 前拿不到 user | P1 |
| ReBAC / 字段脱敏 / 特性开关 | P2 | `viewer` 可见客户手机号；owner 只守列表；开关全是进程级 | 详情越权提 **P0**，脱敏 P1，ReBAC P2 |
| 租户导出 / WORM / 指标 | 未列优先级 | 按租户导出无、审计可删、无 metrics | P2（合规客户出现再做） |

## 一、商业化与用量治理（Plan & Metering）

### 现状对照

| 能力 | 建议要求 | 代码事实 | 证据 |
| --- | --- | --- | --- |
| 套餐 | 功能 + 资源配额 | 只有功能套餐 `sys_tenant_menu`（菜单权限交集）；`sys_tenant.plan` 字段仅存储，无任何分支 | `tenant.entity.ts:53-55`、`tenant-package.service.ts:63-93` |
| VIP / 额度 | 商业资格 | 已实现，但额度是「一个 VIP 用户能开几个租户」，不是租户内资源 | `tenant.service.ts:157-230`、`system-config.service.ts:43` |
| Seats | 租户最大用户数 | 无。`user.service.ts:236-294` 创建用户只校验唯一性/密码策略 | `user.service.ts:236-294`、`tenant.service.ts:497-571` |
| Storage | 总容量 | 有，但**按用户**且来自环境变量 `FILE_QUOTA_MB`（默认 2GB）：`usedBytes(ownerId)` 按 owner + 当前租户统计。`/v1/upload` 图片链路完全不计入 | `file.service.ts:36-39, 280-284, 753-763`；`upload.service.ts:44-63` |
| API 调用 | 频次/次数 | 无计量；开放平台只按 IP 限流 20/60s | `api-scope.guard.ts:28-48`、`token.v1.controller.ts:49` |
| 计量 | Redis INCR / 月度汇总 | 无。Redis 仅有 `rl:`（限流）与 `auth:login:fail:` 两类业务计数；`sys_log` 默认 30 天物理删除，没有先汇总 | `rate-limit.service.ts:46`、`job.handlers.ts:83-95` |
| 限流 | Per-tenant | 无。`(route+IP[:account])`，`by:'account'` 全仓零使用且守卫在 JWT 前，注释已承认会退化成 IP | `rate-limit.guard.ts:44-72`、`tenant.v1.controller.ts:98-100` |

### 优化路径（P1，商业化前必须做）

1. **先把配额口径定为「租户 +套餐」，不要延续按用户**。当前 `fileQuotaBytes()` 按 owner 是历史实现，如果商业化直接在其上加套餐倍率，会出现「租户内 10 个用户各 2GB = 20GB」的口径错误。建议新增 `sys_quota(tenant_id, resource, limit, used)` 或直接在 `sys_tenant` 加 `max_users/max_storage_bytes/max_api_calls` 三列，由 `sys_config` 的租户覆盖行承载默认值与例外。
2. **三处植入点**：
   - Seats：`user.service.ts:create` 与 `tenant.service.ts:assignUsers` 共用一个 `assertSeatQuota(tenantId)`，放在事务内 `SELECT ... FOR UPDATE` 锁租户行，避免并发超卖（复用 `applyCreate` 的串行化写法）。
   - Storage：`file.service.ts:assertQuota` 的 `usedBytes` 改成按租户汇总，并把 `/v1/upload` 链路纳入同一计量（或明确它是「公开头像」Small File 不计入套餐，但必须写进文档）。
   - API：`RateLimitGuard` 增加 `by:'tenant'` 后限流即计量（Redis `INCR` 已现成），按月 key 保留 30 天数据即可做账单底稿，不必引入队列。
3. **计量最小实现**：在 `RateLimitService` 旁加 `MeteringService.record(tenantId, resource, delta)` → `INCR tenant:usage:{yyyyMM}:{tenantId}:{resource}`，写路径不 await（`void`）即可；月度归档用一个现有 cron 任务把 Redis 计数落 `sys_usage_monthly` 后删 key。**不要为了 metering 单独引 BullMQ**。
4. `plan` 字段要么接上配额默认值（trial=3 seats/1GB、standard=20/20GB、enterprise=∞），要么删除，避免继续做「看起来有套餐」的死字段。

## 二、异步链路与上下文一致性（Context Propagation）

### 现状对照

| 建议关注点 | 代码事实 | 证据 |
| --- | --- | --- |
| BullMQ Worker 丢 ALS | **无 BullMQ / bull / @nestjs/bullmq / 独立 Worker**；全仓只有 `cron@4.4.0` + `ioredis` | `package.json:40-81`、`main.ts:140-267` |
| 定时任务上下文 | `JobScheduler` 已用 `TenantContext.withTenant(job.tenantId, ...)` 包裹（唯一正确的一个）；`FileCleaner`、`ReminderScheduler` 无包裹 | `job.scheduler.ts:162-167`；`file.cleaner.ts:21-30`；`reminder.scheduler.ts:28,60` |

| EventEmitter | 使用 Node 内置 `EventEmitter`（非 EventEmitter2）；提醒事件载荷无 tenantId，订阅方 `realtime.service.onReminder` 只按 userId 推送 | `reminder.scheduler.ts:126-134`、`realtime.service.ts:46-61` |
| 审计异步 sink | `change-log.service.ts` 在 sink 回调入口同步读 `TenantContext`，ALS 尚在同步栈内，当前是安全的；但这是隐式依赖，重构时极易踩坏 | `change-log.service.ts:47-58` |
| AsyncResource.bind | 全仓 0 处 | — |
| 跨服务透传 | 4 处出站 `fetch`（SSO 3 + Webhook 1）均**未带 `X-Tenant-Id`**；Webhook 把 tenantId 放在 body。无 HttpModule/gRPC | `sso.service.ts:80,114,135`、`webhook.service.ts:250-276` |
| Redis pub/sub | 未使用 | `redis.service.ts:19-34` |

### 优化路径（P0，改写范围是已有异步边界）

1. **补 `TenantContext` 包裹**：给 `FileCleaner.sweep()` 与 `ReminderScheduler.patrol()/trigger()` 显式指定上下文。注意 `FileCleaner` 现在是靠「ALS 为空 → `filterTenantId()` 返回 null → 不过滤」间接实现全租户扫描的；改成逐租户跑时，必须遍历 `sys_tenant`（含共享行 tenant_id=0 的处理），不能简单 `withTenant(null)` 了事。
2. **修 `cleanLogJob` 原生 SQL**：按 `sys_log.tenant_id` 分组循环删除，或明确它是平台级任务并在 SQL 里加 `tenant_id = 0`。这是「上下文包了但 SQL 没跟」的典型，单靠 ALS 兜不住裸 SQL。
3. **事件载荷显式带 tenantId**：`ReminderPayload` 加 `tenantId`，`realtime.service` 推送前用 `withTenant` 包一层（WebSocket 不经过 HTTP 中间件，ALS 本来就是空的）。
4. **规则先立、队列后引**：把「所有异步入口必须显式携带 tenantId（payload 或 `withTenant`）」写进开发规约和单测，将来真引 BullMQ 时在 `Worker.processor` 首行 `TenantContext.run(store, ...)` 即可，不必现在提前引依赖增加运维面。
5. **跨服务透传**：当前无内部微服务调用，SSO 是对外部 IdP、Webhook 是出站订阅，都不该带内部 `X-Tenant-Id`。若未来拆分，再加统一 `TenantPropagatorInterceptor` 注入该头，现在做属于过度设计。

### 优化路径

**P0（本轮最急的三件事）**

1. 修 `assignRoles` / `delete` 的跨租户解绑：查当前角色绑定时加 `tenant_id = 当前租户 OR tenant_id = 0`，删除只针对这些行；平台视角操作保持全租户语义。补单测 + 冒烟（双租户同账号，A 改角色后 B 角色仍在）。
2. `file.recent` 补 `applyTenantScope`，并把 `/v1/files/recent` 加入 `smoke-file.mjs` 与 CI（现在 CI 4 个 smoke 不含文件域）。
3. 旧 `/v1/upload` 收口：最小改动是**禁止 `public/upload` 目录被静态直出**，改为经 `/api/v1/files/:id/download` 同款鉴权接口；若短期不能改前端，至少给 URL 加不可枚举前缀并对 `Referer`/登录态做校验。`tool_storage` 加 `tenant_id` 列 + 归属校验。这是当前唯一「未登录可越权读文件」的面。

**P1（工具层）**

4. 加 `TenantAwareRepository`：对 `Repository` 的 `find*` / `createQueryBuilder` 做受控包装，业务层注入它而非裸 `DataSource`。**不要走「ESLint 禁裸调 createQueryBuilder」**——非 type-aware 规则无法判断实体是否带 tenantId，会把 55 处合法调用全部误伤（已决策过，见 `docs/README.md:7`）。
5. 把 `createTenantQb` 的覆盖从 5 处扩到所有带 `tenant_id` 列且仍在裸调的查询；每次迁移配一条单测或冒烟断言。
6. `job.service.ts:201` 唯一性检查加租户条件（或明确它是平台级唯一，改名并注释）。

## 四、权限模型精细化（ReBAC / ABAC）

### 现状对照

- RBAC 闭环完整：`sys_user_role` + `sys_role_permission` + `sys_permission.perms`，PermsGuard 做「角色授权 ∩ 套餐授权」双交集（`perms.guard.ts:65-70`）。注意表名不是建议里假设的 `role_menu`。
- `data_scope` 1/2/3/4 在**用户列表**上完整实现（含部门父子展开，多角色取 `Math.min`）；在业务数据上被 `owner-scope.util.ts` 简化为「ALL 放行 / 其余按 `createBy=self`」，部门档保守降级为 self。
- **owner 只守列表**：customer/biz_order 的 `GET /:id`、`PUT /:id`、`DELETE /:id` 走基类 `findOne`，只拼租户条件。`data_scope=4` 的用户列表看不到他人数据，但知道 id 就能读写同租户他人数据（`base.service.ts:35-43,119-141`）。这是 P0 越权，不是 P2。
- 字段级脱敏：`ClassSerializerInterceptor` / `@Exclude` 全仓 0 处；只隐藏了 password/salt/totpSecret（`select:false` + `stripPassword`）。`viewer` 模板拥有 `customer:list` 且 `data_scope=1`，可直接读到全租户客户 `phone`；订单 `amount` 同理。成本价字段库中不存在。
- 关系表：`sys_user_supervise_dept` 不存在；`sys_role_permission.data_rule_ids` 列存在但从未被读取。

### 优化路径

1. **P0：新增 `findOneScoped(id, actor)`** 供 customer/biz_order 的详情、导出、编辑入口使用，不要直接改基类 `findOne`（它被 update/delete 复用，改了会把写路径一起收窄，可能误伤后台任务）。
2. **P1：字段级脱敏先做最小集**。在 `TransformInterceptor` 后追加一个基于 perms 的字段策略：给 `customer.phone`、`biz_order.amount` 声明「需要 `customer:phone:view` / `biz_order:amount:view` 权限，否则打码」，并把这两个权限点录进菜单系统。收益/成本比远高于引入完整 ABAC 引擎。
3. **P2：ReBAC 从「监管部门」这一个具体需求起步**（之前挂账的 `sys_user_supervise_dept` 设计），在 `applyDataScope` 里合并 own ∪ supervise；不要一次性做通用关系图。项目协作关系表等真有协作产品再说。

## 五、租户生命周期高级治理

- **按租户导出：无**。`dump-sql.mjs` / `db-backup.service.ts` 全是整库；租户 `remove()` 只软删租户 + 清关系表，业务表（`customer`/`biz_order`/`supplier`）成为无主残留，`tenant.entity.ts:24-26` 注释也承认不物理清业务数据。
- **合并/拆分：无**，且当前业务数据无主残留状态下做迁移风险极高。
- **Feature Flags：只有进程级 env 开关**（`CODEGEN_ENABLED`、`CAPTCHA_ENABLED`、`SWAGGER_ENABLED` 等），`CODEGEN_ENABLED` 甚至没进 `env.validation.ts` 与 `.env.example`。租户级「功能上限」靠菜单套餐，不是通用 flag。

**优化路径（P2）**：特性开关直接复用现有 `sys_config` 两级配置——加 `feature.<name>` 键并设 `allow_tenant=1`，读取走 `SystemConfigService.getBoolean`，零新机制、零新表；比引配置中心划算。**【已实现 2026-11-21】**：`FeatureService` + `@FeatureFlag`/FeatureGuard + `GET /v1/features`，首批消费者 `feature.rbac.superviseDept`（kill switch）与 `feature.log.maskSensitive`（日志脱敏），见 `docs/2026-11-21-特性开关与管辖部门配置控件.md`。按租户导出先做只读 JSON 导出脚本（按 9 张带 tenant_id 的表逐表 WHERE），并且**必须在租户删除前强制导出或提供归档状态**，否则合规客户流失时数据拿不出来。合并/拆分暂不做。

## 六、可观测性与审计增强

- `prom-client` / `/metrics` 无；只有 `/v1/health`（DB/Redis/uptime）和运维页的实时主机采样。`@nestjs/observe` 已接入但 `appKey` 是占位符 `'YOUR_APP_KEY'`，未配置，指标里也没有 tenant 标签（`app.module.ts:118-125`）。
- `RateLimitGuard` 不含租户维度（见一）。
- `sys_log` 有 `tenant_id` + 索引，但**可被 API 删除**（`log.v1.controller.ts:410-424`）、可被 `cleanLogJob` 物理清理；无哈希链、无 WORM、与业务同库。`sys_log_change` 无删除接口但仍同库、失败只 warn。

**优化路径**：先决定观测后端（配置现有 `@nestjs/observe` 还是自建 Prometheus），再加 `tenant_id` 标签；Per-tenant 限流与配额共用一套 key 口径，别做两套。审计防篡改不要一步到区块链——先做「只追加 + 哈希链（`prev_hash` → `SHA256(prev_hash|payload)`）+ 定期校验接口」，并且**先堵住 API 删除与 cron 清理**这两个破坏链的路径，否则链毫无意义。金融/政务客户出现前不必投入。

### 明确不建议现在做

- **引入 BullMQ / 独立 Worker**：当前单进程无队列，新增运维面大于收益；真有邮件/报表重任务时再引，并同步在 job payload 里带 tenantId、processor 首行 `TenantContext.run`。
- **ESLint 禁裸调 `createQueryBuilder`**：非 type-aware 无法判断实体是否带 tenantId，会误伤 55 处合法调用；继续走「安全工厂 + 单测 + CI 隔离冒烟」。
- **审计上链 / 租户合并拆分**：前置条件（停止可删除审计、业务数据无主残留清理）未满足，先做会返工。
