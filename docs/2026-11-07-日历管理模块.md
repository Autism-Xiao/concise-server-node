# 日历管理模块（含定时提醒）

按《日历管理模块功能说明文档 V1.0》落地，技术栈由文档的 Prisma + PostgreSQL 适配为 TypeORM + MySQL 8.4，并修正了原方案的两个设计缺陷（幂等竞态、userId=0 魔法值）。

## 数据模型（迁移 1794100000000）

| 表 | 说明 | 关键设计 |
| --- | --- | --- |
| `base_calendar` | 日历分类（名称/颜色/属主/是否公开） | owner_id 为 varchar(32)（本项目用户主键非自增） |
| `base_schedule_event` | 日程事件 + 提醒字段 | 索引 (user_id,start_time)、(remind_at,is_reminded) |
| `base_schedule_reminder_log` | 站内提醒消息 | **UNIQUE(event_id,user_id)** 防重 + (user_id,is_read) |

与 PRD 的差异：
- `userId` 为创建者（=提醒接收人），取消「0 表示全局事件」的魔法值；公开日历（is_public=1）的事件全员可读
- `remindType` 收缩为仅 `SOCKET`（站内消息），EMAIL/SMS/WEBHOOK 是文档中永远不会实现的分支
- 提醒触发改为**抢权式**（见下），修复 PRD 巡逻示例代码的并发双发 bug

## 接口（/api/v1/schedule，登录即可用，写操作 service 层校验属主）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/calendars` | 我的 + 公开日历 |
| POST/PUT/DELETE | `/calendars[...]` | 日历 CRUD（删除级联清日程+清定时器，事务） |
| POST | `/calendars/ensure-default` | 无日历时自动建「我的日程」（前端首次添加用） |
| GET | `/events?startDate&endDate&calendarId&limit` | 区间查询（月视图），升序，limit≤1000 |
| GET | `/events/:id` | 详情（公开日历可读，私有校验属主） |
| POST/PUT/DELETE | `/events[...]` | 日程 CRUD；创建/修改自动注册提醒；`remindAt` 传 null 取消 |
| GET | `/reminder/list?current&size&isRead` | 站内提醒消息分页 |
| GET | `/reminder/unread-count` | 未读数（顶部红点） |
| PUT | `/reminder/read-all` / `/reminder/:id/read` | 全部/单条已读 |

## 提醒机制（核心）

1. **内存定时器**：原生 `setTimeout`（Map 管理，jobName 即 eventId），创建/修改时注册；`delay > 2^31-1`（>24 天）溢出保护，交巡逻兜底
2. **触发（抢权式幂等）**：`UPDATE base_schedule_event SET is_reminded=1 WHERE id=? AND is_reminded=0`，**affected=1 的一方才落库+抛事件**——定时器与巡逻并发时天然只触发一次
3. **落库防重**：reminder_log `INSERT ... ON DUPLICATE KEY UPDATE`（UNIQUE(event_id,user_id) 兜底）
4. **兜底巡逻**：cron 每 3 分钟扫 `remind_at<=now AND is_reminded=0` 补发；`onModuleInit` 恢复未来提醒（上限 2000）+ 立即巡逻一次
5. **事件广播**：模块内 `ReminderScheduler.emitter` 抛 `schedule.remind.triggered`（含 eventId/userId/title/message/remindType），后续接 WebSocket 实时推送时监听即可；当前无监听者也不影响站内消息

## 前端对接

- 月视图按当月范围查询真实日程，切换月份自动重查
- 点击日期添加（自动建默认日历）；时间留空=全天 09:00-18:00；可勾选「开始前 15 分钟站内提醒」
- 点日程 chip（悬停显示 ×）确认删除
- `remindType` 仅站内消息；未读消息列表/红点接口已就绪，导航栏红点可后续接入 `GET /reminder/unread-count`

## 遇到的坑

1. **用户主键是 varchar(32)**（JeecgBoot 风格非自增），初版按 PRD 用 BIGINT 导致 `Unknown column 'NaN'`——`Number('e9ca...')`=NaN 直拼 SQL。owner_id/user_id 全链路改 varchar(32) 字符串比较
2. TypeORM 1.1：`@Column({ tinyint, width: 1 })` 的 `width` 已不支持；`select` 数组形式与类型不符需对象形式；`find({ select: ['id'] })` 同理
3. ReminderScheduler 构造器漏 `@InjectRepository` → Nest 依赖解析失败，启动即崩
4. 冒烟偶发 FAIL 是限流窗口（全局 120/60s/IP）干扰，隔 65s 重跑即过

## 使用/扩展

- **WebSocket 实时推送**：监听 `ReminderScheduler.emitter` 的 `schedule.remind.triggered` 事件，按 payload.userId 推送（底座已落库，监听者只管实时通道）
- **多实例部署**：当前内存定时器每实例都会触发，但因抢权式 UPDATE，最终只有一方落库成功，消息不会重复；重复的事件广播由监听侧忽略即可（或引入 DB 锁）
- **村居级提醒消息展示**：导航红点接 `GET /v1/schedule/reminder/unread-count`，消息中心接 `/reminder/list`
