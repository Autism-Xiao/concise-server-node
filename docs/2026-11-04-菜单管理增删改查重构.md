# 菜单管理增删改查重构（v1 接口 + 前端对接）

## 背景

菜单表 `sys_permission` 后端 CRUD 原本已有（挂在旧路由 `/api/menus`），但删除是**硬删除**（BaseService 通用 delete），且前端菜单管理页完全挂在 mock（数字 id、按 path 推层级）。本轮按 v1 约定重构。

## 改动

### 后端（concise-server-node）

| 文件 | 类型 | 说明 |
|---|---|---|
| `src/modules/menu/menu.v1.controller.ts` | 新增 | `/api/v1/menus`：tree/list/详情/新增/更新/删除，类级 `@Roles('admin')` + `@OperLog` |
| `src/modules/menu/menu.service.ts` | 重构 | ① `delete` 改**软删除**（del_flag=1）+ **子级保护**（有未删子菜单时拒绝，code 1005）；② `update` 维护 updateTime + **换父级防环**（新父级不能是自己或后代，沿父链向上校验）；③ `create` 校验父级存在 |
| `src/modules/menu/menu.module.ts` | 修改 | 注册 MenuV1Controller |

旧 `/api/menus` 保留兼容。

### 前端（concise-admin）

| 文件 | 类型 | 说明 |
|---|---|---|
| `src/features/system/menu/api.ts` | 重写 | 对接 `/backend-api/v1/menus`：fetchMenus/fetchMenuTree/createMenu/updateMenu/deleteMenu，完整 jeecg 字段（menuType/perms/url/sortNo/status/icon/hidden） |
| `src/features/system/menu/index.tsx` | 重写 | 按 **parentId** 组树（原来是按 path 前缀推层级）；补「类型/权限编码」列；类型筛选（目录/菜单/按钮）；操作按钮包 `hasPermission(system:menu:*)` |
| `src/features/system/menu/components/menu-form-dialog.tsx` | 重写 | 类型切换联动字段（按钮只需名称+权限编码，目录无组件路径）；上级下拉排除自身及后代防环；status 用 '1'/'0' 字符串对齐后端 |
| `src/lib/permissions.ts` | 修改 | mock 兜底的 `Menu` 类型内联为本地 `MockMenu`，解除对 menu/api 的类型耦合 |

## 坑

- BaseService.delete 是硬删除，菜单/部门这类树形表必须覆写（本轮菜单已覆写，部门后续可参照）。
- 删除保护在**后端兜底**（code 1005），前端只做提示，不做级联删除——级联会连按钮权限一起删，风险大。
- 表单里按钮类型（menuType=2）不发 url/component；目录（0）不发 component，避免脏数据。
- `permissions.ts` 的 mock 兜底类型原来从 menu/api 导入，重写后要内联，否则类型对不上。

## 实测（全流程）

```text
新增   测试菜单CRUD → 32位 id、sortNo=99 ✅
更新   改名+改排序 → updateTime 维护 ✅
删除保护 有子按钮时删父级 → code:1005 拒绝 ✅
软删   先删子级再删父级 → 成功，列表无残留 ✅
```

## 使用

前端「菜单管理」页：树形展示（可折叠）、按类型/名称/路由筛选、行内「新增子菜单」；给角色勾 `system:menu:add/update/delete` 控制按钮显隐。新增/修改菜单后用户重新登录生效（菜单树在登录时拉取）。
