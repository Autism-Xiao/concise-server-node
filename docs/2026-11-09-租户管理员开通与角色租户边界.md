# 租户管理员开通与角色/租户边界

> 2026-11-09 · 多租户

## 问题

「多租户下 admin 只有一个」—— 库里的 `admin` 是**平台管理员**（`sys_user.is_platform_admin=1`），它能看所有租户，但每个租户需要自己的管理员时，没有现成入口：

1. 用户名**全局唯一**（`sys_user.username` 唯一键），不能每个租户都建一个叫 `admin` 的账号；
2. 直接在「用户管理」里建号，平台视角下 `resolveJoinTenantId()` 会兜底到默认租户 1 —— 想建到租户 19 得先切租户，容易建错地方。

## 模型（先理清，才能说清怎么用）

| 概念 | 存在哪 | 隔离粒度 |
| --- | --- | --- |
| 账号 | `sys_user` | 全局唯一 |
| 账号归属哪些租户 | `sys_user_tenant` | 多对多 |
| 角色 | `sys_role` | **租户级**（`tenant_id`，0=平台共享） |
| 账号有哪些角色 | `sys_user_role` | 表里有 `tenant_id` 列，但此前**没人写也没人读** |

关键结论：**「租户管理员」不是一个特殊身份，就是「属于该租户 + 绑了该租户的 admin 角色」的普通账号**。平台管理员（`is_platform_admin=1`）才是另一条线，它绕过所有租户校验，全库只有极少数账号该有。

租户的 `admin` 角色是建租户时自动生成的（见 `docs/2026-11-09-租户默认角色模板.md`），`is_builtin=1`，不可删、不可停用，带该租户全部 78 个租户级菜单权限。

## 做了什么

### 1. 新接口：一步开通租户管理员

```
POST /api/v1/tenants/:id/admin
{ "username": "admin_sz", "realname": "深圳管理员", "password": "Sz@123456" }
```

服务端做三件事（`TenantService.createAdmin`）：

1. 校验租户存在（软删的会被 `findOne` 拦掉）
2. 取该租户的 `role_code='admin'` 角色，**没有就报错提示先「同步全部角色」**（空壳租户建管理员会建出一个什么都点不了的号，不如直接拒绝）
3. 用 `TenantContext.withTenant(tenantId, ...)` 包住 `UserService.create()` —— 这一步是必须的：`create()` 内部按「当前租户」写 `sys_user_tenant`，不包的话平台视角下建号会落到租户 1

复用 `UserService.create` 而不是自己写插入：密码哈希、唯一性预检、界面设置行初始化都在里面，重写一遍迟早漏。

角色不用传，固定绑该租户的 admin —— 调用方没有传错角色的口子。

权限沿用 `system:tenant:edit`（platform 作用域），只有平台管理员能开通。

### 2. 补上角色分配时的租户边界（**这是个真漏洞**）

`UserService.assignRoles` 原来是这样：

```ts
const roles = await this.roleRepository.findBy({ id: In(roleIds) })   // 不校验归属
await repo.createQueryBuilder().relation(UserEntity, 'roles').of(id).addAndRemove(toAdd, toRemove)
```

实测证据（修复前）：在租户 19 建一个普通账号，把**租户 1 的 admin 角色** id 传给 `PUT /users/:id/roles`，返回 200；用它登录后拿到 **71 项权限 + 完整菜单树**（含 `system:user:add`）。

原因有两层：

- `assignRoles` 完全不看角色属于哪个租户；
- `PermsGuard` 是拿 `user.roles` 里的 `role_id` 直接去查权限集合的，不认租户。

修复：

```ts
const currentTenant = TenantContext.filterTenantId()
if (currentTenant !== null) {
  const illegal = roles.filter(role => {
    const owner = Number(role.tenantId ?? 0)
    return owner !== 0 && owner !== currentTenant
  })
  if (illegal.length) throw new BadRequestException(`角色「…」不属于当前租户，不能分配`)
}
```

规则：租户视角只能分配「本租户」或「平台共享（0）」的角色；平台视角（`null`）不受限，用于开通租户。

顺带两处修正：

- **无效角色 id 从静默忽略改成 400** —— 原来传错 id 会「成功但少给一半」，最难排查的那种 bug；
- **`sys_user_role.tenant_id` 终于写对了**：关联表改用显式 SQL 写入，记的是**角色归属租户**，不是用户归属。relation API 只能写两列，让它一直留默认值 0 的话，这张表的 `tenant_id` 就永远是废列。

### 3. 权限计算按当前租户收窄（兜底）

`AuthService.getPermissions` 过滤角色时多一层：

```ts
const currentTenant = TenantContext.filterTenantId()
const enabledRoles = (user.roles ?? []).filter(role => {
  if (role.status === 0) return false
  if (currentTenant === null) return true
  const owner = Number(role.tenantId ?? 0)
  return owner === 0 || owner === currentTenant
})
```

历史脏数据（跨租户绑定的关联行）即使还在，租户视角下也不再算数。平台视角仍然看全量。

### 4. 前端入口

租户列表操作列从 4 个图标改成「3 个常用 + 更多」：

| 位置 | 操作 |
| --- | --- |
| 图标 | 分配用户 / 编辑 / 删除 |
| 「更多」下拉 | **开通管理员**、初始化默认角色 |

这样加功能不会把 1280 视口再次挤爆（之前加一个图标就溢出 31px 的教训）。实测 1280 下页面溢出 0、表格内滚 0、操作列 4 个按钮完整可见。

弹窗只收账号/姓名/初始密码，账号占位符按租户编码生成（`admin_default`），并提示「账号全局唯一，建议带上租户编码」。

## 怎么用（给操作者）

**给某个租户开管理员**，两种方式任选：

1. **租户管理页**（推荐）：找到租户 → 操作列「⋮」→ 开通管理员 → 填账号/姓名/密码 → 开通
2. **接口**：`POST /api/v1/tenants/{id}/admin`

开通后：

- 新账号已在 `sys_user_tenant` 里，只属于这一个租户；
- 绑的是该租户的 `admin` 角色（78 项租户级权限，不含任何平台级权限）；
- 它登录后**看不到「租户管理」「菜单管理」「运维监控」**，也不能给自己提平台管理员。

**账号命名**：不能叫 `admin`（已被平台管理员占用），建议 `admin_<租户编码>`，如 `admin_sz` / `admin_cs`。

## 已知边界

- **一个账号在多个租户下使用不同角色，当前不支持**。`assignRoles` 是「全量覆盖用户的所有角色」，不分租户；`getPermissions` 也是汇总全部（过滤掉不属于当前租户的）。要支持得把 `assignRoles` 改成「按当前租户这个维度覆盖」，前端角色表单也要按租户回显 —— 这是另一件事，先记在这里。
- 实际影响不大：给每个租户开独立管理员账号（本方案）就能满足绝大多数场景。
- `sys_user_role.tenant_id` 现在写对了，但**读的地方只有 `getPermissions` 这一处兜底**；`PermsGuard` 仍按 `role_id` 查权限。源头 `assignRoles` 已校验，正常路径不会串。

## 遇到的坑

1. **`TenantService` 注入 `UserService` 会不会循环依赖**：`UserModule` 不 import `TenantModule`，单向依赖安全；`PermissionCacheService` / `AuthUserCacheService` 都是 `@Global`，不用再 import。
2. **`TenantContext.withTenant()` 会重设 `isSuper`**：传 19 时 `isSuper=false`。确认过 `create` 路径不用 `isSuper`（只有 menu/role service 用），不会误伤。
3. **`smoke-tenant.mjs` 的 cleanup 直接 `DELETE FROM sys_tenant`**，绕过 `remove()` 的级联删除，又造出 3 个孤儿角色。已补：先删角色的授权与角色，再删租户，顺带清 `sys_user_role` / `sys_user_setting`。
