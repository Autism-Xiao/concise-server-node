# 列表筛选全面改为服务端（关键字 / 状态 / 排序 / 分页）

## 背景

审计结论：全站列表只有「文件管理」是真服务端分页，其余页面都是 `useDataTable`（TanStack 客户端模式）先按 `pageSize: 100/500/全量` 拉一批，再本地 `getFilteredRowModel` 过滤 + 本地分页。后果有三：

1. **超过拉取上限的数据在界面上根本不存在**（用户列表 800 人只显示前 500，搜索也搜不到）。
2. 搜索「看起来能用」是因为样本小，数据一多就变成假搜索。
3. 排序只排当前这批，翻页后顺序错乱。

本轮把列表页的关键字/状态/排序/分页全部下推到接口，前端只负责把参数发出去和渲染返回值。

## 关键设计

### 1. 排序走白名单，不做「传什么排什么」

`applySort(qb, alias, query, allow)` 只认白名单里的**前端列 id**，映射到**实体属性名**再 `orderBy`。命不中就静默回落默认排序 —— 好处是前端列 id 与数据库列名解耦（`notice.title` 的库列名是历史上拼错的 `titile`，但实体属性是 `title`），也不会因为随便传个字段名拼出 `ORDER BY` 注入面。

命中排序列后一律**补 `addOrderBy(id)`** 兜底：排序列有重复值（比如状态只有两个值）时，MySQL 的 `LIMIT/OFFSET` 在并列行之间不保证稳定顺序，翻页会出现同一行重复出现 + 另一行永远看不到。

### 2. 导出必须和列表共用同一个 QB 构造方法

各 service 都抽出了 `buildXxxQuery(query)`，`listByQuery` 分页取、`exportXxx` 全量取（仍保留上限截断）。如果导出另写一份 where，列表加了 keyword 而导出没加，就会出现「页面上筛了 3 条，导出的 Excel 是 300 条」这种口径漂移。

### 3. 前端 `useServerTable` 的三个易错点

- **防抖 + 竞态**：300ms 防抖后请求，每个请求带自增序号，只有最新序号的响应才落地。否则慢的旧请求会覆盖新结果（表现是「搜 A 出 B」）。
- **换关键字必须回第 1 页**：`pageIndex` 不重置的话，搜「张」时停在第 5 页，而结果只有 1 页 → 空白列表。
- **删空最后一页要自动回退**：删除最后一条后 `pageIndex` 仍在旧页，`pageCount` 变小 → TanStack 不会自己纠偏。

`filters` 用 `JSON.stringify` 比较内容而不是比引用，否则页面每次渲染新建一个对象字面量都会触发请求。`query` 函数放进 ref，避免调用方没 memo 时无限请求。

### 4. 小表为什么不全上 `useServerTable`

角色/岗位/职级/租户/字典/部门这些页面需要**整棵树或整组数据**（分组表头、树形展开、下拉选项），分页会把结构切碎。所以它们的做法是：数据仍一次全量取回，但**关键字交给后端**（`manualFiltering` 置空 `globalFilter` 不参与本地行过滤，`onKeywordChange` 触发重新请求）；状态下拉这类列筛选（`columnFilters`）继续走本地 —— 全量数据在内存里，本地筛更快也不必多发请求。

## 踩的坑

1. **DTO 相对路径层数**：`src/modules/role/dto/` 只上溯 3 层到 `src/`，写成 `../../../../common/dto/pager.dto` 会 `tsc` 报 `has no properties in common with SortQuery` —— 报错信息完全指不到 import 路径上。
2. **`Pagination` 是值不是类型**：`role.service.ts` 里要 `new Pagination(...)`，写成 `import type` 会报 `cannot be used as a value`。
3. **`toPagination` 只在 controller 用**：service 改返回 `Pagination` 后 controller 里的 `toPagination` 变成未使用，eslint 直接红。
4. **前端接口返回类型没跟着改**：`biz_order` / `customer` 的 api 仍声明 `{ records, total }`，缺 `current/size/pages` 报类型错；页面里 `bizOrders.length` 也要换成 `total`。
5. **`useServerTable` 泛型用了 `Record<string, unknown>`**：`ChangeLogQuery` 这种 interface 没有索引签名，赋不进去。放宽成 `TFilters = Record<string, never>`。
6. **`useDataTable` 第一版把 `getFilteredRowModel` 一起删了**：状态列筛选当场失效。正确做法是只置空 `globalFilter`。
7. **ref 写法触 eslint**：`useRef(() => {})` 报 `Unexpected empty arrow function`，渲染期 `reloadRef.current = reload` 报 `Cannot access refs during render`。改成 `useRef<(() => void) | null>(null)` + `useEffect` 里赋值 + 调用处 `reloadRef.current?.()`。
8. **日志「清空」没有按条件清空的接口**：原实现是清掉整个筛选结果，改成分页后只能删当前页，按钮语义已改成「清空当前页」。
9. **小表加了分页参数反而容易翻车**：字典改成真分页后默认只回 10 条，`smoke-tenant.mjs` 里按全量断言的 3 条检查直接红。脚本里补 `?pageSize=100`。
10. **冒烟脚本自身的统计口径也要跟代码一起改**：`smoke-tenant.mjs` 的「平台共享字典条数」用裸 SQL `WHERE tenant_id = 0` 统计，没有 `del_flag = 0`，历史软删行（当时 4 条）被算成「共享」，而接口只返回 8 条 → 断言 `len=8 共享=12` 长期是脚本的问题不是代码的问题。教训：**冒烟里的期望值尽量从接口取，或至少与接口用同一套过滤条件**。

## 如何扩展

**新增一个可排序列**（以公告为例）：

```ts
// 1. service 的白名单里加映射：前端列 id -> 实体属性名
const NOTICE_SORTABLE: Record<string, string> = { title: 'title', createTime: 'createTime', /* 新增 */ status: 'status' }
// 2. 前端表格列定义里把 id 写成同一个 key，并给 enableSorting（TanStack 默认就有）
```

不需要改 DTO、controller、前端 hook —— `sortBy/sortOrder` 是所有 `PagerDto` 子类天然带的。

**新增一个走服务端筛选的列表页**：

1. 后端 DTO 继承 `PagerDto`，service 里抽 `buildXxxQuery(query)`，`listByQuery` 用 `paginate(qb, { page, pageSize })`，导出复用同一个 QB。
2. 前端 api 声明 `(query: XxxQuery) => Promise<PageResult<T>>`，页面用 `useServerTable({ query, pageSize, filters })`，`filters` 里只放真正要下推的字段。
3. 加断言到 `scripts/smoke-server-list.mjs` 的接口列表里，跑一条 `pageSize=2` 翻页查重即可覆盖大部分回归。

**判断该用哪个 hook**：数据结构是「平铺列表」→ `useServerTable`；页面需要「整棵树 / 整组 / 下拉全量」→ `useDataTable` + `manualFiltering` + `onKeywordChange`。
