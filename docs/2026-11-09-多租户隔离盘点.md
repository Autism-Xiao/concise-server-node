# 多租户隔离盘点：哪些该隔离、哪些不该

> 本文是**盘点分析**，不含代码改动。结论基于当前 `src/` 实际代码与 26 张实体表逐一核对。
> 目的是给出一把可复用的尺子，而不是逐表拍脑袋决定。

## 零、一句话结论

- 26 张表里，**11 张业务表已隔离**、**1 张关系表天然带租户**、**14 张不隔离**（其中 9 张合理、5 张是漏洞）。
- 真正的问题不是「该隔离的没隔离」，而是两件更底层的事：
  1. **「平台管理员」和「租户管理员」没有分开** —— `isSuper` 用全局 `role_code` 判定，导致租户管理员等同于平台超管，且能切进任意租户。
  2. **裸 SQL 绕过了隔离层** —— 首页概览、站内信「我的消息」直接写 `dataSource.query` / 手拼 join，没走 `applyTenantScope`，读到了别的租户的数据。

先修这两件，收益远大于给某张表补 `tenant_id`。

---

## 一、判定原则：一张表要不要隔离，只问四个问题

按顺序问，命中即停。这套判定和 JeecgBoot 的 `TenantLineInnerInterceptor` 思路一致，也和本项目 `tenant-scope.util.ts` 的「`0` = 平台共享」对齐。

| # | 问题 | 命中含义 | 落点 |
| --- | --- | --- | --- |
| 1 | 这行数据是**某个租户的业务资产**吗？（删了别的租户不该受影响） | 必须隔离 | 加 `tenant_id`，走 `BaseService` 自动读写隔离；`tenant_id=0` 保留给「内置示例数据」 |
| 2 | 它是**所有租户共用的只读/平台配置**吗？ | 不隔离 | 单表全局（`sys_region`、`sys_permission`），或全局配置单行 |
| 3 | 它是**「人」的全局身份**吗？（一个人可同时属于多个租户） | 不隔离 | 身份表不挂租户，用关系表（`sys_user_tenant`）表达归属 |
| 4 | 它是**「人」的个人偏好**且与当前租户无关吗？ | 不隔离 | 跟人走（`sys_user_setting`、`sys_user_watermark`） |

**反向原则**：隔离粒度不是越细越好。「能不能被租户管理员改」比「有没有租户字段」更重要 —— 一个全局单行配置（如 `sys_watermark_setting`）如果谁都能改，那就是跨租户越权，比不隔离更糟。

## 二、现状盘点

### A. 已隔离（11 张业务表 + 1 张关系表）

走 `BaseService` 的自动隔离（读过滤 + 写打标），或 `applyTenantScope` 手动补条件。

| 表 | 业务语义 | 隔离方式 | 判定 |
| --- | --- | --- | --- |
| `sys_role` | 角色 | BaseService | ✅ 对 |
| `sys_depart` | 部门 | BaseService | ✅ 对 |
| `sys_position` | 岗位 | BaseService | ✅ 对 |
| `sys_level` | 职级 | BaseService | ✅ 对 |
| `sys_dict` | 字典类型 | BaseService | ✅ 对（内置字典落 `tenant_id=0` 共享） |
| `sys_dict_item` | 字典项 | BaseService | ✅ 对 |
| `sys_announcement` | 通知公告 | BaseService | ✅ 对 |
| `task` | 任务 | BaseService + 手写 QB 补条件 | ✅ 对 |
| `supplier` | 供应商 | BaseService | ✅ 对 |
| `sys_message` | 站内信主体 | 手写 `applyTenantScope` | ✅ 对（但「我的消息」有漏，见 P1-4） |
| `sys_file` | 文件 | 手写 `applyTenantScope` | ✅ 对（但首页统计有漏，见 P0-3） |
| `sys_user_tenant` | 用户—租户归属 | 本身就是关系表 | ✅ 对 |

### B. 不隔离且**合理**（9 张）

| 表 | 为什么不该隔离 | 对应原则 |
| --- | --- | --- |
| `sys_tenant` | 租户本体，平台级数据。给它加 `tenant_id` 是循环定义 | 2 |
| `sys_user` | 全局身份。一个人可属于多个租户，隔离了就没法跨租户共用账号；归属靠 `sys_user_tenant` + `login_tenant_id` | 3 |
| `sys_permission` | 菜单/按钮定义是**代码资产**，不是租户资产。租户差异应该体现在「角色授了哪些菜单」，不该各租户复制一份菜单树 | 2 |
| `sys_region` | 行政区划，国家数据，全平台只读共享 | 2 |
| `sys_user_setting` | 界面偏好（主题色/字号/布局）。切租户不该变主题色（本项目明确决定） | 4 |
| `sys_user_watermark` | 用户自己的水印开关，跟人走 | 4 |
| `tool_storage` | 存储后端配置（OSS 账号）。平台级基础设施 | 2 |
| `sys_quartz_job` | 定时任务是运维配置，跑在进程级，不属于业务租户 | 2 |
| `sys_message_user` | 消息已读状态，靠 `(message_id, user_id)` 天然收敛 | 3 |

> 这 9 张不是「漏了」，是**明确决定不隔离**。后续谁想给它们加 `tenant_id`，先回答：加了之后，A 租户改主题色会不会影响 B 租户？（不会 → 不该加）

### C. 不隔离但**有问题**（5 张）

| 表 | 问题 | 严重度 |
| --- | --- | --- |
| `sys_log` | 审计日志无 `tenant_id`，租户 A 的审计员能看到租户 B 的操作明细（`params` 里可能带业务数据） | P1 |
| `sys_watermark_setting` | 全局单行表，A 租户管理员改水印 = 改全平台所有租户 | P1 |
| `base_calendar` / `base_schedule_event` / `base_schedule_reminder_log` | 只有 `userId` 维度。同一用户在 A、B 两个租户的日程混在一起，且日程标题往往含客户名/项目名 | P1 |
| `sys_message_user` | 表本身可以不加租户，但「我的消息」查询没按 `m.tenant_id` 过滤 → 跨租户消息可见 | P1 |
| `sys_dict` 的共享语义 | `tenant_id=0` 内置字典是共享的，但**共享字典可被任意租户读取**是设计意图；风险在于任何租户能否**修改** `tenant_id=0` 的行需要确认 | P2 |

## 三、P0：先修这四件（都是「绕过隔离」而非「少个字段」）

### P0-1 租户管理员 = 平台超管（最严重）

**位置**：`src/shared/tenant/tenant-access.service.ts:61`、`:78-87`

```ts
const isSuper = roles.some(role => ['admin', 'superadmin'].includes(role.roleCode))
```

`role_code` 是**全局**概念，但 `sys_role` 是**租户级**表。后果：

1. 平台把 `admin` 角色分给某租户的用户 → 该用户 `isSuper = true`。
2. `resolveTenant` 走超管分支：**带了 `X-Tenant-Id` 就进那个租户，只校验租户存在且可用，不校验归属**（`assertTenantUsable` 只查 `sys_tenant`，不查 `sys_user_tenant`）。
3. 也就是说：任何被授予 `admin` 角色的租户用户，只要请求头写 `X-Tenant-Id: 2`，就能读到租户 2 的全部数据。
4. 更隐蔽的一层：超管**不带**请求头时 `tenantId = null` → `tenantCondition` 返回 `null` → 所有 `BaseService` 查询完全不过滤 → 全库可见。前端 localStorage 里 `concise-tenant` 为空（新浏览器/清缓存）就会出现这个状态。

**修法**（推荐，改动最小）：

- `sys_user` 加 `is_platform_admin tinyint default 0`，只有平台运营账号为 1；
- `isSuper` 改为读这个字段，**不再看 role_code**；
- `resolveTenant` 对非平台管理员**永不返回 `null`**：没有可用租户时返回 `0`（只看共享数据），而不是 `null`；
- `assertTenantUsable` 对非平台管理员额外校验 `sys_user_tenant` 归属（现在是超管分支才跳过校验，非超管分支已有校验，改完就一致了）。

### P0-2 `role_code` 全局唯一，租户建不了自己的 `admin`

**位置**：`src/modules/role/entities/role.entity.ts:23`（`unique: true`）

- 租户 B 想建一个自己语义的 `admin` 编码 → 撞 A 租户（或平台）的唯一键；
- 软删角色仍占坑，删了重建同名编码会失败。

**修法**：唯一键改 `(tenant_id, role_code)` 联合唯一；同时把「`admin` 是内置角色不可删」的保护从 `roleCode === 'admin'` 改成 `is_builtin` 标记位（否则 B 租户的 `admin` 会被误判为平台内置角色）。

### P0-3 首页概览裸 SQL 全部没带租户条件

**位置**：`src/modules/dashboard/dashboard.service.ts`

| 行 | SQL | 后果 |
| --- | --- | --- |
| 150 | `FROM sys_log WHERE log_type=0 AND operate_user_name=?` | 按账号取最近登录，同账号跨租户时取到别的租户的登录记录 |
| 183 | `FROM sys_log ... 今日登录` | 登录成功率是**全平台**口径，租户 A 看到 B 的失败次数 |
| 212 | `FROM sys_log ... 登录趋势` | 同上 |
| 249 | `FROM sys_log WHERE log_type=1` 最近操作 | **租户 A 能看到 B 的操作明细**（含操作人、IP） |
| 194 | `SELECT COUNT(1) FROM sys_role` | 「角色数」是全平台角色数，不是本租户的 |
| 273 | `FROM sys_file WHERE owner_id=?` | 同一用户跨租户，存储用量把 B 租户的文件算进来 |
| 296 | `FROM task WHERE assignee_id=?` | 同上 |
| 313 | `FROM sys_announcement WHERE send_status='1'` | **租户 A 首页显示 B 的公告**（公告表本身是有 `tenant_id` 的，这里没加条件） |

**修法**：`DashboardService` 注入后统一拼租户条件。建议抽一个 `tenantSql(alias)` 返回 `{ clause, params }`（等价于 `tenantRawCondition` 的字符串版），裸 SQL 一律走它。**公告块最优先**，它是唯一会影响用户可见内容的。

### P0-4 用户列表跨租户暴露 PII

**位置**：`src/modules/user/user.service.ts:459`（`scopedQuery`）

用户是全局身份（正确），但「用户管理」页在租户 A 下应该只列**属于 A 的用户**。现在 `scopedQuery` 只有 `del_flag` + `data_scope`，没有租户维度 → 租户 A 的管理员能翻到全平台用户（手机号、邮箱、部门）。

**修法**：`scopedQuery` 增加 `EXISTS (SELECT 1 FROM sys_user_tenant ut WHERE ut.user_id = user.id AND ut.tenant_id = :tenantId)`；平台视角（`tenantId === null`）不加。首页 `countScoped` 复用同一个方法，口径自动一致。

> 注意：这条与 P0-1 联动。P0-1 不修，这个过滤可以被「切到平台视角」直接绕过。

## 四、P1：二期处理

### P1-1 `sys_log` 补 `tenant_id`

登录/操作日志是**审计数据**，天然按租户归属。现在 A 租户的审计员权限（`system:log:*`）能看到全平台日志。

- 加列 `tenant_id INT NOT NULL DEFAULT 1`（存量按 `operate_user_id` 的 `login_tenant_id` 回填，回填不到给 1）；
- 写入侧两个入口：`AuthService.login` 与 `OperLogInterceptor`，都要从 `TenantContext.currentTenantId()` 取值；
- 查询侧 `LogService` 加 `applyTenantScope`，导出同样；
- 索引：现有索引基础上补 `(tenant_id, log_type, create_time)`。

### P1-2 `sys_watermark_setting` 改成租户级

单行表 `id=1` 的假设在单租户下成立，多租户下就是跨租户越权。两种改法：

- **轻**：主键改 `tenant_id`（或 `(tenant_id, id)`），`tenant_id=0` 存平台默认，租户首次修改时 copy 一行；
- **重**：拆「平台策略」+「租户策略」两张表，`resolveWatermarkState` 的优先级再加一层。

建议轻方案，`resolveWatermarkState` 的判定链再加一级：`租户策略 ?? 平台默认`。

### P1-3 日程三张表补 `tenant_id`（或明确「日程跨租户共享」）

`base_schedule_event.user_id` 是唯一归属。同一用户在 A、B 两租户的日程会混。若产品上不接受，加 `tenant_id`；若接受（日程属于「我这个人」而非「这个租户」），就在文档里**明写**，别再当成 bug 反复讨论。

> 这类「跟随人」的表，多租户系统里必须二选一并写进文档。个人意见：日程跟人（和 `sys_user_setting` 同类），因为日程标题是用户自己写的个人事务，不属于租户资产。

### P1-4 站内信「我的消息」/ 未读数补租户过滤

`message.service.ts:139`、`:171`：`where('mu.userId = :userId')` 没有 join 条件过滤 `m.tenant_id`。同一用户跨租户时，A 租户能看到发给「我」但属于 B 租户的消息。

修法：列表 join 加 `AND m.tenant_id IN (:tenantId, 0)`；未读数改为子查询 `message_id IN (SELECT id FROM sys_message WHERE ...)`。

### P1-5 平台级权限没有二级划分

`/v1/tenants` 用的是 `@Perms('system:tenant:*')`。权限来自角色，角色由租户管理员自己编辑 → 租户管理员可以给自己授 `system:tenant:add`，从而创建/删除租户。

同类还有：`system:menu:*`（改菜单就改了全平台路由）、`system:log:delete`（删全平台日志）。

**修法**：权限项加 `scope` 维度（`platform` / `tenant`），`PermsGuard` 里对 `platform` 权限额外要求 `is_platform_admin`。这依赖 P0-1 先把身份拆干净。

## 五、明确**不做**的事（避免反复返工）

| 想法 | 结论 | 理由 |
| --- | --- | --- |
| 给 `sys_user` 加 `tenant_id` | ❌ 不做 | 退化成「一人一租户」，跨租户协作/统一运维账号全废。JeecgBoot 同样用关系表 |
| 给 `sys_permission` 加 `tenant_id` | ❌ 不做 | 菜单是代码资产，各租户复制会导致升级时 100 份菜单树要同步 |
| 给 `sys_user_setting` 加 `tenant_id` | ❌ 不做 | 主题色切租户不该变（已有明确决定） |
| 给 `sys_dict_item` 的内置项加租户 | ❌ 不做 | 内置字典 `tenant_id=0` 共享正是设计意图 |
| 每个租户独立数据库 | ⏸ 暂不做 | 当前是共享库 + 行级隔离。真要做需重写 `DataSource` 路由层，属于架构级项目 |

## 六、建议落地顺序

**一期（P0，安全底线）**

1. `sys_user.is_platform_admin` + `resolveTenant` 兜底（不返回 `null`）+ `assertTenantUsable` 归属校验
2. `role_code` 唯一键改 `(tenant_id, role_code)`
3. 首页裸 SQL 全部补租户条件（公告块优先）
4. `scopedQuery` 补 `sys_user_tenant` 子查询

**二期（P1，审计与配置）**

5. `sys_log.tenant_id` + 写入/查询/导出三处
6. `sys_watermark_setting` 租户级化
7. 站内信 mine/unreadCount
8. 日程：决定「跟人」还是「跟租户」并写进文档

**三期（P1-5，权限分层）**

9. 权限项 `scope` 维度 + `PermsGuard` 平台校验

## 七、验收清单（每期改完照着跑）

- 租户 A 的 `admin` 角色用户，带 `X-Tenant-Id: 2` → **403**
- 租户 A 的 `admin` 用户，不带 `X-Tenant-Id` → 落 `tenant_id=A` 或 `0`，**绝不返回全库**
- 租户 A 首页：公告、角色数、最近操作、登录趋势 → 与 B 完全无交集
- 租户 A 用户列表 → 只出现 A 的用户（B 的用户查不到，且 404 而非 403，不泄漏存在性）
- 审计员账号（只有 `system:log:*`）在 A 租户 → 日志列表只看得到 A
- 已隔离的 11 张表：`GET /v1/<资源>?current=1&size=100` 在两租户下 `total` 不同且互不包含

## 附：本轮改动

无代码改动，纯盘点。产出的表分类与 P0 清单可直接拆成工单。

**遇到的坑**（记录给后来人）：

- 判断某张表是否隔离，别只看实体有没有 `tenantId` —— `sys_message_user` 没有，但它靠外键收敛，本来就是对的；`sys_log` 也没有，但它是漏的。要看**查询路径有没有绕过 `BaseService` / `applyTenantScope`**。
- `grep -c tenantId` 在实体上会把 `sys_user_tenant` 数出 2 次（`tenantId` 列 + 注释），别当成两个列。
- 首页/报表类 `dataSource.query` 是隔离的天然盲区：写的时候都在 `Service` 里手拼 SQL，很容易忘。建议后续把「裸 SQL 必须带租户条件」写进 code review 检查项。
