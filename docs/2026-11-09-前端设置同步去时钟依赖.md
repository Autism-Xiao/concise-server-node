# 前端设置同步：去掉跨时钟比较

> 修的是上一轮遗留的隐患（`loadSettings()` 里 `remote.updatedAt || Date.now()`）。
> 纯前端改动，仓库 `concise-admin`，后端无变化。

## 一、原来错在哪

```ts
// 旧代码
if (remote && (!local || remote.updatedAt >= local.updatedAt)) return persistLocal(remote.settings, remote.updatedAt || Date.now())
```

两个问题叠在一起：

1. **两个时间戳来自不同时钟**：`local.updatedAt` 是客户端 `Date.now()`，`remote.updatedAt` 是服务端写库时间。
   机器时钟偏快 1 小时（很常见）时，云端的新值永远小于本地基准 → **云端更新被永久忽略**。
2. **云端没有时间戳时写入了客户端当前时间**：`|| Date.now()` 让「服务端从未改过」变成「本地刚刚改过」，
   把错误基准固化进 localStorage，后续再也不会接受云端值。

复现路径：设备 A 时钟快 → 首次登录拿到默认值并把 `now+1h` 写成基准 → 在设备 B 改主题色（服务端时间真实）
→ 回到设备 A，仍显示旧主题，且刷新不恢复。

## 二、改法：用 `dirty` 表达「本地有未同步改动」

不再比时间，只回答一个问题：**本地有没有没推上去的修改？**

| 状态 | `dirty` | 加载时 |
| --- | --- | --- |
| 用户改了设置、推送成功 | false | 以云端为准 |
| 用户改了设置、推送失败/离线 | true | 以本地为准，界面显示「未同步」，可点重试 |
| 从云端回写本地 | false | 下次仍以云端为准 |
| 老版本快照（无该字段） | 按 false | 以云端为准 |

代码点：

- `SettingsSnapshot` 增加 `dirty?: boolean`；`updatedAt` 降级为「仅诊断/首帧缓存」，**不参与比较**；
- `persistLocal(settings, updatedAt = Date.now(), dirty = true)`：默认「用户改动」语义；
  从云端回写必须显式 `false`；
- 新增 `markSynced(settings)`：推送成功后清标记。**带内容比对** —— 推送是异步的，回调到达时用户可能
  又改了一版，若直接清 `dirty` 会把新改动当成已同步、永不重推；
- `loadSettings()`：`local.dirty` → 本地；否则云端 → 本地 → 默认值。

## 五、行为变化与坑

1. **老用户升级后第一次加载可能被云端覆盖**：老快照没有 `dirty` 字段，按「已同步」处理。
   如果该用户之前在本地改过、但从未推送成功，这次会被云端值替换。做了取舍：不这样处理，
   老用户会永远压着云端不更新（旧代码给几乎所有快照都写了 `Date.now()`，无法区分「改过」与「只是加载过」）。
2. **`dirty=true` 会一直压着云端**：这是刻意的 —— 改动确实还没上去。界面有「未同步」状态与重试入口，
   不要为了「看起来已同步」去无条件清标记。
3. **多标签页**：标签 A 改动后本地 `dirty=true`，标签 B 刷新读到的就是 `dirty` → 以本地为准，不会互相打架；
   但两个标签同时改仍会「后写覆盖」，属于既有行为，本轮不处理。
4. 首帧样式缓存（`concise-settings-css`）与 `index.html` 内联脚本读的仍是 `settings` 字段，
   localStorage 结构只多了一个 `dirty`，向后兼容。
