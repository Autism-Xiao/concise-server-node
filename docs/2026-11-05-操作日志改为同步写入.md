# 操作日志改为同步写入（消除 observe 未完成 span 告警）

## 背景

启动日志里出现这样一条 warn：

```
warn [OperationTraceRegistry] Trace "01a1ab58-…" (/api/v1/auth/logout) was reported without
"LogService#recordOper", "Repository#save", "mysql2#INSERT sys_log",
which had not ended 1000ms after the operation did.
Some of your async operations were not awaited and outlived the operation that started them.
```

它来自项目已启用的 `@nestjs/observe`（`app.module.ts` 里的 `ObserveModule.forRoot`），不是业务报错。含义是：这条 HTTP trace 已经结束，但它内部启动的「操作日志写库」链路在 1 秒后仍没有结束标记 —— 判定为**有异步操作没有 await，生命周期超出了启动它的请求**。

## 根因

`src/common/interceptors/oper-log.interceptor.ts` 原先用 `tap` + `void` 写日志：

```ts
tap({
  next: () => {
    void this.logService.recordOper({ ... })   // 故意不 await
  }
})
```

`tap` 是同步副作用，返回的 Promise 不会被 RxJS 等待，于是：

1. HTTP 响应先返回，trace 收尾；
2. 日志 INSERT 之后才开始，span 结束事件已经没有归属；
3. observe 在 trace 结束后等 1000ms 取快照，发现还有 start 状态的 span → 打 warn。

附带的真实代价：进程在 INSERT 完成前退出会丢最后几条操作日志；可观测性里这些请求永远显示「有未完成的 span」。所有写请求（POST/PUT/DELETE/PATCH）都会触发，`/api/v1/auth/logout` 只是最容易注意到的一个。

## 改了什么

| 文件 | 类型 | 说明 |
| --- | --- | --- |
| `src/common/interceptors/oper-log.interceptor.ts` | 修改 | `tap` + `void` 改为 `concatMap` 等待日志落库；`catchError` 写失败日志后重新抛出原异常；新增 `resolveErrorMessage` 提取可读错误信息 |

### 1. 成功路径用 concatMap 等日志写完

```ts
concatMap(async (data: unknown) => {
  await this.logService.recordOper({ status: 0, ... })
  return data
})
```

`concatMap` 会等返回的 Promise resolve 后才把值往下游发，因此响应返回时日志已经落库，span 也在 trace 内正常结束。`recordOper` 内部本身有 `try/catch`，日志写失败不会污染业务响应，也不需要额外包裹。

### 2. 失败路径先记录再抛原异常

```ts
catchError((error: unknown) =>
  from(this.logService.recordOper({ status: 1, errorMsg: resolveErrorMessage(error).slice(0, 255), ... })).pipe(
    mergeMap(() => throwError(() => error))
  )
)
```

注意必须是 `throwError(() => error)` 而不是 `throwError(error)`：后者在 rxjs 7+ 已废弃，且只接工厂函数。原异常原样抛回全局异常过滤器，前端拿到的错误结构、HTTP 状态码都不变。

### 3. 顺带修好失败日志只有 "Bad Request Exception" 的问题

原来 `error?.message` 对 `BadRequestException` 永远只有 `Bad Request Exception`，`BizException` 更是连业务文案都拿不到（文案在 `getResponse()` 里）。新增：

```ts
function resolveErrorMessage(error: unknown): string {
  const response = error?.getResponse?.()
  const raw = response && typeof response === 'object' ? response.message : undefined
  const message = Array.isArray(raw) ? raw.join('；') : raw
  if (typeof message === 'string' && message) return message
  const fallback = error?.message
  return typeof fallback === 'string' && fallback ? fallback : '未知错误'
}
```

- `ValidationPipe` 的多条错误 → 用「；」拼成一行
- `BizException` → 取 response.message 里的业务文案
- 都取不到时退回 `error.message`，再兜底「未知错误」

## 验证结果

用签发 JWT 的方式绕过登录（admin 密码已改），起在 `PORT=3463`：

| 场景 | 结果 |
| --- | --- |
| `POST /api/v1/auth/logout` 成功 | 201，34ms，响应返回时 `sys_log` 里已能查到该条记录 |
| `POST /api/v1/users` 传空 body 失败 | 400 + `code:1001`「用户名长度须在 3~100 位之间」，错误结构与改前一致 |
| 失败日志内容 | `用户名长度须在 3~100 位之间；username must be a string；…`（不再是 `Bad Request Exception`） |
| 服务日志 | 启动后执行上述请求，`warn` 一条都没有（旧版本同样操作必现） |

响应耗时增加约一次 INSERT 的时间（本机 1~5ms，实测 logout 全程 34ms），可以接受。

## 坑

- `throwError` 在 rxjs 7+ 从 `'rxjs'` 导出，不在 `'rxjs/operators'`；写成后者会直接 `TS2305: has no exported member 'throwError'`。
- 不要用 `mergeMap` 代替 `concatMap` 做日志写入：`mergeMap` 只保证并发发起，不保证顺序，同一请求内多条日志的落库顺序会乱。
- `@nestjs/observe` 未连接时（appKey/appSecret 还是占位符）**依然会做本地 trace 检查并打 warn**，所以不能用「没连上 observe 就不会告警」来判断。
- 全局拦截器注册顺序是 `TransformInterceptor` → `OperLogInterceptor`，日志等待发生在响应包装内层，不会影响统一响应结构。

## 扩展与回退

- **只想对慢接口豁免**：可在 `intercept` 里按 `request.path` 白名单直接 `return next.handle()`，等于不记该接口的操作日志。
- **想彻底回到 fire-and-forget**：把 `concatMap` 换回 `tap` + `void` 即可，但 observe 的 warn 会重新出现，且进程异常退出时可能丢日志 —— 不建议。
- **想让日志更细**：`recordOper` 的入参 `OperLogInput` 已支持 `errorMsg`、`costTime`，如需记录响应体可在 `concatMap` 里对 `data` 脱敏后追加字段。
