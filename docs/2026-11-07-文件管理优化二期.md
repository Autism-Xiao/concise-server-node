# 文件管理优化二期：磁盘治理 + 回收站/移动/预览

**日期**：2026-11-07
**仓库**：backend（concise-server-node）+ frontend（concise-admin）
**前置**：[文件管理落地（P0）](./2026-11-07-文件管理落地.md)

## 背景

P0 把文件管理从 mock 切到了真实接口，功能能用了，但自己盘了一遍代码发现三类问题：

1. **磁盘只增不减**：覆盖上传会漏旧文件、回收站没有保留期、tmp 目录没人清 —— 而 2G 配额只统计 `is_deleted = 0`，等于只管账面不管磁盘；
2. **数据会出现同名的两条记录**：从回收站恢复时不查重名；
3. **功能缺口**：后端 `recycled/restore/purge` 早就有，前端一个都没接 —— 删了文件在界面上无法恢复。

这一轮把这三类一起修掉。

## 一、磁盘治理（后端）

### 1. 覆盖上传漏文件

`PUT`-style 的 `onConflict=overwrite` 分支原先是「替换 `storage_key` 然后保存」，旧 key 指向的物理文件从此没有任何记录引用，但也没人删它 —— **每覆盖一次漏一份磁盘**，界面上完全看不出来，只有 `du -sh storage` 会慢慢涨。

抽出 `removeStorageIfUnused(storageKey)`：

```ts
private async removeStorageIfUnused(storageKey: string | null | undefined): Promise<void> {
  const key = storageKey?.trim()
  if (!key) return
  const stillUsed = await this.fileRepository.count({ where: { storageKey: key } })
  if (stillUsed > 0) return                       // 同一份内容还被别处引用，不能删
  await fs.promises.unlink(this.absolutePath(key)).catch(() => undefined)
}
```

`purge`（彻底删除）与 `upload`（覆盖）共用这一个出口，避免两处各写一套引用计数。

### 2. 回收站没有保留期

配额算的是 `is_deleted = 0`，回收站不占账面但**占磁盘**。没有保留期策略的话，用户只要「删了不彻底删」，磁盘就能无限涨。

新增 `FileCleaner`（`file.cleaner.ts`，`cron` 包，每天 03:30）做两件事：

| 任务 | 配置 | 行为 |
|---|---|---|
| 超期回收站清理 | `FILE_RECYCLE_DAYS=30` | 查 `is_deleted=1 AND deleted_at < now-N天`，按 owner 分组走 `purge()`（连带物理文件） |
| 残留临时文件清理 | `FILE_TMP_HOURS=24` | 删 `storage/tmp` 下 mtime 超期的文件 |

两个配置 **<= 0 表示关闭**（不想自动删就配 0）。

细节：

- 单轮上限 1000 条，积压多时分多轮消化，避免一次性把内存/连接占满；
- `onModuleInit` 里先 `void this.sweep()` 扫一次再挂 cron —— 本地开发经常是「关终端就重启」，只等凌晨 3:30 可能永远等不到；
- 清理失败只记日志不抛（清理任务不该把应用搞挂）。

### 3. 残留临时文件

`upload()` 的 `finally` 会删掉临时文件，但**客户端中途断开**、**进程被强杀**时没人收尸。multer 的 `diskStorage` 已经把字节写在 `storage/tmp` 里了，只能靠定时任务兜底（即上面第 2 项的第二段）。

### 4. 恢复时不查重名

场景：删掉 `报告.pdf` → 同目录又传了一份 `报告.pdf` → 从回收站恢复 → 同目录出现**两条同名记录**，之后重命名/移动的查重会一直报「已存在」。

`restore()` 现在先对「要恢复的记录 + 一并恢复的父链」逐条查同目录是否已有未删除的同名，冲突的走 `uniqueName` 自动改名，返回 `{ restored, renamed }` 让前端提示「其中 N 项因重名自动改名」。

### 5. 配额校验的并发窗口

原逻辑是「`SELECT SUM(size)` → 判断 → INSERT」，三步之间没有锁也没有事务，两个并发上传都能读到旧值、双双通过。

改成两段式：

- **前置**：冲突先判（`skip` 直接返回，不必算配额），再算增量 —— 覆盖上传的增量是 `size - 旧文件大小`，不是整个 `size`（否则 100MB 覆盖 100MB 会被误判空间不足）；
- **后置**：写库后 `assertQuotaAfterWrite` 再核一次 `SUM`，超额就 `delete` 掉刚写的记录 + 清盘 + 抛 400。

代价是并发打满时后完成的那次会被撤销并提示重试 —— 比长期超配额、磁盘被撑爆好。没上 `SELECT ... FOR UPDATE` / `GET_LOCK`：`sys_file` 没有「用户行」可锁，命名锁又要固定连接（queryRunner），为一个概率极低的场景引入连接级锁不划算。

## 二、下载与预览（后端）

### 6. Range 断点续传

原来只设 `Content-Length` + `StreamableFile`，视频拖动进度条会从头重下、断线无法续传。

现在解析单区间 `Range`：

| 请求 | 响应 |
|---|---|
| 无 Range | 200 + 全量 |
| `bytes=0-1023` | 206 + `Content-Range: bytes 0-1023/total` |
| `bytes=-500`（最后 500 字节） | 206 |
| 越界 / 非法 | 416 + `Content-Range: bytes */total` |

始终返回 `Accept-Ranges: bytes`。多区间（`bytes=0-1,5-6`）不处理，按整文件返回。

### 7. 在线预览 `GET /v1/files/:id/preview`

只放行三类，其余 400 让前端退回下载：

| 类型 | 放行条件 | 返回 |
|---|---|---|
| 位图 | 扩展名在白名单 **且** 文件头 `detectImageSignature` 认出真身 | 真实 mime（png/jpeg/gif/webp/bmp），`inline` |
| PDF | 文件头 `%PDF` | `application/pdf` |
| 纯文本 | `txt/md/json/csv/log/yml/yaml/xml/ini/conf` | 统一 `text/plain; charset=utf-8` |

安全取舍：

- **SVG 不放行**：XML 文本能内嵌 `<script>`，inline 渲染就是同源 XSS；
- **不信扩展名、不信库里的 mime**（都是上传时可伪造的），必须读文件头验真 —— 否则「.png 里装 HTML」就能执行；
- 文本统一 `text/plain` + `X-Content-Type-Options: nosniff`，即使内容真是 HTML 也不会被解析；
- 图片/文本额外加 `Content-Security-Policy: default-src 'none'`；**PDF 不加** —— 交给浏览器内置阅读器，加 CSP 在部分版本会白屏。

## 四、验证

`scripts/smoke-file.mjs` 扩到 **39 项，全通过**（新增 11 项）：

```
PASS  Range 返回 206 / 响应头 bytes 0-3/30 / 内容为前 4 字节
PASS  越界 Range 返回 416
PASS  文本预览 200 / inline + text/plain
PASS  伪装图片被拒预览（.png 里装 HTML → 400）
PASS  不支持的类型拒绝预览（zip → 400）
PASS  覆盖前物理文件存在 / 覆盖复用同一条记录
PASS  覆盖后旧物理文件已清盘 / 新物理文件存在
PASS  删除后可重新建同名 / 恢复时重名自动改名（renamed:1）/ 恢复后名字带序号
```

覆盖清盘的断言是**直接读磁盘**的（`fs.existsSync(storagePath(key))`），所以脚本必须和后端同机跑。

跑法：

```powershell
$env:SMOKE_BASE="http://127.0.0.1:3461/api"
node scripts/smoke-file.mjs
```

目标实例要关验证码：`PORT=3461 CAPTCHA_ENABLED=false node dist/main.js`。

## 五、坑

1. **`fs.promises.open` 读文件头**：预览验真只读前 16 字节，别用 `readFileSync` —— 200MB 的视频会把内存打爆。
2. **`blob.slice(0, 200KB).text()`**：文本预览只截前 200KB，几十 MB 的日志整段塞进 DOM 会卡死页面。
3. **`revokeObjectURL` 要在清理函数里做**：`objectUrl` 声明在 `useEffect` 内层闭包，cleanup 才能拿到；写成外层 state 会导致关闭弹窗后内存不释放。
4. **覆盖上传的增量**：`used + size` 是错的，要 `used + size - 旧大小`，否则「用 100MB 覆盖自己的 100MB」会被判空间不足。
5. **`assertQuotaAfterWrite` 不能用在覆盖分支**：覆盖是复用原记录，删记录 = 丢文件；所以覆盖走精确增量前置判断，只有新建路径才允许「撤销本次写入」。
6. **Range 的 `bytes=-500`**：`-` 前面为空表示「最后 N 字节」，不是「从 0 开始」，解析时要单独分支。
7. **PDF 不设 CSP**：加了 `default-src 'none'` 后部分 Chrome 版本内置阅读器直接白屏。
8. **`recycled` 接口不支持 keyword**：前端搜索框在该视图下禁用，别让用户输入后没反应。

## 六、如何扩展

- **回收站前端已有，只差「清空回收站」**：批量 `purge` 已支持，加一个「清空」按钮即可（注意二次确认）。
- **文件夹打包下载**：`archiver` 流式 zip，别一次性读进内存；注意 zip 内路径要按逻辑目录重建。
- **秒传**：`hash` 索引已建，缺 `POST /files/check-hash`；前端用 WebWorker 算 sha256，命中就直接建记录。
- **缩略图**：`jimp` 已在依赖里，可在上传时生成 256px 缩略图另存一份，列表页用它替代原图。
- **部门共享**：`dept_id` 字段已预留；要做得把 `list/findOneOrFail` 的 owner 过滤放宽成「owner 或同部门共享」，并补共享关系表 —— 注意配额归属会跟着变复杂。
- **清理任务的保留期做成可配置界面**：目前只能改 `.env`，`sys_config` 表已有的话可以挪过去热更新。
