# 锁屏状态服务端化（Redis）：关机重开不再"解锁"

## 背景

锁屏标志原来存 `sessionStorage`（`concise-locked`），关标签页/关机就没了；而登录凭证存在 `localStorage`，重开系统后自动恢复登录态 → `isLocked() === false` → **直接进工作区，锁屏形同虚设**。`lib/lock-screen.ts` 头注释里「关闭标签页自动解锁（重新打开需要重新登录）」的假设不成立——凭证是持久的，不会要求重新登录。

方向对比（讨论结论）：
- **本地改 localStorage**：一行改动，能挡「误关机」，但 F12 删 key 即绕过，本质仍是前端自说自话；
- **Redis 存服务端标志（采用）**：锁屏防的是「人不在座位时旁人操作」，只要 UI 渲染的是服务端事实，本地篡改就没有意义。换设备/清缓存/关机重开全部拦得住，且解锁必须走后端、可审计、将来能做强制锁屏/无操作自动锁等策略。

## 设计

- `POST /v1/auth/lock`：`SET lock:screen:<userId> 1 EX 86400`。**TTL 24h 是自愈兜底**——锁屏后没解锁就关机，到期自动解除，不会把人永久锁在门外（`SCREEN_LOCK_HOURS` 可覆盖，下限 300s）。
- 解锁复用 `POST /v1/auth/verify-password`：校验通过后端**顺带 DEL 标志**，前端无需再发请求；连错 5 次锁账号的计数逻辑原样复用。
- `GET /v1/auth/lock-state`：前端启动时以结果纠正本地标志。
- 退出登录必须清标志（按令牌 payload 的 userId DEL），否则换人登录同一账号会被锁屏挡在门外。
- **语义按 userId 不按设备**：A 电脑锁屏，B 电脑同账号一并锁。锁屏防的是「人不在」，不是「这台机器」；且不用维护会话维度。
- 前端 sessionStorage 保留为**瞬时镜像**（锁屏期间快捷键静默等高频判断不发请求），状态源是服务端。

## 踩的坑

1. **fail-open 是刻意的**：锁屏状态查询任何失败（Redis 未启用/连接断开/超时）都按「未锁」处理 + warn 日志。锁屏是防君子不是硬安全（接口本来都有鉴权），不能重蹈「验证码强依赖 Redis 挂掉 → 登录页死局」的覆辙。锁屏 POST 失败同理：本地会话照样锁住，只是不持久化。
2. **启动期竞态**：页面刚打开就发 lock-state 请求，如果用户在这条请求回来之前点了锁屏，迟到的 `{locked:false}` 会把刚锁上的屏又盖掉。用 `interactedRef`（用户本会话碰过锁就跳过服务端纠正）解决。
3. **登出必须清标志**：锁标志按账号维度，不清的话换人登录同一直接被锁屏挡住（有「回到登录」按钮兜底，但体验不对）。
4. **TTL 下限 300s**：`Math.max(..., 300)` 防止配置成 0 或负数把锁屏变成一闪而过。
5. **不要在 `me`/登录响应里塞 `screenLocked`**：me 的消费方很多且可能被缓存，独立 lock-state 接口让前端启动期一次轻量查询就能对齐，语义清晰。

## 验证

- 后端编译、eslint 通过；前端 `tsc -b`、eslint 通过。
- 3461 实例端到端：初始 `locked:false` → lock → `locked:true, persisted:true` → 错密码标志仍在 → 对密码 verify-password → `locked:false` → 再锁 → logout → 重新登录 → `locked:false`（登出清标志）。
- Redis 实测键 `lock:screen:<adminId>` 写入/删除正常。
- 回归：smoke-server-list 24/0、smoke-dashboard 60/60、smoke-tenant 30/0、`npm test` 全过。

## 如何扩展

- **无操作自动锁屏**：前端定时器（可配置）到点调 `POST /v1/auth/lock`，服务端逻辑零改动；
- **管理员强制锁屏**：管理接口直接写 `lock:screen:<userId>`，被锁端下次启动/刷新即被拦；
- **强制锁屏策略开关**：`sys_config` 加一项（allow_tenant=1 可租户级开放），登录响应带 `screenLocked` 时前端直接进锁屏；
- TTL 与语义都不用动：策略变化只影响「谁写标志」，读取端已经统一。
