# 首页入口改回动态菜单（仪表盘不再固定挂在搜索上方）

## 背景

上一轮《确认弹窗通用化与侧边栏去重》为了解决「侧边栏出现两个仪表盘」，采取了**剔除菜单树里的 `/dashboard` 节点 + 顶部固定入口**的方案。
固定入口放在 `SidebarContent` 第一个 `SidebarGroup` 里，视觉上就落在「搜索」上方，与其它页面入口的层级不一致；同时
菜单管理里改「仪表盘」的名称、排序、分组都不会生效（因为渲染的是硬编码项）。

本轮改为**完全由后端菜单树渲染**：`/dashboard` 和其它菜单走同一条路径（排序、分组、改名都由「菜单管理」决定），
固定入口删除，搜索按钮保留在最上方（它是动作不是路由）。

## 改了哪些文件

| 文件 | 类型 | 说明 |
| --- | --- | --- |
| `src/modules/auth/services/auth.service.ts` | 修改 | 新增 `HOME_MENU_URL` 常量与 `withHomeMenu()`；`getPermissions()` 的超管分支、按角色分支都过一遍，保证菜单树里一定有首页节点 |
| `concise-admin/src/components/layout/app-sidebar.tsx` | 修改 | 删除顶部固定仪表盘入口；`visible()` 恢复渲染 `/dashboard`；静态回退分支对 `HOME_PATH` 放行；`dynamicGroups` 增加「树里没有首页节点则注入一个」的兜底 |
| `concise-admin/src/lib/home-path.ts` | 修改 | 注释重写：首页入口走动态菜单，不再是「前端固定入口」 |

## 每个东西是干什么的

### 后端 `withHomeMenu(menus, allMenus)`

`getPermissions()` 是按角色算菜单树的地方（前端登录后 `GET /v1/auth/permissions` 拿它渲染侧边栏）。新增的收尾步骤：

1. 递归检查树里有没有 `url === '/dashboard'` 的节点，有就直接返回；
2. 没有则从 `allMenus`（已过滤 `del_flag = 0`、`status = '1'`）里找 `/dashboard` 的非按钮节点，`unshift` 到树顶；
3. 菜单表里找不到该节点（被停用/删除）就不注入 —— 运维可以主动关掉首页菜单。

超管分支（`permissions: ['*']`）同样走一遍，虽然超管本来就能拿到全表，但这样两个分支行为一致，不用记「只有普通角色才会被补节点」。

### 前端 `app-sidebar.tsx`

- **删掉的**：`SidebarContent` 里第一个 `SidebarMenuItem`（`/dashboard` 固定链接）。搜索按钮留在原来的 `SidebarGroup`（`pb-0`），成为菜单区最上面一行。
- **`visible()`**：上一轮加的 `menuPath(n) !== HOME_PATH` 去掉，否则后端下发了也渲染不出来。
- **静态回退分支**（`menuTree === null`，未登录/接口未返回时短暂出现）：不再过滤 `/dashboard`；权限判定改成 `allowed(url)`，首页直接放行，其余照旧看 `permitted`。
- **`dynamicGroups` 兜底**：遍历分组（含二级）看有没有 `/dashboard`；没有就塞一个无名分组到最前面，`label` 用 i18n 的 `nav.dashboard`。这是给**改动前已登录的会话**准备的 —— 菜单树存在 `localStorage.concise-menus`，只在登录时写入，线上老会话里没有刚注入的节点，兜底负责让它们刷新就能看到入口。

侧边栏最终顺序（admin 实测）：

```
[搜索]
仪表盘 | 任务 | 应用 | 聊天     ← 无标题分组（顶层无子级的叶子菜单）
系统管理  ▸
运维管理  ▸
```

## 遇到的坑

1. **两处过滤要一起清**：上一轮在 `visible()` 和静态分支各剔了一次 `HOME_PATH`，只清一处会出现「动态菜单里没仪表盘、静态菜单里有」的错位。
2. **注入必须覆盖两个分支**：只在「按角色」分支补节点时，超管看不出来问题，但新建角色（没勾选仪表盘）登录后侧边栏没有首页入口 —— 这类角色恰恰是最需要点的。
3. **localStorage 缓存**：`concise-menus` 只在登录时写入，后端改了注入逻辑，已登录用户不刷新就拿不到新树。前端兜底是必须的，不能指望用户重新登录。
4. **oxlint `no-misused-spread` 的 inline disable 位置**：写在 `return [{ ...home, children: [] }, ...menus]` 上一行**不生效**（数组字面量里的 spread 仍被报）；先把对象赋给变量，再在变量声明上一行 disable 才行。
5. **`npm run restart` 可能被 safe-delete 拦**：`nest build` 要清 `dist`（717 个文件），批量删除会触发 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`，整条命令失败但 `&&` 后面的启动没跑，表现为「改完代码行为没变」。正确姿势：先单独 `npm run build`，再 `node scripts/serve.mjs`。
6. **验证脚本取值**：统一响应已是 `{ code, message, result, success, timestamp }`，登录 token 在 `result` 而不是 `data`，写 `body.data` 会拿到 undefined。

## 怎么用 / 怎么扩展

- **改首页的名称/图标/排序/位置**：系统管理 → 菜单管理 → 编辑 `menu_35`（仪表盘）。`sort_no = 1` 排第一；想让它进某个分组，把 `parent_id` 改成那个目录；改 `name` 侧边栏立刻跟着变。
- **新建角色**：不用勾「仪表盘」，后端会自动补节点；如果业务上确实要禁止某类角色看首页，把 `menu_35` 停用（`status = '0'`），注入就会跳过，但前端兜底仍会补一个 —— 想彻底关掉要连前端 `_home` 兜底一起改（`app-sidebar.tsx` 的 `dynamicGroups`）。
- **加第二个常驻入口**（比如「帮助中心」）：不要重复加固定 `SidebarMenuItem`，在 `sys_permission` 里建节点即可，后端按角色授权或参照 `withHomeMenu` 补节点，前端无需改代码。
- **验证方式**：登录后看 `GET /api/v1/auth/permissions` 的 `result.menus[0].url` 是否为 `/dashboard`；再用一个没有该菜单授权的角色登录，同样应出现在第一位。

## 验证结果

- 后端接口实测（临时账号赋 `editor` 角色，该角色未授权 `menu_35`）：
  - admin 顶层菜单：仪表盘、任务、应用、聊天、系统管理、运维管理（`sort_no` 升序）
  - editor 顶层菜单：仪表盘（注入）、系统管理（已授权）
  - 注入节点 `menuType = 0`、`children = []`、`name = '仪表盘'`，不带按钮子级
- `tsc -b`（前端）/ `tsc --noEmit`（后端）零错误；eslint 零告警；oxlint 0 warning；前端 `node --test` 7/7 通过。
- 后端 jest：3 个 suite 通过、`excel-export.spec.ts` 仍报 `ERR_REQUIRE_ESM`（该文件用 `require` 加载，属既有问题，与本次改动无关）。
