# 千万级用户性能评估：能不能扛住，差在哪，怎么改

> 日期：2026-11-09 ｜ 类型：性能压测 + 架构评估 ｜ 结论：**当前状态不能，但不是必须推倒重来**

## 一、结论先说

| 问题 | 回答 |
| --- | --- |
| 现在的代码结构支持千万级用户吗？ | **支持**。应用层完全无状态（JWT + Redis 会话），加实例就能横向扩，不需要改架构 |
| 现在的数据库能扛千万级用户吗？ | **不能**。用户管理列表页在 1000 万行下实测**超时 > 90 秒**，关键字搜索 **> 120 秒** |
| 单机最多能扛多少请求？ | 实测单进程 **200~370 RPS**（视接口而定），加机器线性提升 |
| 改造成本大吗？ | 三个索引/查询层面的改动就能把列表页从 **>90 秒降到 0.9 毫秒**，不需要换数据库 |

一句话：**代码底子是对的（无状态 + 有 Redis + 有权限缓存），欠的是数据库查询设计和部署形态**。补齐 5 处，千万级用户可行。

## 三、第一组：真实接口并发压测（当前数据量：用户 194）

每档 6 秒，`c` = 并发数，RPS = 成功请求/秒。

| 接口 | c=1 | c=5 | c=20 | c=50 | c=1 的 p50 |
| --- | --- | --- | --- | --- | --- |
| `GET /auth/permissions`（登录后菜单树） | 114 | 183 | 191 | 202 | 8.6 ms |
| `GET /dashboard/overview`（首页 11 个块） | 5 | 23 | 87 | 172 | 215.6 ms |
| `GET /users`（用户列表） | 156 | 227 | 216 | 247 | 6.3 ms |
| `GET /users&keyword=zhang` | 167 | 241 | 252 | 272 | 5.8 ms |
| `GET /notices/published` | 252 | 376 | 454 | 408 | 3.8 ms |
| `GET /regions/children/440000` | 282 | 399 | 472 | 482 | 3.3 ms |
| `POST /auth/login`（含 Argon2 校验） | 54 | 138 | 163 | 165 | 18.1 ms |

4 线程客户端 100 并发复核（排除客户端瓶颈）：

| 接口 | RPS | p50 | p95 |
| --- | --- | --- | --- |
| `GET /users` | 235 | 420 ms | 455 ms |
| `GET /auth/permissions` | 201 | 481 ms | 534 ms |
| `GET /dashboard/overview` | 160 | 593 ms | 735 ms |
| `GET /notices/published` | 366 | 262 ms | 335 ms |

**读数**：并发从 1 加到 100，RPS 只从 ~115 涨到 ~235，而 p50 线性恶化到 420ms —— 典型的**服务端已饱和**（不是客户端打不上去）。单进程能力就在 200~370 RPS。

**为什么只有 200 多 RPS**：每个已登录请求都要走
`限流(Redis) → JWT 校验(1 次 MySQL 查用户+角色 + 1 次 Redis MGET 黑名单 + 1 次 Redis SETEX 续期) → 业务查询`，
而连接池只有 **10**。`/users` 一个请求还要再跑 7 条 SQL（COUNT + 分页 + 部门/角色/岗位/职级/水印 5 次 attach）。

`/dashboard/overview` 的 215ms 基线不是数据库慢，是 `getServerInfo` 内部**固定 200ms CPU 采样**——每个请求都要等 200ms，这个设计在千万级下必须改成「后台定时采样 + 接口只读缓存」。

## 四、第二组：数据量压测（核心结论）

真实业务 SQL 在 100 万 / 1000 万行下的表现（毫秒，取最快一次）：

| 查询（对应真实接口） | 100 万行<br>（原索引） | 100 万行<br>+复合索引 | 1000 万行<br>（原索引） | 1000 万行<br>+复合索引 |
| --- | --- | --- | --- | --- |
| 登录：`username = ?` | **0.4** | 0.5 | **4.5** | **0.6** |
| JWT 校验：`id` 主键 | **0.4** | 0.4 | **1.0** | **0.6** |
| 列表：`COUNT(*) WHERE del_flag=0` | 1,470 | 1,291 | 18,479 | **17,807** ❌ |
| **列表第 1 页**（`ORDER BY create_time DESC LIMIT 10`） | **11,701** ❌ | **0.4** ✅ | **>90,000 超时** ❌ | **0.9** ✅ |
| 列表第 100 页（`OFFSET 990`） | 11,448 | 5.0 | >90,000 超时 | 8.7 |
| 关键字搜索 COUNT（`LIKE '%zhang%'`） | 10,543 | 11,001 | >90,000 超时 | **>120,000 超时** ❌ |
| 关键字搜索取页（`LIKE '%1000%'`，命中 1000 行） | 9,950 | 406 | >90,000 超时 | 8,703 ❌ |

> 复合索引 = `KEY idx_del_ct (del_flag, create_time)`，1000 万行上创建耗时 **56 秒**。

**三个硬结论**：

1. **登录和鉴权天然没问题**（唯一索引 + 主键，千万行仍是亚毫秒级）—— 这是最容易被担心、实际最不用担心的一环。
2. **列表第一页是致命伤**：`sys_user` 上**没有 `create_time` 索引**，`ORDER BY create_time DESC LIMIT 10` 要对全部匹配行做 filesort。加 `(del_flag, create_time)` 后从 **11.7 秒 / 超时 → 0.9 毫秒**（一万倍），说明这只是设计问题，不是数据量问题。
3. **即使加了索引，`COUNT(*)` 和 `LIKE '%kw%'` 依然废**：
   - `COUNT(*)` 是 O(n) 索引扫描，1000 万行 **17.8 秒**，而它现在**每翻一页都要算一次**；
   - `LIKE '%kw%'` 前导通配无法用索引，千万行下 **> 2 分钟**。

## 五、瓶颈清单（按严重程度）

| 级别 | 问题 | 证据 | 修法 |
| --- | --- | --- | --- |
| **P0** | 用户列表 `ORDER BY create_time` 无索引 | 1000 万行 > 90 秒 | 加 `(del_flag, create_time)` 复合索引（实测 0.9ms）|
| **P0** | 每页都算 `COUNT(*)` 精确总数 | 1000 万行 17.8 秒 | 取消总数 / 缓存 30~60s / 用「是否有下一页」的 keyset 分页 |
| **P1** | 关键字 `LIKE '%kw%'` 全表扫描 | 1000 万行 > 120 秒 | 改前缀匹配 `kw%`（可走索引）+ 姓名用全文索引；再大就上 ES/Meilisearch |
| **P1** | 每个请求查 1 次用户库 + 2 次 Redis，连接池仅 10 | 单进程 200~370 RPS 就饱和 | 用户身份缓存（Redis/in-process，TTL 30~60s）、连接池按实例调到 20~30、会话续期改成惰性（每 N 秒才写一次）|
| **P1** | 单进程部署，无线程/实例扩展 | RPS 到 235 就不再涨 | PM2 cluster / K8s 多副本 + Nginx 负载，前面加 Redis 共享会话（已具备）|
| **P2** | `innodb_buffer_pool_size=128MB`（默认） | 千万行表 7.4GB，命中率极低 | 按内存 50~60% 调，如 16GB 机器设 8~10GB |
| **P2** | 首页固定 200ms CPU 采样 | p50 恒 215ms | 后台每 30s 采一次写 Redis，接口只读 |
| **P2** | 一个列表请求 8 条 SQL（5 次 attach） | `/users` p50 在 c=50 时 420ms | attach 合并成 1~2 条 JOIN/批量 IN 查询 |

## 六、要撑千万级用户，需要什么

**容量估算**（1000 万注册用户，日活 5%~10% = 50~100 万）：

| 指标 | 估算 | 依据 |
| --- | --- | --- |
| 峰值 QPS（读为主） | 3,000 ~ 6,000 | 100 万日活 × 人均 200 次页面请求 / 峰值集中 6 小时 |
| 单库承载用户表 | 可（7.4GB / 千万行，SSD + 8GB buffer pool 足够） | 本次实测 |
| 应用实例数 | 15 ~ 30 个（每个 200~370 RPS） | 实测单实例上限 |
| 连接池总连接 | 15 实例 × 25 = 375（MySQL 默认 max_connections 151 **不够**） | 需同步上调 |

**分三步走**：

### 第一步：单库优化（做到百万用户级 / 数千并发）— 成本最低，收益最大

1. 加索引：`sys_user(del_flag, create_time)`、`sys_oper_log(create_time)`、`sys_user_depart(dep_id, user_id)`
2. 列表去掉每页 `COUNT(*)`，改「加载更多 / 是否有下一页」
3. 关键字搜索改前缀匹配 + 全文索引
4. `innodb_buffer_pool_size` 调到物理内存 50%
5. 连接池 10 → 25

做完后：千万行列表页 ~1ms，单机可支撑 **1,000+ RPS**。

### 第二步：水平扩展（做到千万用户级 / 万级并发）

1. 应用多副本（PM2 cluster 或容器多实例）+ Nginx
2. 会话/限流/权限缓存全部走 Redis（**已经具备**，只是要确认没有进程内状态依赖）
3. 首页仪表盘改为定时任务预聚合 + 读缓存
4. 数据库读写分离（主写从读），列表/报表走从库
5. 大表分区：`sys_log`、`sys_oper_log` 按时间分区或归档

### 第三步：真要冲亿级才需要

分库分表（按 tenant_id / user_id 哈希）、搜索引擎独立集群、对象存储、消息队列削峰、单元化部署。

## 七、我现在就可以动手的改动（按性价比排序）

1. **加 3 个索引的迁移**（`sys_user`、`sys_oper_log`、`sys_user_depart`）—— 改动小、风险低、收益最大
2. **用户列表去掉精确总数**，换成「共约 N 人（缓存）+ 是否有下一页」
3. **关键字搜索改前缀匹配**，`realname` 加 MySQL 全文索引（ngram 分词，中文可用）
4. **用户身份缓存**（JWT 校验时 30s 缓存 user+roles），把每请求 1 次 DB 查询打掉
5. **首页 CPU 采样**改后台定时 + 缓存，p50 从 215ms 降到 ~15ms

这 5 项做完，同一个 4 核 8G 的机器从 200 RPS 能到 **1,500~2,000 RPS**，列表页在千万数据下仍是毫秒级。

node .tmp-bench.mjs

# 4) 数据量测试：造 100 万行
#    CREATE TABLE concise_bench.sys_user LIKE concise_server.sys_user;

## 九、注意事项

- 本次所有数据量测试都在**独立库 `concise_bench`**，测完已 DROP，主库 `concise_server` 未受影响。
- 这台机器 MySQL 用默认 128MB 缓冲池，真实服务器调大后，所有"无索引"数字会好看一些（预计 3~5 倍），但**结论不变**：`COUNT(*)` 和 `LIKE '%kw%'` 在千万行下仍然不可接受。
- 压测时关闭了限流，线上是 `120 次/分钟/IP/接口`，真实场景下这个限制会先于性能瓶颈生效。
