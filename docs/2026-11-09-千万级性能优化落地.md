# 千万级性能优化落地：索引 / 去 COUNT / 前缀搜索 / CPU 后台采样

> 日期：2026-11-09 ｜ 类型：性能优化实施 ｜ 前置报告：[2026-11-09-千万级用户性能评估](./2026-11-09-千万级用户性能评估.md)
> 结论：评估报告里「按性价比排序」的 5 项，除第 4 项（用户身份 30s 缓存 + 连接池 20 + 压缩，远端 `ae227fe` 已完成）外，其余 4 项本轮全部落地。

## 一、一句话结果

| 优化项 | 改动前（实测） | 改动后（实测） | 数据量 |
| --- | --- | --- | --- |
| 用户列表第 1 页（排序 + 分页） | > 90 秒（无合适索引，filesort 全表） | **0.33 ms** | 100 万行 |
| 用户列表每页 `COUNT(*)` | 17.8 秒 | 直接不发（skipCount）／发的话 358 ms | 1000 万 / 100 万行 |
| 关键字搜索（不命中） | > 120 秒（`LIKE '%kw%'` 全表扫） | **0.3 ms**（ASCII）／**0.12 ms**（中文） | 1000 万 / 100 万行 |
| 首页 `GET /dashboard/overview` p50 | 216 ms（每请求固定 200ms CPU 采样） | **31 ~ 54 ms** | 本机开发库 |

> 1000 万行的 >90 秒 / >120 秒 / 17.8 秒来自上一轮报告；本轮没有再造 1000 万行表（那一次 7.4GB、跑完即删），
> 用 100 万行验证「索引是否被真正用上」，两者是同一套索引，耗时随行数近似线性。

## 三、每一项在干什么

### 1. 索引：为什么是 `(del_flag, create_time)`

列表 SQL 是 `WHERE del_flag = 0 ORDER BY create_time DESC LIMIT 10`。
优化前 `sys_user` 上只有 `idx_su_del_flag(del_flag)` 这种**低基数单列索引**（del_flag 只有 0/1），
MySQL 认为用它筛完还要 filesort，不如直接全表扫 + 排序 —— 千万行就是 90 秒起。

复合索引 `(del_flag, create_time)` 让「先按 del_flag 等值定位，再沿 create_time 倒序读」一次完成，`LIMIT 10` 一凑够就停：

```
EXPLAIN SELECT id FROM sys_user WHERE del_flag=0 ORDER BY create_time DESC LIMIT 10;
type=ref  key=idx_user_del_create  Extra=Backward index scan; Using index
```

`(del_flag, realname)` 是给搜索用的（见第 3 项）。`sys_user_depart(dep_id, user_id)` 让「按部门筛人」的
`EXISTS (SELECT 1 FROM sys_user_depart ud WHERE ud.user_id = user.id AND ud.dep_id IN (...))` 走覆盖索引，不再回表。

### 2. 去掉每页 `COUNT(*)`

`COUNT(*)` 在 InnoDB 上是**全索引扫描**，跟数据量线性增长，而且**每翻一页都要重算一次**。
但列表页其实只需要知道「还有没有下一页」。

现在 `paginate(qb, { count: false })` 走快路径：`LIMIT pageSize + 1` 取回来，多出来一条就说明 `hasNext = true`，
返回 `total = -1`、`pages = -1`。

契约上这是**显式的「不知道」**，不是 0：前端拿到 `-1` 必须换文案（本轮已改），任何脚本判 `total === 0` 都要注意。

### 3. 前缀搜索 + 按字符集分流（本轮最反直觉的一处）

第一层：`%kw%` → `kw%`，否则索引完全用不上。

第二层（**实测才发现**）：只改成前缀还不够。三列 OR 一起写 `(username LIKE 'kw%' OR realname LIKE 'kw%' OR phone LIKE 'kw%')`，
优化器**不做 index_merge**，而是选 `(del_flag, create_time)` 顺序扫描逐行判断 —— 关键字命中率高时看不出问题（59ms），
一旦不命中就是 3.4 秒（100 万行全扫一遍）。1000 万行就是 30 秒以上。

100 万行实测（`SET profiling=1`）：

| 写法 | 耗时 |
| --- | --- |
| `username OR realname OR phone` 三列前缀 OR（不命中） | 3.38 s |
| `username OR phone` 两列前缀 OR（不命中） | **0.30 ms** |
| `realname` 单列前缀（不命中） | **0.12 ms** |

所以 `user-search.util.ts` 按字符集分流：

- 关键字**全 ASCII**（`/^[\x20-\x7e]*$/`）→ 只查 `username, phone`。用户名正则本来就禁止中文，手机号是纯数字。
- 关键字**含中文** → 只查 `realname`。
- `USER_SEARCH_MODE=contains` → 回退到原来的三列 `%kw%`（慢，只用于排障）。

**取舍**：英文姓名（`realname = 'John Smith'`）用 ASCII 关键字搜不到，得搜账号。这是为了千万级场景做的明确取舍，不是 bug。

顺带修了一个隐患：关键字里的 `\` / `%` / `_` 现在会转义。原来用户输入 `_` 等于「任意字符」，既慢又能把不该出现的人带出来。

### 4. CPU 采样后台化

`getServerInfo()` 原来每次调用都 `await 200ms` 做两次 `os.cpus()` 差值 —— 首页概览是常驻页面，
每点一次刷新就白等 200ms。现在改成 `onModuleInit` 起一个 5 秒定时器采样，结果写进 `cpuUsage`，接口直接读。

`node dist/main.js` 之外被 import 时（冒烟脚本、单测）定时器会拖住进程，所以必须 `unref()`。

实测首页：`p50 216ms → 31~54ms`，「系统状态」卡片里的 CPU 仍会每 5 秒变化（不是写死的常量）。

## 四、踩到的坑

1. **`CREATE INDEX` 不吃 `ALGORITHM=INPLACE, LOCK=NONE`**
   先写成 `... (cols) ALGORITHM=INPLACE, LOCK=NONE COMMENT '...'` → `ER_PARSE_ERROR`（COMMENT 必须在 ALGORITHM 之前）；
   调成 `COMMENT '...' ALGORITHM=INPLACE, LOCK=NONE` → 还是报错在 `, LOCK=NONE`（两个 option 之间不能用逗号）。
   最后**干脆不写**：MySQL 8 对普通二级索引默认就走 Online DDL（INPLACE + LOCK=NONE），显式写只是自找麻烦。

2. **单事务灌 100 万行 + `KILL` = 20 分钟锁表**
   一个大事务 `INSERT ... SELECT` 扫笛卡尔积，跑了 679 秒没完，`KILL` 之后 InnoDB 回滚 undo 用了 **1180 秒**，
   期间表被锁住，后续每批 `INSERT` 全部 `ERROR 1205 Lock wait timeout`、行数一直是 0。
   正确做法：**分批提交**（10 万行/批，实测 7 秒/批），既快又不会留下巨型回滚。

3. **`typeorm migration:show` 的 `[ ]` 不可信**
   它按迁移 `name` 比较，而历史迁移类名带数字前缀（`AddUserBio1794160000000`）与数据库记录不完全一致，
   于是 6 个早就执行过的迁移仍显示 `[ ]`。以 `migration:run` 输出的「N migrations are new」为准。

4. **`Pagination.pages` 不能直接 `Math.ceil(total / size)`**
   `total = -1` 时算出 `-0`，序列化后是 `-0`，前端判 `< 0` 会漏。必须显式 `total < 0 ? -1 : Math.ceil(...)`。

5. **前端把 `total = -1` 直接渲染**
   原来文案是 `共 {total} 个用户`，跳过统计后会显示「共 -1 个用户」。现在按三态判断，见改动表。

6. **索引迁移必须幂等**
   MySQL 没有 `CREATE INDEX IF NOT EXISTS`。线上库可能已人工加过同名索引，
   不复用 `information_schema.statistics` 判断的话，迁移失败重跑会直接 duplicate key。

7. **临时脚本别放仓库根目录**
   `.tmp-*` 会被 git 扫到；本轮验证脚本已删。

## 五、怎么用 / 怎么扩展

### 其他大表列表也想跳过 COUNT

```ts
// 1) DTO 加同名字段（照抄 QueryUserDto.skipCount 的三行）
@IsOptional() @IsIn(['true', 'false']) skipCount?: string

// 2) service 里把 paginate 的 count 打开
const result = await paginate(qb, { page: query.page, pageSize: query.pageSize, count: query.skipCount !== 'true' })

// 3) 前端拿到 total = -1 时换文案，用 hasNext 判断能不能翻页
```

`total = -1` 是**约定的未知值**，不要用它做算术。

### 搜索语义临时回退

```bash
# 部署环境变量（重启生效）：回到三列包含匹配，千万行下会很慢，只用于排障
USER_SEARCH_MODE=contains
```

### 新增索引的规范

1. 写进 `src/migrations/<timestamp>-<Name>.ts`，用 `information_schema` 判断幂等；
2. 同时在实体上加 `@Index('同名', [...])`，否则 `migration:generate` 下次会想删它；
3. 复合索引把**等值条件放前、排序列放后**（`(del_flag, create_time)`），低基数列单独建索引基本没用。

### 生产环境执行迁移注意事项

- 千万行表建二级索引：MySQL 8 默认 Online DDL（不阻塞读写），但仍会持续占用 IO，**放低峰执行**；
- 批量导入/刷数前可临时 `DROP INDEX` 再重建，能省 30%~50% 写入时间；
- 索引会让写入变慢（每行多维护 2 个索引），这是用写换读，本场景（读多写少）值得。
