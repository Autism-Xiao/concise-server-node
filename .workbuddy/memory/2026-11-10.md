## 冒烟脚本开关冲突（重要）

`scripts/smoke-captcha.mjs`（18 项）需要 `CAPTCHA_ENABLED=true`，其余冒烟脚本一律 `false`。已把它做成自检：

- 开头一次裸登录探针，能登进去 = 开关没开 → 打印提示 + **退出码 2**；
- `/auth/captcha` 拿不到出图（旧实例 / 429 限流）→ **退出码 3**，不再以 TypeError 崩在半路；

反复跑本脚本会触发 `/auth/captcha` 频率限制（120/60/IP/路由），被 429 时等一分钟再跑。

## 业务错误码分段细化（本轮）

审前后端 code 定义，发现「后端定义得很细、前端消费端完全没接上」：

- `login.tsx` 用 `message.includes('已锁定')` 判账号锁定 → 文案一改就静默失效。根因是 `ApiError` 没透传业务码，调用方想按码分支也拿不到。
- `http.ts` 里 `json.code === 401` 初审时以为是死分支（后端 401 的 body code 恒为 1003/1007），**删完单测当场红** —— `http-unauthorized.test.cjs` 有 `business401` 用例（HTTP 200 + code 401）锁定了这个兼容分支，已恢复并加注释。另外把 `res.status === 401` 移到 `parseJsonBody` 之前（401 响应体可能不是合法 JSON，先解析会抛解析错、走不到登出）。
- 414/415/416 是短信验证码遗产，全项目零使用，但 Swagger 还在宣传 415。
- 过滤器把未映射的 4xx（如 409）一律映射成 1006「内部错误」，HTTP 与 body 自相矛盾。

改法：
- `biz-error-code.enum.ts` 重写分段：冻结段（0/41x/1001~1009/429/503，**只增不改**）+ 21xx 认证 / 31xx 角色 / 41xx 组织 / 51xx 配置 / 61xx 文件导入 / 71xx 协作 / 81xx 租户 / 91xx 运维。四位数与三位老码天然可辨。
- **加码铁律：一码一消费者**——新增前必须写明谁在用（前端 UI / 监控聚合 / 重试策略），同类细节靠 message 区分（缺哪列都是 6103）。
- 替换 40 余处关键 throw；过滤器未映射 4xx 用 `status` 本身兜底，仅 5xx 回落 1006。
- 前端 `ApiError` 加 `code?: number`（构造参数追加末尾），`http.ts` 透传 `json.code`，登录页改判 `code === 1009`（`message.includes` 降级为兜底）。

坑（都花了时间）：
- `/v1/files/purge` 的 `ids` 必须是**字符串数组**，传 number 返回 `1001 每个 id 必须是字符串`。脚本没检查 code 就打印「删掉 N 项」，看起来成功其实没删，绕了一大圈。
- `smoke-file` 的「移动到根目录」偶发失败：上一轮运行被 `| head` 截断（SIGPIPE 提前退出）导致结尾 purge 没跑，根目录留 `改名后.md`，下次 move 撞同名 400。已在脚本开头加「按冒烟专用命名清根目录残留」，并给该断言补诊断信息。
- 替换 throw 后 `BadRequestException`/`NotFoundException` 的 import 会变成未使用，`eslint --max-warnings=0` 逐个报出来（4 个文件）。

回归：13 个冒烟脚本全绿（tenant 30 / tenant-admin 20 / provision 27 / isolation 23 / dept-status 9 / platform-admin 8 / user-setting 18 / menu-perm-nodes 14 / batch-io 31 / file 39 / dashboard 60 / auth-lock-watermark 22 / captcha 18）。

## 租户切换器挪进头像菜单（concise-admin 034dcc4）

用户对比三个方案（顶栏/头像下拉/侧边栏顶部）后选了头像下拉。实现：逻辑抽成 `features/system/tenant/use-tenant-switch.ts` hook（唯一实例，NavUser 持有），新增 `tenant-switch-dialog.tsx` 纯展示弹窗；nav-user 菜单 label 区显示「当前租户：xxx」，`switchable=false`（单租户非超管）时菜单项不渲染；site-header 移除按钮，删 tenant-switcher.tsx。软切换机制不变；hook 依赖 epoch 在切换后重新拉取 mine，菜单里当前租户自动刷新。

## 租户信息提升到全局 context（concise-admin fb9a3a8）

针对「挪进头像菜单后当前租户不可见」，最终形态：`tenant-scope-provider` 扩展持有 mine 数据（tenants/isSuper/current/currentLabel/switchable/switchTo，依赖 epoch 自动刷新），顶栏加 `tenant-badge.tsx`（常驻显示当前租户名，一次点击直达弹窗），头像菜单保留「切换租户」入口 + label 显示当前租户，两处共用 context 单一状态。`use-tenant-switch.ts` 已删，逻辑并入 provider；`tenant-switch-dialog.tsx` 保持纯展示收 props。

结论：租户切换的 UI 状态必须放 context（provider 在 _authenticated 内挂载，必已登录），不能各自调 hook——两个实例会导致切换后状态不同步。
