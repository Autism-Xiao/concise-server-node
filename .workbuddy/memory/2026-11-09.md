## 性能优化落地（对应评估报告 5 项的第 1/2/3/5 项）

- 迁移 `PerfIndexes1794230000000`：`sys_user(del_flag, create_time)`、`sys_user(del_flag, realname)`、`sys_user_depart(dep_id, user_id)`，幂等（information_schema 判断）+ `down()` 可回滚；实体同步加 `@Index`，否则 `migration:generate` 会把索引当孤儿删掉。**开发库已执行**
- `paginate(qb, { count: false })`：多取 1 条判 `hasNext`，`total`/`pages` 返回 **-1**（显式「未知」，不是 0）；`Pagination` 加可选 `hasNext`。用户列表 DTO 加 `skipCount: 'true'|'false'`，前端 `fetchUsers` 固定带 true，文案改三态
- 搜索 `src/modules/user/user-search.util.ts`：前缀 + **按字符集分流**。实测 100 万行：三列前缀 OR 不命中 3.38s（优化器不做 index_merge，退化成沿 create_time 顺序扫全表），ASCII 两列 OR 0.3ms，中文单列 realname 0.12ms。代价：英文姓名（realname='John'）用 ASCII 关键字搜不到，`USER_SEARCH_MODE=contains` 可回退
- LIKE 通配符 `\ % _` 必须转义，否则输入 `_` 等于任意匹配
- CPU 采样后台化：`MonitorService.onModuleInit` 起 5s 定时器（`MONITOR_CPU_SAMPLE_MS` 可调），`getServerInfo` 读缓存不再 `await 200ms`；定时器必须 `unref()`。首页 p50 216ms → 31~54ms
- 100 万行实测（`concise_perf_check`，测完 DROP）：列表首页 0.33ms（Backward index scan）、LIMIT 100 0.14ms、COUNT(*) 358ms、搜索 0.3ms

### 本轮踩的坑

- `CREATE INDEX ... ALGORITHM=INPLACE, LOCK=NONE` 语法报错（COMMENT 位置 + 逗号都不行），干脆不写，MySQL 8 普通二级索引默认就是 Online DDL
- 单事务 `INSERT ... SELECT` 灌 100 万行跑到 679s 未完成，`KILL` 后 InnoDB 回滚 **1180 秒**且一直锁表，后续批次全部 1205；正确做法是分批提交（10 万/批 ≈ 7 秒）
- `typeorm migration:show` 的 `[ ]` 按 name 比较，类名带数字前缀时不可信；以 `migration:run` 的「N new」为准
- 灌数测性能时临时 `SET GLOBAL innodb_flush_log_at_trx_commit=2`，**测完必须改回 1**

## 部门表列合并 + 区划搜索扩容（收尾上一轮遗留两项）

- 搜索提示文案不能再用 `records.length`（截断后恒等于 limit），必须用后端 `total` → 新增 `searchTotal` state

- CDP 坑：`Input.insertText` 打不进 React 受控输入框（Base UI），必须点焦点 + 原型 `value` setter + `dispatchEvent(new Event('input'))`
- 判断表格溢出要用 `clientWidth`（不含边框）比 `scrollWidth`，用 `getBoundingClientRect().width` 会差 2px 误判

## 用户设置改「建号即建行」（去掉懒创建）

- 原来只有 `PUT /users/me/settings` 的 `upsert` 会写 `sys_user_setting`，新账号必须登录点一下设置才有行 → 用户表 4 行 / 设置表 2 行
- 新增 `UserSettingService.ensure(userId, manager?)`：`INSERT IGNORE` 一行 `'{}'`；在 `UserService.create()` 事务内调用，`restore()` 重建，`delete()` 清 `sys_user_setting`（与 role/depart/post/watermark 同一处清理）
- `UserModule.imports` 加 `UserSettingModule`（后者不反向依赖，无循环）
- 迁移 `1794250000000-BackfillUserSetting`：`INSERT IGNORE ... SELECT id,'{}',NULL FROM sys_user WHERE del_flag=0`；down 只删 `settings='{}' AND update_time IS NULL`（这个组合只可能是系统建的空行，`save()` 必写 update_time）
- **存 `'{}'` 不存完整默认值**：默认值随前端迭代会变，固化会让老用户永远停在旧默认，也看不出「到底有没有自定义过」；`update_time` 留 NULL = 从未修改
- **坑**：`ensure` 不能 `upsert`（覆盖语义会冲掉真实偏好）；事务内必须传 `manager`（默认连接看不到未提交数据）；`get()` 现在会返回 `{settings:{},updatedAt:null}`，前端 `if (!json.result?.settings)` 对 `{}` 是 truthy → safeMerge 成默认值，行为正确，前端无需改
